## Capability summary

`tools` and `tools.binaries` have package markers. The `tools` module docstring describes release instruments; `tools.binaries` describes a release-only PyApp builder excluded from the product wheel. Those packaging and test-discovery explanations are documentation claims in the source, not independently checked here ([tools/__init__.py:1-11](../../../../tools/__init__.py#L1); [tools/binaries/__init__.py:1-17](../../../../tools/binaries/__init__.py#L1)).

Two general-purpose guards live alongside the release tooling. [tools/absolute_import_gate.py](../../../../tools/absolute_import_gate.py) parses Python ASTs under `src/vaultspec_rag` and reports absolute `from vaultspec_rag.x import ...` sibling imports unless the statement carries `absolute-import-ok`; its documented scope explicitly excludes `import vaultspec_rag.x` and dotless `from vaultspec_rag import x` forms ([tools/absolute_import_gate.py:1-23,36-55,58-79](../../../../tools/absolute_import_gate.py#L1)). [tools/advisory.py](../../../../tools/advisory.py) runs a scanner without a shell, treating configured finding exit statuses as advisory success while preserving other failures and a distinct missing-command status ([tools/advisory.py:31-62,65-82,85-107](../../../../tools/advisory.py#L31)).

[tools/binaries/build_pyapp.py](../../../../tools/binaries/build_pyapp.py) builds two standalone launchers for the `vaultspec-rag` distribution, one using module execution and one an object spec. It selects or validates a single exact project wheel, configures PyApp with the project/version, GPU and MCP extras, Python 3.13 and embedded interpreter settings, and invokes pinned PyApp through Cargo for the requested target ([tools/binaries/build_pyapp.py:87-113,119-197,199-257](../../../../tools/binaries/build_pyapp.py#L87)). It also parses Linux ELF version requirements to enforce per-target glibc floors, names assets using the packaging product definitions, stamps Windows icon/version resources, and writes SHA-256 sidecars with LF endings ([tools/binaries/build_pyapp.py:264-409,412-428,431-509](../../../../tools/binaries/build_pyapp.py#L264)). Its module documentation says the embedded runtime removes the user's Python prerequisite but the first launch still needs network access; that statement was not validated against a produced binary ([tools/binaries/build_pyapp.py:28-48](../../../../tools/binaries/build_pyapp.py#L28)).

Torch bootstrap selection is isolated in [tools/binaries/torch_channel.py](../../../../tools/binaries/torch_channel.py): it reads the configured HTTPS index and derives the locked torch version, maps Windows and Linux target triples to wheel tags, constructs an ABI-specific wheel URL, and returns a direct `torch @ URL` requirement. Unsupported targets return `None` ([tools/binaries/torch_channel.py:45-68,71-89,92-124](../../../../tools/binaries/torch_channel.py#L45)).

Bun provisioning is split among static pins, host identification, redirect policy and `provision_bun`. The pin module contains a version plus archive and executable digests for four native targets ([tools/binaries/bun_pins.py:1-40](../../../../tools/binaries/bun_pins.py#L1)). `host_target()` maps supported OS/architecture pairs and raises `UnsupportedTargetError` for unknown hosts ([src/vaultspec_rag/native_binary/\_targets.py:49-67](../../../../src/vaultspec_rag/native_binary/_targets.py#L49)). `provision_bun(cache, target)` requires a supported native host target, downloads the pinned release archive through the runtime downloader, extracts and verifies it, verifies the executable digest, runs the verified binary's `--version`, and returns its cache path ([tools/binaries/bun_toolchain.py:27-59](../../../../tools/binaries/bun_toolchain.py#L27)). The release redirect allowlist is a fixed set of GitHub and asset-store hosts ([tools/binaries/release_hosts.py:7-18](../../../../tools/binaries/release_hosts.py#L7)).

[tools/binaries/windows_icon.py](../../../../tools/binaries/windows_icon.py) parses bounded ICO containers, constructs PE icon group and version-resource payloads, commits resources with the Win32 API, then reads them back for exact verification. It also derives user-visible version fields from a product and executable record. PE resource operations reject non-Windows hosts ([tools/binaries/windows_icon.py:31-79,82-121,129-169,211-303,327-364,367-440](../../../../tools/binaries/windows_icon.py#L31)).

The six test modules cover separate contracts: [tools/binaries/tests/test_build_pyapp.py](../../../../tools/binaries/tests/test_build_pyapp.py) checks wheel selection/identity, build environment, asset naming, checksum bytes, entry-point metadata and workflow/recipe wiring ([tools/binaries/tests/test_build_pyapp.py:53-97,100-129,171-225,228-351,354-438](../../../../tools/binaries/tests/test_build_pyapp.py#L53)); [tools/binaries/tests/test_bun_toolchain.py](../../../../tools/binaries/tests/test_bun_toolchain.py) checks target pin coverage and verified archive/executable admission cases ([tools/binaries/tests/test_bun_toolchain.py:26-93](../../../../tools/binaries/tests/test_bun_toolchain.py#L26)); [tools/binaries/tests/test_platform_floor.py](../../../../tools/binaries/tests/test_platform_floor.py) checks that Linux targets in the workflow matrix declare floors ([tools/binaries/tests/test_platform_floor.py:28-52](../../../../tools/binaries/tests/test_platform_floor.py#L28)); [tools/binaries/tests/test_release_workflow.py](../../../../tools/binaries/tests/test_release_workflow.py) encodes release workflow contracts for dispatch inputs, provenance, checksum/archive coverage, permissions, publication ordering, rehearsal and action pins ([tools/binaries/tests/test_release_workflow.py:27-94,97-185,188-275,299-410,412-539,547-699,702-850](../../../../tools/binaries/tests/test_release_workflow.py#L27)); [tools/binaries/tests/test_torch_channel.py](../../../../tools/binaries/tests/test_torch_channel.py) checks target mappings and consistency with project lock/config ([tools/binaries/tests/test_torch_channel.py:37-147](../../../../tools/binaries/tests/test_torch_channel.py#L37)); [tools/binaries/tests/test_windows_icon.py](../../../../tools/binaries/tests/test_windows_icon.py) checks ICO and version resource cases plus a Windows-only real-PE scenario ([tools/binaries/tests/test_windows_icon.py:32-158](../../../../tools/binaries/tests/test_windows_icon.py#L32)). These are test expectations only; none were executed.

## Interfaces and data flow

- Executable script entry points are `absolute_import_gate.main()` and `advisory.main()`. The import gate takes no CLI options and returns 0 for no findings, 1 for findings, or 2 for a missing package tree ([tools/absolute_import_gate.py:58-83](../../../../tools/absolute_import_gate.py#L58)). The advisory CLI accepts repeated `--finding-exit N`, then `--` and a command vector; it executes with `shell=False`, forwards scanner output, and returns the mapped scanner status ([tools/advisory.py:31-55,85-111](../../../../tools/advisory.py#L31)).
- `build_pyapp.main()` accepts exactly one of `--tag` or `--version`, plus optional `--target`, `--wheel` or `--wheel-dir`, and `--outdir`; it writes two target-named executables and checksum files. Wheel inputs are validated from wheel metadata, not the filename ([tools/binaries/build_pyapp.py:119-197,431-509](../../../../tools/binaries/build_pyapp.py#L119)). The per-binary PyApp configuration comes from `Binary`, `PROJECT_FEATURES`, `PYTHON_VERSION`, and `pip_extra_args`; Cargo is the build subprocess ([tools/binaries/build_pyapp.py:87-113,199-257](../../../../tools/binaries/build_pyapp.py#L87)).
- `provision_bun(cache, target) -> Path` uses a caller-supplied cache root and target; downloaded archives are temporary within the version/target cache directory and removed after extraction. Existing or newly extracted binaries are checked against the pinned executable digest and version ([tools/binaries/bun_toolchain.py:27-59](../../../../tools/binaries/bun_toolchain.py#L27)).
- `torch_channel.index_url(root?)`, `wheel_url(target, python_version, root?)`, and `pip_extra_args(...)` expose configuration-derived values. `index_url` reads [pyproject.toml](../../../../pyproject.toml); the version is obtained through `locked_torch_version`, and the build tool injects the resulting requirement into `PYAPP_PIP_EXTRA_ARGS` ([tools/binaries/torch_channel.py:71-124](../../../../tools/binaries/torch_channel.py#L71); [tools/binaries/build_pyapp.py:229-234](../../../../tools/binaries/build_pyapp.py#L229)).
- Windows stamping takes an executable path, governed ICO path and `VersionInfo`. It writes icon and version resources in one update transaction, then verifies the resulting resource bytes before the builder calculates the checksum ([tools/binaries/windows_icon.py:348-364](../../../../tools/binaries/windows_icon.py#L348); [tools/binaries/build_pyapp.py:481-503](../../../../tools/binaries/build_pyapp.py#L481)).
- State is filesystem-based: builder output directory and temporary build directory, Bun's version/target cache path, project config/lock reads, and per-asset checksum sidecars. Integrations visible in these files are Cargo, subprocess execution of Bun, HTTPS release downloads, PyTorch wheel URLs and Win32 PE resource APIs ([tools/binaries/build_pyapp.py:199-257,471-509](../../../../tools/binaries/build_pyapp.py#L199); [tools/binaries/bun_toolchain.py:31-59](../../../../tools/binaries/bun_toolchain.py#L31); [tools/binaries/torch_channel.py:76-108](../../../../tools/binaries/torch_channel.py#L76); [tools/binaries/windows_icon.py:129-169,327-364](../../../../tools/binaries/windows_icon.py#L129)).

## Boundaries and dependencies

Local relationships visible in the inspected code: the builder imports host triple detection, torch bootstrap selection, Windows resource helpers and packaging product metadata ([tools/binaries/build_pyapp.py:67-70](../../../../tools/binaries/build_pyapp.py#L67)). Bun provisioning uses the pin table, host triple, release-host allowlist, executable naming and runtime download/extraction/verification helpers ([tools/binaries/bun_toolchain.py:8-21](../../../../tools/binaries/bun_toolchain.py#L8)). Torch version derivation delegates to `vaultspec_rag.torch_config._lockfile.locked_torch_version` after placing `src` on `sys.path` ([tools/binaries/torch_channel.py:45-52](../../../../tools/binaries/torch_channel.py#L45)). The Windows resource module uses `ctypes` and Win32 APIs; its product types are typing-only inputs ([tools/binaries/windows_icon.py:9-20,129-169](../../../../tools/binaries/windows_icon.py#L9)).

Dependencies not inspected, so their contracts are not asserted here: [src/vaultspec_rag/torch_config/\_lockfile.py](../../../../src/vaultspec_rag/torch_config/_lockfile.py):locked_torch_version (how the lock version is selected); [src/vaultspec_rag/native_binary/\_download.py](../../../../src/vaultspec_rag/native_binary/_download.py):download_https and [src/vaultspec_rag/qdrant_runtime/\_provision.py](../../../../src/vaultspec_rag/qdrant_runtime/_provision.py):extract_verified_archive, verify_native_binary (download and artifact-admission guarantees); [tools/packaging/products.py](../../../../tools/packaging/products.py) (supported targets and executable/asset names); and the referenced GitHub workflows and `justfile` (actual release callers and job ordering). [tools/binaries/tests/test_release_workflow.py](../../../../tools/binaries/tests/test_release_workflow.py) and [tools/binaries/tests/test_build_pyapp.py](../../../../tools/binaries/tests/test_build_pyapp.py) assert properties of workflow and recipe files, but those assertions do not establish current file contents or passing behavior in this report.
