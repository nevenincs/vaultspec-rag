## Capability summary

- Implementation — [src/vaultspec_rag/watcher_retry.py](../../../../src/vaultspec_rag/watcher_retry.py) defines the durable retry-state model, source/circuit/path-event/refusal enums, recovery marker model, and limits. It serializes state to bounded JSON with atomic durable writes; validates loaded schema and invariants; serializes transactions with thread and file locks; merges and restores exact path observations; validates path authority; and provides process-identity, error-classification, and numeric-validation helpers. It also reads recovery markers and removes stale marker temporaries under bounds.
- Implementation — [src/vaultspec_rag/watcher_retry_policy.py](../../../../src/vaultspec_rag/watcher_retry_policy.py) owns policy decisions over that state. It loads/creates root-and-source policy state, recovers abandoned attempts and marker handoffs, records exact pending path scope, reserves and admits attempts, gates retries by time/circuit, records success/interruption/failure, and reconciles refusal after a qualifying certified rebuild. Admission reservations are process-local; the durable attempt fields fence work across policy instances/processes.
- Implementation — [src/vaultspec_rag/watcher_retry_settlement.py](../../../../src/vaultspec_rag/watcher_retry_settlement.py) owns asyncio settlement tasks by resolved root. It registers a completion observer, removes completed tasks from its registry, waits for the root's tasks within a supplied deadline, and reports whether settlements have been released.
- Implementation — [src/vaultspec_rag/watcher_runtime.py](../../../../src/vaultspec_rag/watcher_runtime.py) provides in-memory convergence slots and attempt/scope data, projects manager snapshots into the legacy job registry, coalesces dirty paths into attempts, applies terminal outcomes and replacement backoff, logs transitions, reconciles durable attempt fences with manager history, and settles recovered attempts through the durability layer. It also exposes a rebuild reconciliation function for an already-existing retry state file.
- Documentation claims — The [src/vaultspec_rag/watcher_runtime.py](../../../../src/vaultspec_rag/watcher_runtime.py) module docstring says the watcher uses `watchfiles.awatch()` for `.vault/` and project-root changes and triggers incremental indexing (lines 1–5). The inspected file contains runtime coordination helpers but no visible `awatch` import or watcher-loop entry point; that claim is not verified by this slice.
- Test expectations — No test files were assigned or read. No passing-test or test-expectation claims can be made from this coverage.
- Inference — Together these modules appear to implement durable, source-qualified watcher convergence with exact changed-path scope, retry/circuit controls, recovery fencing, and in-memory orchestration. The slice does not establish how an external watcher loop creates/routs events or invokes these APIs.

## Interfaces and data flow

- `WatcherRetryPolicy.for_root(root, source, ...)` obtains configuration, resolves/canonicalizes the root, and builds `{root}/{data_dir}/watcher-retry/{source}.json`. Construction takes the transaction lock, reads or creates state, checks root/source and scope-limit authority, applies marker recovery, and may recover an abandoned attempt ([src/vaultspec_rag/watcher_retry_policy.py:547–577, 410–495](../../../../src/vaultspec_rag/watcher_retry_policy.py#L547)).
- `WatcherRetryState` stores retry/circuit state and convergence authority: pending and captured observations, generation, scope bounds/refusal, attempt/job/token/owner fields, error/failure/progress timestamps, and root/source ([src/vaultspec_rag/watcher_retry.py:157–198](../../../../src/vaultspec_rag/watcher_retry.py#L157)). `read_state` accepts schema 2 or 3, promotes to schema 3, and validates attempt and scope relationships; `write_state` checks configured bytes and uses durable atomic JSON output ([src/vaultspec_rag/watcher_retry.py:334–347, 498–575, 578–641](../../../../src/vaultspec_rag/watcher_retry.py#L334)).
- An event batch enters `mark_scope_pending`: observations must be nonempty and valid for this source; identities are merged by source/path and assigned a new convergence generation. Exceeding path or serialized-byte capacity records a refusal requiring full reindex rather than truncating the exact scope ([src/vaultspec_rag/watcher_retry_policy.py:584–621](../../../../src/vaultspec_rag/watcher_retry_policy.py#L584)).
- Admission first reserves a process-local UUID token, then `admit_reserved` refreshes durable state and rejects missing intent, structural refusal, an existing attempt, or an active retry delay. An admitted attempt records owner identity and generation; when a `job_id` is provided, pending observations are moved into captured observations ([src/vaultspec_rag/watcher_retry_policy.py:727–842](../../../../src/vaultspec_rag/watcher_retry_policy.py#L727)).
- The outcome methods require the matching active generation and owned token. Success clears the attempt and captured paths while retaining newer pending intent/refusal; interruption restores captured paths; failure classifies the error, applies jittered backoff/circuit rules, and restores captured scope ([src/vaultspec_rag/watcher_retry_policy.py:884–943, 945–997, 998–1086](../../../../src/vaultspec_rag/watcher_retry_policy.py#L884)).
- If cancellation cannot use the main state lock, `write_recovery_marker` writes a uniquely named sibling marker containing root/source, observed generation, attempt token, owner process identity, and creation time. The policy later consumes bounded markers under the state lock and marks exact-scope loss as unscoped/full-reindex-required ([src/vaultspec_rag/watcher_retry_policy.py:679–725, 1226–1282](../../../../src/vaultspec_rag/watcher_retry_policy.py#L679); marker parsing in [src/vaultspec_rag/watcher_retry.py:413–495](../../../../src/vaultspec_rag/watcher_retry.py#L413)).
- Runtime `WatcherConvergenceSlot` keeps pending/held paths, per-attempt path sets and retry generations, manager job identity, replacement timing, and observed state behind an `RLock`. Capturing moves a batch into held scope; terminal success for watcher-owned work releases captured paths, while other terminal outcomes return held scope to pending ([src/vaultspec_rag/watcher_runtime.py:118–195, 278–298](../../../../src/vaultspec_rag/watcher_runtime.py#L118)).
- Runtime recovery reads the retry policy's durable fence, looks up its `job_id` in manager history, verifies exact incremental watcher authority, and either reattaches an active job or settles a terminal/missing/mismatched attempt. It scans terminal history for rebuild evidence when appropriate ([src/vaultspec_rag/watcher_runtime.py:435–499, 516–553](../../../../src/vaultspec_rag/watcher_runtime.py#L435)). The separate `reconcile_completed_rebuild` path only acts on succeeded explicit rebuild jobs and only when the corresponding state file already exists ([src/vaultspec_rag/watcher_runtime.py:555–594](../../../../src/vaultspec_rag/watcher_runtime.py#L555)).
- `register_retry_settlement(root, task, observe)` tracks one task until the callback observes its result. `wait_for_retry_settlements(root, deadline)` returns false on timeout, pending work, cancellation, or task exception; `retry_settlements_released` checks whether the resolved root has no tracked tasks ([src/vaultspec_rag/watcher_retry_settlement.py:17–61](../../../../src/vaultspec_rag/watcher_retry_settlement.py#L17)).

## Boundaries and dependencies

- The direct local relationship is [src/vaultspec_rag/watcher_retry_policy.py](../../../../src/vaultspec_rag/watcher_retry_policy.py) → [src/vaultspec_rag/watcher_retry.py](../../../../src/vaultspec_rag/watcher_retry.py) for state types and persistence primitives; [src/vaultspec_rag/watcher_runtime.py](../../../../src/vaultspec_rag/watcher_runtime.py) → retry policy/state abstractions for coordination; and [src/vaultspec_rag/watcher_runtime.py](../../../../src/vaultspec_rag/watcher_runtime.py) dynamically imports the recovered-attempt settlement layer ([src/vaultspec_rag/watcher_runtime.py:596–645](../../../../src/vaultspec_rag/watcher_runtime.py#L596)).
- Durable state and marker files are filesystem-backed; the state transaction uses a per-path in-process lock plus a lock file. Admission-token reservations and retry-settlement task ownership are process-local maps ([src/vaultspec_rag/watcher_retry.py:89–102, 272–331](../../../../src/vaultspec_rag/watcher_retry.py#L89); [src/vaultspec_rag/watcher_retry_policy.py:82–89](../../../../src/vaultspec_rag/watcher_retry_policy.py#L82); [src/vaultspec_rag/watcher_retry_settlement.py:13–15](../../../../src/vaultspec_rag/watcher_retry_settlement.py#L13)).
- Imported behavior not inspected: `_typed_fields`, `_atomic_write`, `_job_errors`, `_process_probe`, `_store_locks`, `_root_identity`, indexer publication/ledger modules, `job_models`, configuration, `_backoff`, manager/job registry, logging, and `watcher_durability`. References to these describe call boundaries only, not their internal guarantees.
- No external watcher loop or direct `watchfiles` integration is visible in the assigned implementation ranges. Whether another module invokes these helpers and how it routes filesystem events requires an authorized caller read.
