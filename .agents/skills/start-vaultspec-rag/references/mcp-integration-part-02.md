## Capability summary

This slice is a suite of behavioral contracts and architecture guards. It does not itself establish that any test passes or that the implementation currently satisfies these expectations.

- [src/vaultspec_rag/tests/test_machine_discovery_resolution.py](../../../../src/vaultspec_rag/tests/test_machine_discovery_resolution.py) specifies machine-service discovery against temporary storage/status locations. It covers absent, ready, and degraded resolution; a live lock plus fresh pointer; stale, malformed, portless, foreign-PID, missing, and unnamed-holder cases; status-file fallback only when no live machine service takes precedence; evidence fields/reasons; and the default-port helper. Its fixtures write actual JSON pointer/status files and acquire a real lock, according to the test setup and descriptions.
- [src/vaultspec_rag/tests/test_machine_lock_presence.py](../../../../src/vaultspec_rag/tests/test_machine_lock_presence.py) specifies that OS inspection errors leave lock ownership uncertain and produce degraded/probe-failed expectations, while a confirmed missing lock is absent and a read-only probe must not create the anchor.
- [src/vaultspec_rag/tests/test_machine_pressure.py](../../../../src/vaultspec_rag/tests/test_machine_pressure.py) specifies pressure-tier classification and transitions from `MachinePressureSignals`, an injected clock, and `PressureEvaluator`: three-sample escalation, sample cadence, quiet-window release and rung-by-rung descent, stale/backwards-clock release, storage-failure distinctions, and a ceiling for GPU/forward pressure. It also specifies the evidence payload shape, selecting the worst forward, no backend probe for idle evidence, `/jobs` envelope exposure, CLI line rendering, cache/sample interval equality, and structured transition/staleness events.
- [src/vaultspec_rag/tests/test_machine_singleton_reclaim.py](../../../../src/vaultspec_rag/tests/test_machine_singleton_reclaim.py) specifies reclaiming a wedged child process that holds the machine lock, a no-holder no-op, held-but-unnameable probe results, and an explicit refusal/error for reclaiming an unnameable holder.
- [src/vaultspec_rag/tests/test_managed_install.py](../../../../src/vaultspec_rag/tests/test_managed_install.py) specifies expected `classify_managed_binary` verdicts for missing, pinned, unpinned, obstructed, unreadable, and accompanied paths. It covers digest/pin matching, manifests not changing byte-based verdicts, symlink refusal, companion-file cleanup guidance, accepted install working files, and refusal text. The module docstring says resolver, spawn check, provisioner, and status listing share this verdict; those callers were not inspected.
- [src/vaultspec_rag/tests/test_managed_log_sink.py](../../../../src/vaultspec_rag/tests/test_managed_log_sink.py) specifies CR redraw framing, CRLF split across writes, and bounded framing state for `RawRotatingLogSink`. Although the module docstring mentions rollover and the fixture configures backups, the displayed tests do not assert rollover behavior.
- [src/vaultspec_rag/tests/test_markdown_passages.py](../../../../src/vaultspec_rag/tests/test_markdown_passages.py) specifies `parse_markdown` passage/section behavior: nested headings, fenced heading-like text, verbatim offsets and file-line spans, list/long-line splitting, short-lead merging, setext headings, thematic breaks, clipping, and offset-to-section/line queries.
- [src/vaultspec_rag/tests/test_marker_discipline.py](../../../../src/vaultspec_rag/tests/test_marker_discipline.py) specifies tier classification and pytest collection/scheduling gates: untiered or contradictory markers are rejected; modifiers and `torch` do not act as tiers; selected tiers are extracted; distributed GPU runs and mixed hardware tiers are refused while allowed CPU/serial/separated lanes remain admissible. It also text-inspects MPS acceptance assertions and CI/release workflow wiring; those target files were not read here.
- [src/vaultspec_rag/tests/test_mcp_conformance_surface.py](../../../../src/vaultspec_rag/tests/test_mcp_conformance_surface.py) specifies an MCP tool/schema/annotation surface, root resolution precedence, code-file admission/refusal over a live local service, resource-template behavior, server identity metadata, and a legible empty-body HTTP 404. **Internal mismatch:** the module docstring describes search, index-refresh, and read-only retrieval tools, while `_EXPECTED_TOOLS` also includes `clean_documents` and `clean_all`; later assertions explicitly classify clean tools as destructive/idempotent.
- [src/vaultspec_rag/tests/test_mcp_import_isolation.py](../../../../src/vaultspec_rag/tests/test_mcp_import_isolation.py) defines static AST expectations against imports from selected package submodules and a fresh-interpreter expectation that importing `vaultspec_rag.mcp` does not load listed ML/vector-store libraries. It also tests its relative-import detector on allowed and forbidden examples. The package tree itself was not traversed.

## Interfaces and data flow

Observed interfaces are test call sites and asserted values. Test code calls the named APIs below; their production contracts remain unverified in this slice.

- Discovery tests set the configured storage and status environment variables, prepare temporary directories, write pointer/status JSON, acquire/release a machine lock, then call `resolve_machine_service()`, `_default_service_port()`, and `probe_machine_lock()`. Assertions inspect resolution state/source/port/PIDs/token/heartbeat/reason and evidence. The presence and reclaim tests inject stat/open failures or start a subprocess holder before probing/reclaiming.
- Pressure tests feed typed signals and synthetic times to `PressureEvaluator.observe`; the service-side evidence cases call `machine_pressure`; the route case creates the production HTTP app and requests `GET /jobs` with a bearer token; CLI cases call `_machine_pressure_line`. Tests assert dict keys/values and log-message fragments.
- Managed-install cases create temporary version directories and files, then call `classify_managed_binary` or `unreadable_refusal`; an explicit stand-in pin seam is used for healthy cases. The log-sink tests call `write` and `close`, then inspect emitted bytes.
- Markdown tests pass bodies and offsets/line origins to `parse_markdown`, then inspect `Passage` fields and structure helpers (`clip`, `line_of`, `section_at`, `span_lines`).
- Marker tests construct fake collected items and pytest option namespaces, then call tier-reading/enforcement helpers. Two additional tests read MPS test/workflow files from disk as part of their own assertions; their contents are outside this slice.
- MCP conformance tests inspect `mcp.list_tools()` and resource templates; other cases call `get_code_file` through the MCP adapter while a local Uvicorn service is running, call `mcp.read_resource`, query client metadata, or call `_do_http_call` against a local empty-404 HTTP server. The tests assert tool names, JSON schemas, annotations, result text/errors, and metadata. MCP import isolation statically parses package files during the test and launches a fresh Python interpreter for the import check; neither action was executed in this task.

Temporary paths and environment variables are the principal isolated state shown in these tests. Machine discovery also uses lock and JSON pointer/status files; other exercised state includes a child process, loopback HTTP servers, and test-time package/workflow reads. These are observations about test setup, not a traced production data flow.

## Boundaries and dependencies

- All ten modules are marked or parameterized as unit tests. Several deliberately cross seams into route composition, HTTP clients, Uvicorn, subprocesses, and OS locks, so “unit” is the test marker rather than evidence that every test is isolated from process/network behavior.
- The test sources import production symbols from `_machine_lock`, `_anchor_claim`, `serviceclient._discovery`, `pressure`, `_job_evidence`, `cli._service_stop`, `qdrant_runtime._managed_install`, `_managed_log_sink`, `_markdown_passages`, `_tier_gate`, and `mcp`/`serviceclient`. These relationships are import/call references only; their implementation and transitive dependency boundaries remain uninspected.
- Test helpers and fixtures include `_machine_lock_fixtures`, `_unnamed_lock_holder`, `test_service_stop_port`, `_fake_qdrant_binary`, `_stand_in_release`, `_http_stubs`, `_ports`, `_cli_helpers`, and `_state_fixtures`. Their internals were not followed. The MCP isolation tests themselves inspect `mcp/**/*.py` when run, but this audit did not.
- The MCP test's expected surface contains destructive clean operations alongside search/read-only and refresh operations, despite the narrower surface wording in its module docstring. This is a test-source discrepancy; whether it reflects current policy or stale wording requires decision/implementation context.
