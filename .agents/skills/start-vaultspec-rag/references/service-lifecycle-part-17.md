## Capability summary

This slice is a collection of unit-test expectations around service lifecycle/version compatibility, start-time backend/provisioning decisions, test-session isolation, indexing write ordering, and a small set of source/storage guards. All descriptions below are what the test source asserts or claims; none establishes that the tests pass or independently verifies production behavior.

- [src/vaultspec_rag/tests/test_service_version_compatibility.py](../../../../src/vaultspec_rag/tests/test_service_version_compatibility.py) exercises a shared version verdict across readiness publication, discovery metadata, `server start`, MCP search, doctor status, and CLI data-plane search/index. It expects incompatible and unreported service releases to fail with distinct codes and operator-facing remediation, same-release start to remain idempotent, CLI and MCP to agree, discovery schema incompatibility to degrade, and stop to remain ungated. Its test harness serves `/health` over loopback and updates the discovery pointer (lines 1-634; particularly the module setup and fixtures, classification/publication/start/MCP/discovery/doctor/data-plane groups). The introductory and individual docstrings describe the motivation and intended historical regression; those are test-authored claims, not verified history.
- [src/vaultspec_rag/tests/test_service_working_directory.py](../../../../src/vaultspec_rag/tests/test_service_working_directory.py) drives production service spawning with a stand-in child bootstrap. It asserts the child runs in the managed status directory, cannot resolve a planted executable from the invoking checkout, allows the checkout to be renamed while the child lives, receives absolute forms of relative managed settings, and only rewrites relative path-valued environment variables (1-350). The fixture also bounds the stand-in lifetime and reaps its processes.
- [src/vaultspec_rag/tests/test_serving_verdict_parity.py](../../../../src/vaultspec_rag/tests/test_serving_verdict_parity.py) feeds one table of model-loaded and Qdrant runtime combinations to the service health classifier and CLI serving verdict, expecting parity on infrastructure faults. It separately expects a degraded job-history status alone not to count as infrastructure failure (1-146).
- [src/vaultspec_rag/tests/test_session_uv_environment.py](../../../../src/vaultspec_rag/tests/test_session_uv_environment.py) covers the helper decision and one session-level assertion for `UV_PROJECT_ENVIRONMENT`: retain an unset operator value when the running interpreter is the checkout's own `.venv`, redirect a foreign interpreter to a named path under scratch, and respect an already configured value (1-136).
- [src/vaultspec_rag/tests/test_singleton_root_reclaim.py](../../../../src/vaultspec_rag/tests/test_singleton_root_reclaim.py) specifies teardown ownership and retention: remove the machine-singleton tree, preserve failed-run `basetemp` evidence when requested, delete green-run roots, reclaim an owned worker pair under an inherited root without removing siblings/root, tolerate an absent root, and avoid a nested pytest process deleting its live parent's directories (1-243).
- [src/vaultspec_rag/tests/test_slice_writer_overlap.py](../../../../src/vaultspec_rag/tests/test_slice_writer_overlap.py) uses a structural deterministic encoder and local store subclasses to specify vault encode/upsert overlap and writer semantics. Expectations include one FIFO storage writer, encoding on the caller thread, slice order, surfaced failures, mutation intent/confirmation ordering, cancellation safety, queued-task release after failure, and bounded close behavior when cancelled or wedged. It also passes lifecycle objects through code and document slice entry points (1-597).
- [src/vaultspec_rag/tests/test_source_types.py](../../../../src/vaultspec_rag/tests/test_source_types.py) specifies canonical `PublicSourceType` parsing, three compatibility aliases only when explicitly enabled, and a structured error payload for unknown or non-string values (1-48).
- [src/vaultspec_rag/tests/test_sqlite_connections_close.py](../../../../src/vaultspec_rag/tests/test_sqlite_connections_close.py) is an AST-based guard. It scans package Python sources and expects no `with sqlite3.connect(...)` scope, whose context manager commits but does not close the connection (1-64). The searched source tree was not inspected by this slice.
- [src/vaultspec_rag/tests/test_start_backend_decision.py](../../../../src/vaultspec_rag/tests/test_start_backend_decision.py) runs a case matrix across saved selection, exported environment, and CLI flags. It expects precedence and parity among `decide_backend`, the environment handed to a real child interpreter, and the start preflight; a remote address and existing service are described as orthogonal in the module docstring. A test also expects the remote-address explanation not to echo its value (1-304).
- [src/vaultspec_rag/tests/test_start_provisioning.py](../../../../src/vaultspec_rag/tests/test_start_provisioning.py) specifies host start's dependency sequence and Qdrant provisioning switch: default/explicit opt-in provision a missing managed binary, opt-out and local-store choices skip it, progress and JSON failures remain bounded to their intended surfaces, and already resolved, operator-supplied, invalid, or unpinned binaries follow guarded paths. Model availability is expected to be checked before Qdrant provisioning (1-596). The test module marks these tests as unit tests using an inference-host fixture.

## Interfaces and data flow

- Version compatibility tests set a loopback health response, write discovery status, then invoke Typer CLI commands or MCP `search_vault`. Other direct seams under test are `classify_service_version`, `compute_readiness`, `_doctor_exit_code`, `_discovery_pair_understood`, `resolve_machine_service`, and `DataPlaneService`. Expected outward results include JSON envelopes, exit codes, MCP errors, discovery states, and remediation text. The concrete implementation and transport behavior remain uninspected.
- Serving parity derives a `ServiceHealth` value and `QdrantRuntimeState`, asks `_service_health_status` for infrastructure reasons, builds a health-shaped mapping, and compares the CLI `_daemon_is_serving` result against that mapping. Test inputs/outputs are visible; health-handler implementation is not.
- The working-directory test's parent process calls `_spawn_service`; the spawned child uses a temporary `sitecustomize.py` stand-in to record its PID, CWD, safe-path flag, executable lookup, selected environment values, and resolved paths. A discovery path and process IDs are returned to the test for assertions and cleanup.
- Backend-decision tests stage an on-disk local-only choice and exported variables, derive the backend decision, build the service child environment, then run a real interpreter to read its effective settings. A separate call to `_ensure_start_dependencies` observes whether preflight expects a managed Qdrant server.
- Provisioning tests stage models/cache and a loopback stand-in release where fetching is expected. Otherwise a recorder replaces the provisioner so forbidden calls are observable. They observe resolution/manifest state, request count, console progress, exit code, and JSON envelope. These are test harness data flows, not a complete description of production provisioning.
- Session tests call `uv_project_environment_redirect` with prefix/root/configured/scratch paths and inspect the session environment. Singleton teardown tests construct representative directory trees and call `reclaim_singleton_paths`; nested cases launch a child pytest process and inspect parent/child paths and evidence.
- Writer tests send typed slice requests or `StoreWriteTask` objects through the real streaming/write seams, using event lists, thread IDs, time windows, injected latency/failure, and a real local `VaultStore` as observations. Parser tests compare inputs with enum/error outputs. The SQLite guard parses Python ASTs and reports matching `with` lines by package-relative path.
