## Capability summary

This slice is a set of repository and CI contract guards. The callers of the inspected project surfaces are these pytest modules; they parse or inspect workflow/configuration data and assert contracts. No production implementation file was assigned.

- Output formatting: [dev/guards/test_ci_formats.py](../../../../dev/guards/test_ci_formats.py) calls `dev.ci_formats.augment` with command vectors and an environment mapping. Its tests expect annotations to be opt-in, to add tool-specific formats only where supported, and to preserve a caller-selected format (lines 21-48).
- Hardware CI: [dev/guards/test_ci_hardware_tiers.py](../../../../dev/guards/test_ci_hardware_tiers.py) checks test isolation for live-service integration tests, central ownership and provisioning/order for accelerator recipes, CUDA service shutdown and monitor compilation, secret declaration/passing and service-state checks, free-port setup, Windows shell compatibility, and full checkout history (lines 81-416). Its module docstring states why duplicated accelerator jobs should be blocked (lines 1-10).
- Inference environment sizing: [dev/guards/test_ci_inference_stack.py](../../../../dev/guards/test_ci_inference_stack.py) derives a required stack from a job’s recipes and final commands, resolves the effective workflow/job/step environment, and checks initializing jobs against the allowed stack values (lines 28-99, 102-137). Its docstring describes the intended `full`/`types`/`none` mapping (lines 1-14).
- Workflow identity and verdict: [dev/guards/test_ci_job_names.py](../../../../dev/guards/test_ci_job_names.py) checks product/shared workflow naming, duplicate job display names, and matrix names that omit an axis (lines 19-69). [dev/guards/test_ci_jobs_reach_a_verdict.py](../../../../dev/guards/test_ci_jobs_reach_a_verdict.py) checks timeouts for step-running jobs, non-advisory merge-box jobs, main-branch concurrency grouping/cancellation policy, and concurrency coverage for merge-box jobs (lines 109-207).
- Merge-gate lanes: [dev/guards/test_ci_lanes.py](../../../../dev/guards/test_ci_lanes.py) checks pull-request lifecycle triggers and reusable/push/dispatch triggers, evaluates declared job conditions against a matrix of event payloads, verifies the aggregate needs every measuring job, checks required recipe/platform coverage, and checks monitor build dependencies for lifecycle suites (lines 61-89, 97-219, 246-337).
- Issue-board and duplicate-work boundaries: [dev/guards/test_ci_never_writes_the_issue_board.py](../../../../dev/guards/test_ci_never_writes_the_issue_board.py) rejects `issues: write` in workflow permission blocks and text matching the listed issue-write commands in GitHub YAML files (lines 30-89). [dev/guards/test_ci_no_repeated_work.py](../../../../dev/guards/test_ci_no_repeated_work.py) indexes expanded command vectors by job and event, allows repeats only for disjoint platforms and declared platform-sensitive recipes, and separately checks subset-lane coverage/exclusivity (lines 50-86, 100-221).
- Windows recipe compatibility: [dev/guards/test_ci_recipes_survive_cmd.py](../../../../dev/guards/test_ci_recipes_survive_cmd.py) finds recipes reachable by Windows jobs and asserts their recipe lines contain no double quote (lines 23-42).
- Release artifact and ordering: [dev/guards/test_ci_package_built_once.py](../../../../dev/guards/test_ci_package_built_once.py) checks that only the designated Publish builder contains recognized package-build commands outside a rehearsal-only step, and that the Binaries wheel job downloads the attached release wheel and verifies its digest (lines 20-74). [dev/guards/test_ci_release_draft_order.py](../../../../dev/guards/test_ci_release_draft_order.py) checks draft/tag configuration, package-index dispatch from a proof gate, exactly one late release publication, dependency/order and permission conditions, absence of release-edit recovery paths, and absence of tag/release-event triggers (lines 99-304). [dev/guards/test_ci_release_please_prs.py](../../../../dev/guards/test_ci_release_please_prs.py) checks Release Please dispatch after lock regeneration, main-push candidate/proposal selection, cut prerequisites, requested-ref checkouts, exact-SHA dev proof and approval checks, and final-stage results (lines 47-231).
- Workflow scripting: [dev/guards/test_ci_script_injection.py](../../../../dev/guards/test_ci_script_injection.py) scans workflow/local-action documents for expressions embedded in `run:` and broad workflow-level write permissions (lines 26-117).
- Environment provisioning tests: [dev/guards/test_env_provisioning.py](../../../../dev/guards/test_env_provisioning.py) exercises `dev.init.dotenv` functions against temporary files and linked worktrees. Expectations include preserving example structure, seeding only declared values, preserving existing values and permissions, refusing an unreadable line without rewriting, choosing the default-branch worktree as seed, round-trip rendering, and `.env` preflight registration (lines 40-48, 75-308). These are test expectations, not a read of the implementation.
- Exit-code and interpreter contracts: [dev/guards/test_exit_code_contract.py](../../../../dev/guards/test_exit_code_contract.py) checks imported exit-code mapping data/functions and scans authored justfiles for hand-rolled status swallowing and dead standalone `$LASTEXITCODE` checks (lines 25-68, 71-113, 116-222). [dev/guards/test_interpreter_pin.py](../../../../dev/guards/test_interpreter_pin.py) cross-checks a closed Python range, development pin, analyzer targets, CI test matrix, release smoke matrix, and workflow copies of an interpreter assertion (lines 36-78, 81-230).
- Hook exclusion: [dev/guards/test_no_commit_hooks.py](../../../../dev/guards/test_no_commit_hooks.py) checks tracked hook-runner config names, init-plan steps, and justfile/workflow text for hook installation commands (lines 25-93).

## Interfaces and data flow

The workflow guards obtain parsed workflow documents, jobs, triggers, recipes, conditions, platforms, and final command vectors through `dev.guards._workflows`; some also use constants/types from `dev.guards._ci_names`. The inspected code supplies the calls and assertions, not those helpers’ parsing or evaluation semantics. Inputs include workflow YAML and local-action YAML as text/data, workflow/job/step `env`, `if`, `needs`, matrices and permissions, recipe bodies, and synthetic event bindings. Outputs are pytest assertions/findings; embedded `gh`, `just`, and other command strings are inspected as data rather than executed by these guards. Relevant call sites include hardware workflow/job queries (hardware tiers 127-145, 154-160), event/job evaluation (lanes 259-266, 294-306), and recipe-command expansion (no repeated work 100-109).

Other inspected interfaces are narrower: [dev/guards/test_ci_formats.py](../../../../dev/guards/test_ci_formats.py) supplies argv plus an environment to `ci_formats.augment` and expects a list result (14-18, 21-48); environment tests call `provision`, `render`, and `seed_source`, inspect filesystem results, and create temporary Git repositories/worktrees via a subprocess helper (dotenv tests 51-84, 87-308); the exit-code tests call `advisory_result` and inspect repository justfiles (exit-code tests 25-38, 71-113, 116-222); interpreter tests read TOML, `.python-version`, and workflow matrices (interpreter tests 42-78, 81-190); hook tests query Git’s tracked-file index and inspect init-plan argv and installer surfaces (hook tests 46-93).

The exercised state is primarily checked-in configuration read by tests, plus temporary `.env`/Git fixtures in the provisioning tests. No service/database state or persistent application storage is established by this slice. Credential and secret names occur as asserted identifiers; this report does not reproduce any credential values.
