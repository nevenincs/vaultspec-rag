## Capability summary

This slice is a collection of unit and integration-style tests around managed job lifecycle, control, admission, persistence, and service quiesce. It probes real manager/controller/worker paths in several places and substitutes small runners or handcrafted state where stated. The production implementation is outside the read boundary.

- [src/vaultspec_rag/tests/test_job_contracts_persistence.py](../../../../src/vaultspec_rag/tests/test_job_contracts_persistence.py) is the broad persistence contract suite. It expects complete job snapshots and generations to round-trip, including enum authority, retry history, runtime/resource/resilience fields, and reuse/drift telemetry. Telemetry tests cover JSON-compatible nested values and spell out two transformations: sorted object-key order and loss of shared-reference identity. They also expect persisted capabilities to match values derived again on load (158-410). Schema cases expect the current writer to omit a retired idempotency section while the reader accepts files with it, require persisted authority, reject version 1 and older/foreign schemas, distinguish too-new state with `NewerStateVersionError`, ignore additive unknown fields, and default listed optional fields (450-666). Write-side cases expect invalid construction to be rejected before a file is written, quiesce-parked PAUSED/RUNNING state to load, failed writes to report unpublished and leave no temporary files, and serialization failures to be translated to `PersistenceWriteError` before a temporary is named (669-822). Restart cases exercise requeueing owned interruptions under the same ID, preserving spec/checkpoint and incrementing attempt number, respecting operator intent and failure state, and fencing shutdown parents when a later retry owns continuation even if timestamps roll back (824-952).
- [src/vaultspec_rag/tests/test_job_control_admission.py](../../../../src/vaultspec_rag/tests/test_job_control_admission.py) sets up two encode-capacity jobs: one worker holds protected work and the other waits for admission. It expects pause, cancel, quiesce, or shutdown to unwind the waiting attempt before its worker starts; expects a pause withdrawn before delivery to allow later execution; and expects protected work and shielded results to complete once without duplicate workers (35-229).
- [src/vaultspec_rag/tests/test_job_control_unit.py](../../../../src/vaultspec_rag/tests/test_job_control_unit.py) tests `RunControlToken` safe edges and request semantics: cross-thread pause waits for nested protected scopes to unwind, an undelivered pause can be withdrawn, delivered pause cannot, cancel is absorbing, and checkpoint precedence is shutdown then cancel then pause then quiesce. It checks that application errors are not masked, and that the null control conforms to the runtime protocol and never interrupts. Its subprocess probes expect job-manager configuration defaults, environment parsing, public overrides, and rejection of invalid limits/timeouts (85-309).
- [src/vaultspec_rag/tests/test_job_manager_admission.py](../../../../src/vaultspec_rag/tests/test_job_manager_admission.py) expects equivalent concurrent creates to converge on one exact job ID, enforce nonterminal capacity, default to a managed state file while allowing explicit memory-only mode, expand a home-relative status directory, reject invalid job kinds/roots, and deduplicate canonical-equivalent root spellings (32-209).
- [src/vaultspec_rag/tests/test_job_manager_degradation.py](../../../../src/vaultspec_rag/tests/test_job_manager_degradation.py) distinguishes two status surfaces in its assertions: an interrupted job is expected to add an `interrupted` degradation reason to project index status while remaining present but not degraded in service health. It also expects a failed state-file replace to be classified as unpublished (35-189).
- [src/vaultspec_rag/tests/test_job_manager_drift.py](../../../../src/vaultspec_rag/tests/test_job_manager_drift.py) supplies a drift block from a fake runner and expects managed success to expose it on the snapshot and public dictionary, preserve it through a later revision that omits telemetry, persist it, and restore the same revision and drift block (34-131).
- [src/vaultspec_rag/tests/test_job_manager_encode_admission.py](../../../../src/vaultspec_rag/tests/test_job_manager_encode_admission.py) expects encode-bearing index jobs to serialize on a single machine-wide limiter, records an admission timestamp on both waiting and solo jobs, passes the persisted authority into runner context, and refuses two tested mode/authority combinations before invoking the runner. It classifies index specs by source as encode-bearing and maintenance/invalid-source specs as outside that gate; asserts limiter capacity/stats; and contains a source-scan assertion that named maintenance, search, and service-lifespan modules do not mention `get_encode_limiter` (36-345).
- [src/vaultspec_rag/tests/test_job_manager_loopless_dispatch.py](../../../../src/vaultspec_rag/tests/test_job_manager_loopless_dispatch.py) probes manager dispatch from `asyncio.to_thread`: with a service loop adopted, the attempt is expected to run and succeed; without an adopted loop, the expected result is `event_loop_required` and the runner stays uncalled. It also checks direct on-loop dispatch, verifies service startup wiring through `_start_job_manager`, and expects registry reset to replace both the public manager and its quiesce controller (97-221).
- [src/vaultspec_rag/tests/test_job_manager_quiesce.py](../../../../src/vaultspec_rag/tests/test_job_manager_quiesce.py) covers timed GPU-lock wait measurement and job-record publication; quiesce drain, resource/ticket release, and same-ID resume; preparation rollback and retry after an unpublished persistence failure; restart recovery of a durably prepared queued retry; operator-intent checks at dispatch; coalescing of concurrent recovery requests; dispatch through an adopted service loop; invalidation of a queued recovery claim by cancellation or shutdown; and releasing/reassigning claims when no live owner loop remains (40-745).

The tests use test-created state paths, in-memory managers, event-controlled fake runners, and several real worker/thread/asyncio transitions. Assertions and comments provide intended contracts, but execution outcomes are unknown because this assignment prohibits running the tests.

## Interfaces and data flow

The test-probed caller path generally starts with `JobSpec` plus `JobInitiator`, passed to `JobManager.create`; tests inspect returned outcomes and snapshots. Dispatch cases bind a runner with `bind_dispatch`, then call `dispatch` or `dispatch_async`. A runner receives `JobAttemptContext` (including control and, in authority coverage, authority) and returns `JobExecutionResult`; completion is observed through manager state and sometimes an `on_finished` callback. Control tests call desired-state methods, quiesce methods, or `RunControlToken` requests and observe state, worker activity, limiter waiters, and compute-ticket counts.

Persistence tests call `save_persisted_state` and `load_persisted_state` directly, or construct a manager with `state_path`, then use `restore_persisted`. The asserted serialized/public fields include spec authority, job/attempt lineage, state and desired state, timestamps (including admission), capabilities, progress, resources, resilience, reuse/drift telemetry, and GPU-lock wait seconds. This describes fields exercised by tests; the codec’s implementation was not read.

Quiesce tests prepare resume state using `prepare_quiesced_resume`, then pass that result to `dispatch_prepared_quiesced_resume`. Other cases construct a fresh manager over the same file to test restart behavior. Tests that dispatch from worker threads adopt an asyncio service loop first, and a service-startup test calls `_start_job_manager` before dispatch. The tests therefore probe coordination between manager state, persistence, control, limiter/controller resources, and loop ownership; internal ordering is unverified here.

The manager-admission tests assert the default managed path is `status_dir/jobs-state.json` after home expansion, and that `state_path=None` selects memory-only behavior. These are test assertions, not independently verified implementation documentation.
