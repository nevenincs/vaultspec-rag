## Capability summary

- **Model pins and configuration — [src/vaultspec_rag/tests/test_model_pins.py](../../../../src/vaultspec_rag/tests/test_model_pins.py).** Expects each default dense, sparse, and reranker model to have a full commit and committed per-file SHA-256 manifest; manifest names are safe relative paths, include configuration and safetensors weights, exclude pickle-style weights, and include the sparse model's implementation file. It checks that defaults and pins agree, only the committed repository-at-committed-revision is pinned, operator-selected repositories/commits remain usable but unpinned, commit environment values require 40 hex characters, sparse has no revision setting, and dense/reranker revision settings cannot be supplied by workspace dotenv or persisted settings. Fixtures remove and restore relevant environment values around each case. These are expectations about imported pin/config APIs, not findings about their implementations.
- **Model readiness — [src/vaultspec_rag/tests/test_model_readiness.py](../../../../src/vaultspec_rag/tests/test_model_readiness.py).** Expects shallow readiness to determine cache presence without claiming digest verification, and deep readiness to report pinned-model digest mismatches as not ready with repository/file context and a warmup remedy. Both depths report missing models; readiness data also exposes pinned status and the revision used. Cases seed a hub-layout cache and exercise `compute_readiness` with a ready compute report. No readiness implementation or cache seeder was inspected.
- **Model acquisition and startup bounds — [src/vaultspec_rag/tests/test_model_setup.py](../../../../src/vaultspec_rag/tests/test_model_setup.py).** Expects sparse cache completeness to require the pinned revision and all manifest filenames; lists the three configured eager service model IDs; and checks online acquisition despite inherited offline variables, restoration after service-environment context entry failures, disabled-reranker startup markers, and rejection of offline-startup evidence with missing model markers or a hub endpoint. Real loopback HTTP 504 endpoints exercise acquisition failures, preservation of endpoint/response details, process deadlines, worker cleanup, and a shared startup envelope. Additional cases check load-based envelope scaling, exact explicit budgets, and fallback when the host load probe raises. The file imports test-side setup and integration helpers whose behavior is uninspected.
- **Snapshot validation and guarded loading — [src/vaultspec_rag/tests/test_model_snapshot.py](../../../../src/vaultspec_rag/tests/test_model_snapshot.py).** Expects directory checks to hash exact manifest files, reject missing, changed, extra, or pickle-only content with named fault categories, and recheck inventory after the checked block. A Windows-specific case expects held files to resist writes, removal, or rename while loading. It distinguishes structural completeness from digest verification, checks pinned and operator-named models, alternate commits, absent caches, safetensors and sharded-weight requirements, and tests that `loadable_snapshot` passes checked files to the loader while surfacing actionable warmup/doctor instructions for refusal classes. A fresh-interpreter case expects an absent model load to download nothing and import neither downloader command modules nor `torch`. These remain test expectations for the imported cache/pin APIs.
- **Monitor access controls — [src/vaultspec_rag/tests/test_monitor_access.py](../../../../src/vaultspec_rag/tests/test_monitor_access.py).** Builds Node scripts that exercise the monitor middleware and Vite dev/preview servers. The assertions cover rejecting nonlocal peers before dispatch across static, read, and mutation routes; local loopback acceptance; listener addresses under loopback and wildcard settings; HTTP and WebSocket admission; capability-link announcement; and an unauthenticated health request versus one carrying the announced capability. Product middleware and Vite behavior were not inspected.
- **Browser adapter — [src/vaultspec_rag/tests/test_monitor_browser.py](../../../../src/vaultspec_rag/tests/test_monitor_browser.py).** Starts a Node bridge around `local-service.ts` and sends HTTP requests through an access URL. Expectations cover forwarding jobs, logs, and search activity; separating the browser capability from the backend service token; rejecting foreign origins, unrelated routes, and missing/incorrect capabilities for reads and mutations; and draining or bounding refused request bodies. Lifecycle cases exercise fixed `server` CLI argument shapes, installed-runtime preference with checkout fallback, process options/timeouts, response credential scrubbing, status mapping, and rejection of caller-supplied commands/roots or invalid route/body shapes. Other cases exercise repository/project/service-state/runtime/storage/quiesce endpoints, service-discovery failure, local proxy authority acceptance, Tailnet or undeclared authority rejection, and denial of a second loopback source address. A projection case checks filtering and identity validation for log/activity payloads plus value comparison and log sanitization. These assertions describe the adapter and projection surface as expected by tests.
- **Browser launcher — [src/vaultspec_rag/tests/test_monitor_browser_launcher.py](../../../../src/vaultspec_rag/tests/test_monitor_browser_launcher.py).** Uses a real browser and a loopback page server that refuses its JavaScript file. It expects the launcher to discard a failed initial page load and retry until the page draws, while a page that still fails after three attempts ends as startup failure rather than being reported ready. Browser availability may cause a test skip; no launcher or browser helper implementation was inspected.
