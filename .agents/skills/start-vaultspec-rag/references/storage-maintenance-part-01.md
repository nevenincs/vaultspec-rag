## Interfaces and data flow

- **Survey:** `vaultspec-rag server storage survey` lists namespace status, count, footprint, and attributed root. It can filter with `--orphaned`/`--unknown`, query a resolved root via `--root`, request fresh data with `--fresh`, and emit JSON. The guide says a live service serves a cached survey to CLI/MCP/HTTP consumers; without it, the CLI reads the store directly. HTTP is documented with `GET /storage/survey`, optional `?fresh=true`, and response fields `computed_at` and `source`; its `totals` rollup includes store-wide size/count/status figures and backlog/read-count information (storage: lines 39-71, 286). The CLI JSON is documented as containing namespace/count information and `queried_root` for root queries, without the HTTP freshness fields or totals rollup (lines 59, 69, 286).
- **Automatic maintenance:** the guide describes a service cycle every 60 minutes by default, first run one interval after startup, disabled by `VAULTSPEC_RAG_STORAGE_AUTOPRUNE=0`. It classifies roots, advances persisted grace clocks, archives data-bearing namespaces before dropping them, and reports results. Ordinary known orphans need continuous grace; empty namespaces wait 24 hours and data-bearing namespaces 7 days. Temp-rooted namespaces use a 72-hour idle timestamp by default and a 24-hour orphan grace; reindexing refreshes `last_indexed`. Unknown and unverifiable namespaces are excluded, archive failure cancels a data-bearing drop, and reclamation is capped at 16 namespaces per cycle. The guide separately describes geometry reconcile of up to four collections per cycle (storage: lines 73-91, 93-101).
- **Reconcile:** `server storage reconcile --dry-run` previews; `--yes` applies; `--no-wait` returns before merge completion and reports no reclaimed bytes; `--limit` caps collections. The documented output waits for merges to start and settle before reporting reclaimed size, and skips work reported as `insufficient_headroom` when there is not enough room for temporary growth. Automatic reconcile can be disabled with `VAULTSPEC_RAG_STORAGE_RECONCILE=0` (storage: lines 103-130).
- **Archive and restore:** archives are described under `~/.vaultspec-rag/qdrant-server/archive/<prefix>/`, with a manifest and one snapshot per collection. Cycles remove old archives after 30 days and evict oldest first above 64 GiB, with configurable bounds. Restore takes an archive directory and `--root`, supports `--dry-run`/`--yes`, and requires a destination root with no collections (storage: lines 132-152).
- **Manual maintenance:** `server storage prune` previews/applies orphan removal, and `server storage delete <prefix>` targets one namespace; delete can require `--allow-unknown` if no root attribution exists. `prune --debris` previews/removes half-written directories with explicit confirmation and no archive/restore path. The guide also documents `delete --root <dir>` as an idempotent harness teardown that exits 0 for an absent namespace (storage: lines 154-210).
- **Harness lifecycle:** indexing a throwaway root against the resident service creates a shared-store namespace. The documented choices are isolate via harness-owned status/storage paths, unconditionally delete by root during cleanup, or remove the root and wait for scheduled reclamation. Survey marks temp-rooted namespaces (storage: lines 204-235).
- **Migration:** `server storage migrate <root> --to server|local` previews with `--dry-run` or copies with `--yes`; the source remains. Docs say the managed service must be reachable, local-store writers/processes must be closed, indexing/watchers/maintenance must not write to either index, and the migration shell's backend environment settings select the invoking CLI. Existing destinations, including partial copies, are skipped rather than repaired on rerun (storage: lines 237-261).
- **Observability:** `server jobs`, structured `service.maintenance` logs, token-gated `/metrics`, and `GET /storage/survey` are documented surfaces. Metrics cover cycle/reclaim counts, disk and dangling footprint, grace backlog, namespace count, reconcile totals/bytes, and geometry drift; low free space generates a `disk_low` warning below 10 GiB. The survey totals also expose an ephemeral backlog and unread point-count population (storage: lines 263-288).
- **Troubleshooting:** `server doctor` is the documented health entry point; inspect live service, installed dependencies, and provisioning. `status --verbose` reports stored section counts and latest retained indexing job by domain, while the guide cautions these do not prove currency or an empty store. `index --type code --dry-run` previews admitted/rejected files, displays up to 50 paths by default, and supports `--dry-run-limit` or `--json`. `index` reindexes; `--type` scopes domains and `--rebuild` rebuilds one. The service watcher is documented to reindex on file changes. Script JSON/exit-code handling is delegated to the automation guide (verification: lines 11-78).

## Boundaries and dependencies

- Storage maintenance is documented as operating on the shared managed store; migration also accesses a project's local-only store (storage: lines 5-7, 237-261). Maintenance requires the resident service; manual storage commands require reachable managed Qdrant, while survey can fall back to direct store reads. Migration also requires the server reachable (lines 5-6).
- Docs state that namespaces are derived from resolved root paths through a one-way hash, with collections sharing a root prefix; the prefix itself cannot be reversed to recover the path (storage: lines 15-29). Root lookup delegates prefix calculation to the service rather than asking external consumers to reproduce it (lines 63-71).
- The guides link to [docs/cli.md](../../../../docs/cli.md), [docs/configuration.md](../../../../docs/configuration.md), [docs/service-mode.md](../../../../docs/service-mode.md), [docs/backends.md](../../../../docs/backends.md), [docs/installation.md](../../../../docs/installation.md), [docs/automation.md](../../../../docs/automation.md), [docs/indexing.md](../../../../docs/indexing.md), [docs/preprocessing-hooks.md](../../../../docs/preprocessing-hooks.md), and [docs/search-and-index.md](../../../../docs/search-and-index.md). Those files were not inspected; exact flags, configuration validation, and linked implementation details remain outside this slice (storage: lines 5, 71, 91, 128, 235, 259, 288-295; verification: lines 3-9, 20-22, 41-60, 73-83).
- No module-level implementation responsibilities or tests can be attributed from this slice. Every behavior above is a documentation claim; the only inference is that these guides intend to route operators from diagnosis to corrective commands, as shown by their section flow (verification: lines 11-78).
