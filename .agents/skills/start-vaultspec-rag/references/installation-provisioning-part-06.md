## Capability summary

- [src/vaultspec_rag/commands/\_model_download.py](../../../../src/vaultspec_rag/commands/_model_download.py) supervises one hub snapshot download in a child process. It consumes newline-delimited JSON records, responds to the child’s declared repository size through an optional caller admission callback, reports changed snapshot counts, and converts child exit, hub failure, refusal, deadline, or inadequate progress into `DownloadOutcome`. It removes newly created incomplete blob files after interrupted or failed child runs. `exclusive_fetch` uses a cache-local OS claim so concurrent fetches wait outside the hub client’s lock; a shared `CacheWait` can bound waiting across repositories.
- [src/vaultspec_rag/commands/\_model_download_child.py](../../../../src/vaultspec_rag/commands/_model_download_child.py) is the child entry point (`python -m ... <repo>`). It makes the hub size request and snapshot request, writes JSON protocol records, and waits for the parent’s `go` response before fetching. `_Wire` counts HTTP response bytes through a hub client factory hook; `_Reporter` combines wire activity with snapshot bar counters for progress/liveness reports. Hub exceptions are classified into a failure code and first-line message.
- [src/vaultspec_rag/commands/\_model_fetch.py](../../../../src/vaultspec_rag/commands/_model_fetch.py) owns model inventory cache checking and fetch policy. It obtains configured repositories, checks each snapshot, handles dry-run/offline states, serializes same-cache downloads, checks declared size against free space before the first file, fetches missing or repair-needed repositories, then verifies again. It returns per-repository and aggregate outcomes with stable codes and operator remedies; it attempts each configured repository in inventory order and records failures as results.
- [src/vaultspec_rag/commands/\_models.py](../../../../src/vaultspec_rag/commands/_models.py) defines `InstallReport` and `UninstallReport` serialization and MCP sync aggregation helpers. It combines provider-attributed counters/errors/items, keeps unattributed errors, and exposes whether MCP sync failed. It is reporting vocabulary for enrollment flows, not the model-fetch engine.
- [src/vaultspec_rag/commands/\_provision.py](../../../../src/vaultspec_rag/commands/_provision.py) is the shared dependency provisioning front door. It defines step/result/outcome types and sequences torch configuration, model fetching, and Qdrant provisioning; maps backend results into shared `ProvisionAction` values; and gates model/Qdrant work on whether the service environment can run. `ensure_runtime_dependencies` is the narrower start-time path: it provisions models first, returns early on model failure, then considers Qdrant. Backend selection and existing-binary checks are also centralized here.
- [src/vaultspec_rag/commands/\_skip.py](../../../../src/vaultspec_rag/commands/_skip.py) defines and validates the install/uninstall `--skip` vocabulary: RAG-consumed `core`/`mcp`, core provider names other than `all`, and core sync-pass names `hooks`/`precommit`. Unknown tokens raise `ValueError` with the accepted values.
- [src/vaultspec_rag/commands/\_snapshot_progress.py](../../../../src/vaultspec_rag/commands/_snapshot_progress.py) provides `SnapshotCounts`, formats operator progress lines, and adapts the hub’s `tqdm_class` seam into thread-safe file/byte counters that draw nothing. It closes bars on completion and tolerates missing tqdm by returning `None` for the hub’s fallback.

## Interfaces and data flow

- Model fetch: `fetch_models(dry_run, progress, limits)` returns `ModelFetch`; its configured repository list becomes ordered `_Wanted` records. Each record is checked with `verify_snapshot`. If a fetch is needed, `download_snapshot(repo, revision, force, limits, caller)` starts `_model_download_child`; the child emits `declared`, then waits on stdin. The parent’s admission callback computes a possible space shortfall and either sends `go` or refuses. The child uses `HfApi.model_info` and `snapshot_download`; the parent supervises progress and exit and then repeats snapshot verification. Existing complete snapshots can return unchanged without a child or hub request.
- The child protocol is JSON-lines on stdout (`progress`, `declared`, `done`, `failed`) plus one parent-to-child `go` line on stdin. It accepts repo, optional revision, and force flags. The parent keeps only a short stderr tail for unexpected child exits. Liveness byte activity combines HTTP response byte counters and bar bytes, so it is an activity measure and can count a plain transfer twice; display counts are separately collapsed to one payload count.
- Model storage is the Hugging Face cache selected by `HF_HUB_CACHE`: snapshot verification uses that cache, incomplete files are found under the repository’s `blobs`, and the one-fetch claim is under `.locks/vaultspec-rag-fetch.lock`. Size admission credits existing blob file sizes and compares the remainder with free bytes on the cache path’s nearest existing ancestor. A caller can supply progress, admission, and monotonic deadline behavior.
- Provisioning: `provision_dependencies(target, **options)` returns `ProvisionOutcome`, with one result per considered torch/model/Qdrant step. Options include local-only, skip set, dry-run, torch configuration/sync controls, confirmation, progress, and a pre-judged service environment. Model and Qdrant steps report skipped when the environment cannot run the service. `provision_models` delegates to `fetch_models`; `provision_qdrant_binary` delegates to the Qdrant runtime provisioner after the same environment gate. `ensure_runtime_dependencies(environment, server_unneeded, qdrant_auto_provision, progress)` runs models before Qdrant. `decide_backend` resolves command overrides and settings to explain whether a managed Qdrant server is needed.
- Enrollment serialization: `InstallReport.to_dict()` reports seeded paths, sync totals/provider outcomes, torch state, MCP errors, and optional provisioning outcomes; if refused, step fields are `null`. `UninstallReport.to_dict()` reports removals and sync/provider outcomes. These structures accept `SyncResult` objects and optional provisioning/torch repair results.
- `validate_rag_skip(set[str])` is the validation entry point for the shared install/uninstall skip vocabulary. `progress_line(prefix, counts)` is the display formatter consumed by a caller; [src/vaultspec_rag/commands/\_snapshot_progress.py](../../../../src/vaultspec_rag/commands/_snapshot_progress.py) itself does not print.

## Boundaries and dependencies

- The local implementation chain is `_provision.provision_models` → `_model_fetch.fetch_models` → `_model_download.download_snapshot` → `_model_download_child.main`; `_snapshot_progress.SnapshotBars` supplies the child’s download counter. `_provision.ensure_runtime_dependencies` reuses the model and Qdrant steps, while `_provision.provision_dependencies` also maps torch configuration and the selected backend. [src/vaultspec_rag/commands/\_models.py](../../../../src/vaultspec_rag/commands/_models.py) serializes enrollment results and is used by `_provision` for the torch report type.
- Named but uninspected dependencies include Hugging Face Hub APIs/cache utilities, `.._model_cache.verify_snapshot`, `.._anchor_claim`, `.._process_probe`, `.._python_child`, `.._hub_failure`, `.._sync_vocabulary`, config/settings and environment gates, torch configuration, Qdrant runtime resolution/trust/provisioning, and `vaultspec_core` sync/provider types. This report does not infer their internal behavior.
- Source docstrings describe install, server warmup, and server-start preflight as callers of the provisioning path. The assigned files establish the internal entry points and delegation above, but do not include the upstream CLI call sites, so those call relationships remain documentation claims here.
