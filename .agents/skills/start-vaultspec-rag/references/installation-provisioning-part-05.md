## Capability summary

- [src/vaultspec_rag/commands/__init__.py](../../../../src/vaultspec_rag/commands/__init__.py) is an empty export surface: its module docstring describes the package as orchestration for install/uninstall and says callers import orchestrators and report types from their defining modules. The visible package file itself exports nothing.
- [src/vaultspec_rag/commands/\_backend_choice.py](../../../../src/vaultspec_rag/commands/_backend_choice.py) persists the host's runtime backend decision after install provisioning. A preview writes nothing; client installs do not choose the host's backend. Explicit local-only is persisted even when the environment/provision outcome would not qualify for server mode; server mode is recorded only when the host can run the service and provisioning succeeded. Persistence errors become report warnings, and the result explains what an unflagged `server start` would select.
- [src/vaultspec_rag/commands/\_hub_failure.py](../../../../src/vaultspec_rag/commands/_hub_failure.py) provides a closed failure vocabulary for model-hub fetches and helpers to classify chained exceptions and extract a concise first message line. Classification prioritizes disk-full, certificate verification, and file-specific OS errors before recognized Hub “not found” exceptions; remaining failures are unreachable.
- [src/vaultspec_rag/commands/\_install.py](../../../../src/vaultspec_rag/commands/_install.py) owns the install entry flow. It validates skip tokens, optionally repairs tool-environment Torch, prepares workspace directories and provider intent, resolves install/upgrade mode, checks required MCP topology, reconciles the optional MCP dependency, seeds bundled files, and runs Core MCP/provider synchronization. It sequences MCP state before unrelated provider sync, Torch configuration and optional dependency provisioning. Reports collect warnings, MCP errors/results, Torch actions, repair state, and provisioning outcome. Dry runs use temporary projections/replay; real MCP runs use snapshots and rollback paths.
- [src/vaultspec_rag/commands/\_mcp_extra.py](../../../../src/vaultspec_rag/commands/_mcp_extra.py) reconciles the `mcp` extra on the RAG requirement in [pyproject.toml](../../../../pyproject.toml), selecting project runtime dependencies for dependency mode and the dev dependency surface for dev mode. It stores exact ownership metadata so a later disable or move can restore only the edit it owns, and reports conflicts when the managed requirement has drifted or declarations conflict.
- [src/vaultspec_rag/commands/\_mcp_topology.py](../../../../src/vaultspec_rag/commands/_mcp_topology.py) defines required MCP filesystem nodes and a lifecycle path inventory; captures file/link snapshots and identities; rejects unsafe links, hard-link aliases, and special node types; and provides temporary materialization, exact restoration, projection, and compare-and-swap rollback operations. It also centralizes MCP failure reporting to both error and warning channels.
- [src/vaultspec_rag/commands/\_mode.py](../../../../src/vaultspec_rag/commands/_mode.py) is the RAG seam over Core's install-mode machinery. It resolves fresh-install and upgrade mode with provenance, checks whether RAG's managed MCP entry is deployed, persists only RAG's package declaration while retaining its version floor, and asks Core to force-migrate RAG's own managed entry after a mode flip.

## Interfaces and data flow

`install_run(path=None, **options) -> InstallReport` is the public install function visible in this slice. It validates RAG skip tokens, constructs an install request, and routes through the pre-install tool-repair decision. The install path then prepares the target and provider selection, resolves mode, performs MCP preflight/transition, seeds sources, asks Core to reconcile MCP and other providers, handles mode migration, configures Torch, and optionally provisions dependencies. Provisioning attaches its structured result and backend selection to the report ([src/vaultspec_rag/commands/\_install.py:859-877, 903-995, 1021-1313, 1330-1387](../../../../src/vaultspec_rag/commands/_install.py#L859)).

[src/vaultspec_rag/commands/\_install.py](../../../../src/vaultspec_rag/commands/_install.py) seeds the bundled tree under `.vaultspec/`, with special handling for MCP sources and skip behavior. Fresh MCP provider selection is derived from Core's provider manifest and is guarded by snapshots of manifests/configuration plus lock paths ([src/vaultspec_rag/commands/\_install.py:115-160, 245-337](../../../../src/vaultspec_rag/commands/_install.py#L115)). The MCP extra, package mode, and seeded intent are treated as a transition: on failure the recorded file snapshots are restored; successful Core MCP sync is followed by fresh-provider enrollment, then non-MCP sync ([src/vaultspec_rag/commands/\_install.py:384-435, 517-688, 760-812, 1161-1250](../../../../src/vaultspec_rag/commands/_install.py#L384)).

For previews, `_mcp_preview_projection` copies the required effective state into a temporary workspace, seeds the projected source intent, and invokes Core against that target; report paths are mapped back to the real target. For normal MCP lifecycle runs, `_install_run` preflights topology, captures a replay in a temporary directory, materializes validated linked nodes if needed, runs install, and commits or restores the topology transaction according to MCP sync success ([src/vaultspec_rag/commands/\_install.py:438-503, 691-706, 903-995](../../../../src/vaultspec_rag/commands/_install.py#L438)). The shown direct state surfaces include `.vaultspec` builtins and manifests, [pyproject.toml](../../../../pyproject.toml), `.mcp.json`, `.codex/config.toml`, provider hook/config paths, and advisory lock paths ([src/vaultspec_rag/commands/\_install.py:245-310](../../../../src/vaultspec_rag/commands/_install.py#L245); [src/vaultspec_rag/commands/\_mcp_topology.py:341-424, 521-590](../../../../src/vaultspec_rag/commands/_mcp_topology.py#L341)).

`reconcile_mcp_extra(pyproject, mode, enabled, dry_run=False)` returns an action/location/conflict report and can apply, remove, move, or preview the MCP extra edit. [src/vaultspec_rag/commands/\_mode.py](../../../../src/vaultspec_rag/commands/_mode.py) exposes `resolve_rag_mode`, `infer_rag_upgrade_mode`, `mode_is_deployed`, `persist_rag_mode`, and `migrate_rag_mcp_entry`; [src/vaultspec_rag/commands/\_backend_choice.py](../../../../src/vaultspec_rag/commands/_backend_choice.py) exposes `save_backend_choice`; [src/vaultspec_rag/commands/\_hub_failure.py](../../../../src/vaultspec_rag/commands/_hub_failure.py) exposes `HubFailure`, `classify_hub_failure`, and `first_line` ([src/vaultspec_rag/commands/\_mcp_extra.py:35-52, 437-458](../../../../src/vaultspec_rag/commands/_mcp_extra.py#L35); [src/vaultspec_rag/commands/\_mode.py:60-284](../../../../src/vaultspec_rag/commands/_mode.py#L60); [src/vaultspec_rag/commands/\_backend_choice.py:19, 77-137](../../../../src/vaultspec_rag/commands/_backend_choice.py#L19); [src/vaultspec_rag/commands/\_hub_failure.py:23, 26-105](../../../../src/vaultspec_rag/commands/_hub_failure.py#L23)). No caller of the hub-classification helpers is visible in the assigned files.

## Boundaries and dependencies

The package presents itself as a thin orchestration layer around `vaultspec_core`. Within this slice, [src/vaultspec_rag/commands/\_install.py](../../../../src/vaultspec_rag/commands/_install.py) calls Core's `sync_provider`, `mcp_sync`, manifest helpers, workspace-mode helpers, and context/path facilities. [src/vaultspec_rag/commands/\_mode.py](../../../../src/vaultspec_rag/commands/_mode.py) delegates resolution, status, persistence, and MCP rendering to Core. [src/vaultspec_rag/commands/\_mcp_extra.py](../../../../src/vaultspec_rag/commands/_mcp_extra.py) relies on RAG Torch TOML helpers for load and shape-preserving writes. [src/vaultspec_rag/commands/\_mcp_topology.py](../../../../src/vaultspec_rag/commands/_mcp_topology.py) relies on RAG atomic-write, plain-parent, workspace-layout, builtins, and program-lookup helpers. Their implementations and compatibility behavior were not inspected.

The package docstring says shared repository state such as MCP configs, manifests, and provider directories is changed through Core ([src/vaultspec_rag/commands/__init__.py:19-21](../../../../src/vaultspec_rag/commands/__init__.py#L19)). The topology helper also directly snapshots and restores required paths and temporarily replaces validated link nodes around the Core operation ([src/vaultspec_rag/commands/\_mcp_topology.py:181-227, 258-325, 790-935](../../../../src/vaultspec_rag/commands/_mcp_topology.py#L181); [src/vaultspec_rag/commands/\_install.py:955-995](../../../../src/vaultspec_rag/commands/_install.py#L955)). This appears to be transaction plumbing around Core's reconciliation, but the precise scope intended by the broad package statement needs confirmation. Separately, [src/vaultspec_rag/commands/\_install.py](../../../../src/vaultspec_rag/commands/_install.py) explicitly invokes `reconcile_mcp_extra` on [pyproject.toml](../../../../pyproject.toml) and writes RAG's bundled `.vaultspec` sources, so the package-level wording should be read as covering the named shared provider state rather than all workspace files.

Inline docstrings and comments describe intended operator behavior, but there is no test evidence in this slice. In particular, the `__init__` statement that integration tests can drive the flow directly is a documentation claim, not proof that such tests exist or pass.
