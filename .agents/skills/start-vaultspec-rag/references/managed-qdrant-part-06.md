## Interfaces and data flow

- Qdrant format tests call write_store_format, read_store_format, store_format_path, and judge_store_format with a storage directory, spawning version, and optionally QdrantIdentity. Expected outcomes include CONFORMING, NONCONFORMING, or UNVERIFIABLE, with may_spawn, may_auto_quarantine, provenance, stored_version, and migrates_store assertions. The tested compatibility window allows same-version, patch, and one-minor forward transitions; tests expect downgrades, major changes, and skipped minors to be refused. Unknown provenance may open but disallows automatic quarantine. These are expectations in the tests, not verified implementation facts.
- The tested start path calls start_supervised_from_config. Tests expect an incompatible judgement to raise before spawning or moving collection directories. They also expect an operator binary of unknown release identity not to authorize automatic quarantine.
- Resilience tests pass child-output text and the storage directory to \_corrupt_collection_from_output, inspect \_list_on_disk_collections, and call \_quarantine_collection. The expected recovery path uses named on-disk collections and bounded retries; a successful quarantine moves collection data beneath a sibling quarantine directory. The CLI test invokes app with server qdrant quarantine arguments and observes JSON or exit status plus filesystem state.
- Health-surfacing tests construct QdrantRuntimeState and call \_service_health_status, then pass a serialized payload to degradation_findings. They expect QdrantSupervisor.state()/to_dict() to carry quarantined names and migrated_from, and expect matching degradation families/remediation commands. Actual production propagation is not inspected.
- Supervisor tests create real subprocesses and HTTP readiness stubs, then call wait_ready, start, restart, spawn, stop, is_alive, and recent_output_tail. Other tests exercise the output drain and log files. Tree-stop tests observe worker process IDs through psutil and pid_alive. These test setups identify subprocess, loopback HTTP, local filesystem, and process inspection boundaries.
- Quiesce tests connect ServiceRegistry and JobManager, persist job state through a state_path, bind dispatch runners, acquire compute tickets, and exercise quiesce_resources/resume_resources. Expected transitions include PAUSE_ABORTED and RESUME_RECOVERY_FAILED; the tests inspect snapshots, persisted state, job IDs/attempt numbers, admission status, and GPU-borrow safety. Projection tests query /health and authenticated /service-state and compare each quiesce value with registry.quiesce_snapshot().as_envelope().
- Readiness tests call compute_readiness, \_torch_readiness, and \_qdrant_readiness. They expect a ReadinessReport with exactly torch, models, and qdrant dimensions, plus serialized schema, support profile, package version, degraded reasons, and environment holders. Test fixtures change environment settings and isolate managed paths; assertions require no managed binary creation and repeatable output. The actual probes and resolution order remain uninspected.
- Warning tests call await_client_warnings with captured warnings and expected version-warning text; their contract is based on the warning list observed by pytest.
