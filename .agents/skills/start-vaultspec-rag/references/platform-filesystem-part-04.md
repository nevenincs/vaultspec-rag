## Capability summary

This slice contains tests for published-value parsing and presentation, safe Python child creation and process-site accounting, and managed Qdrant lifecycle/security.

- [src/vaultspec_rag/tests/test_published_value_narrowing.py](../../../../src/vaultspec_rag/tests/test_published_value_narrowing.py) pins shared scalar/container reader expectations, numeric formatter behavior, boolean timestamps, and distinctions between similar readers. It also parses production and integration Python files with AST to enforce a single home for published-value numeric narrowing, with tightly named exemptions and a bounded assert carve-out. Its coverage includes CLI/TUI presentation and job-route surfaces, plus an integration-test tree (lines 96-220, 223-416, 418-480, 482-723, 726-868).
- [src/vaultspec_rag/tests/test_python_child.py](../../../../src/vaultspec_rag/tests/test_python_child.py) exercises `inline_command`, `module_command`, and `script_command` using real child interpreters. It plants importable modules and checks sentinel files, reported origins, `sys.path`, safe-path mode, argument placement, and unguarded controls (lines 23, 30-93, 95-196).
- [src/vaultspec_rag/tests/test_python_child_shadowing.py](../../../../src/vaultspec_rag/tests/test_python_child_shadowing.py) applies the same planted-code method to the environment probe, resident-service launch command, project preprocess entry runner, and spawned process-pool workers. It also checks that a project hook can still import its sibling module, that nested pool scopes retain the safe-path environment setting until the last pool closes, and that a parent ignoring its environment is refused a pool (lines 30-38, 111-151, 153-211, 213-305, 308-442).
- [src/vaultspec_rag/tests/test_python_child_spawn_sites.py](../../../../src/vaultspec_rag/tests/test_python_child_spawn_sites.py) defines an inventory of package process-creation sites and AST checks for unlisted/changed sites, builder use for Python children, interpreter mode switches, hand-built commands, shell launches, bare native executable names, native-program lookup, and a service-specific working directory. It includes a source-text check for the monitor's Python launch flags (lines 1-33, 49-272, 290-519, 522-712).
- [src/vaultspec_rag/tests/test_qdrant_child_exit.py](../../../../src/vaultspec_rag/tests/test_qdrant_child_exit.py) checks whether a real child has exited and, on platforms where exit observation is peekable, that observing exit leaves its status available for a later wait (lines 30-32, 36-86).
- [src/vaultspec_rag/tests/test_qdrant_credential.py](../../../../src/vaultspec_rag/tests/test_qdrant_credential.py) specifies expectations for generated or configured child keys, publication of the child key, owner-only credential-file permissions, exact managed-endpoint matching before supplying a stored key, client authentication, and readiness checks that reject children accepting anonymous data-plane requests (lines 27-42, 139-236, 239-293, 295-361, 363-436).
- [src/vaultspec_rag/tests/test_qdrant_detection.py](../../../../src/vaultspec_rag/tests/test_qdrant_detection.py) checks endpoint-probe results, PID liveness, and classification of endpoint/identity combinations, including a missing process-start witness (lines 16-24, 34-85, 87-93, 95-155).
- [src/vaultspec_rag/tests/test_qdrant_download.py](../../../../src/vaultspec_rag/tests/test_qdrant_download.py) specifies HTTPS-only downloads, per-hop HTTPS and redirect-host checks, release-base and redirect-host configuration, shipped retry/deadline bounds, and provisioning failure on digest mismatch without installing the unaccepted payload (lines 19-35, 58-84, 86-205, 208-305).

## Interfaces and data flow

- Published-value tests feed hostile `object` values into imported readers and formatters and compare exact result types/values or rendered strings. The AST guard discovers files relative to the imported `_job_values` module, parses those files plus the integration-test tree, and reports numeric `isinstance` sites by function and source location (lines 62-78, 231-247, 472-480, 657-664).
- Child-command tests pass interpreter, module/script/program text, and arguments to command builders, then launch subprocesses. A planted module writes a `.ran` sentinel on import; child JSON output reports import origin, path, and flags. Other cases inspect helper results or pool-worker reports. These are test-specified flows; the builders' actual command construction was not inspected ([src/vaultspec_rag/tests/test_python_child.py](../../../../src/vaultspec_rag/tests/test_python_child.py) 34-93, 95-196; [src/vaultspec_rag/tests/test_python_child_shadowing.py](../../../../src/vaultspec_rag/tests/test_python_child_shadowing.py) 75-102, 318-388).
- The process-site scanner parses production `.py` files beneath the package path it derives from `__file__`, excluding paths with a `tests` component. It compares discovered process-creating calls and lookup/builder uses with inventories declared in the test. The monitor check separately reads `*.ts` files under a computed monitor-server directory when the test runs; that target was not read in this analysis ([src/vaultspec_rag/tests/test_python_child_spawn_sites.py](../../../../src/vaultspec_rag/tests/test_python_child_spawn_sites.py) 49-51, 290-300, 512-519, 522-712).
- Qdrant credential tests use temporary storage and a real loopback HTTP server, plus supervisor instances and child environments. They inspect the published credential file, request headers indirectly through client/probe outcomes, and supervisor state/logs. Download tests use loopback TLS stand-ins, request logs, in-memory output buffers, configuration overrides, and provisioning reports. Detection tests use a loopback server and constructed probe/identity values; child-exit tests launch a real interpreter process ([src/vaultspec_rag/tests/test_qdrant_credential.py](../../../../src/vaultspec_rag/tests/test_qdrant_credential.py) 70-136, 173-236, 295-436; [src/vaultspec_rag/tests/test_qdrant_detection.py](../../../../src/vaultspec_rag/tests/test_qdrant_detection.py) 34-60, 95-155; [src/vaultspec_rag/tests/test_qdrant_download.py](../../../../src/vaultspec_rag/tests/test_qdrant_download.py) 52-56, 86-205, 208-305; [src/vaultspec_rag/tests/test_qdrant_child_exit.py](../../../../src/vaultspec_rag/tests/test_qdrant_child_exit.py) 36-86).

## Boundaries and dependencies

- The inspected files are test code. No production implementation, API contract document, or test-run result was inspected. Explanatory module docstrings/comments are author claims about intended behavior and prior mutation demonstrations, not independent evidence that current implementation or tests satisfy them.
- Local test dependencies are visible through imports: published-value tests depend on job readers, CLI renderers, route helpers, and the package's source tree; child tests depend on command builders, service/process helpers, preprocess execution, environment probing, and pool guarding; Qdrant tests depend on runtime credential, resolve, download, provision, supervise, and child-tree helpers, plus local fixtures and test helpers. The behavior behind these imports is uninspected.
- The child-spawn inventory labels process starts as Python, pool, native, or project-authored and associates them with a builder, lookup, or safety rationale. Those rationales are test metadata, not verified implementation facts in this slice ([src/vaultspec_rag/tests/test_python_child_spawn_sites.py](../../../../src/vaultspec_rag/tests/test_python_child_spawn_sites.py) 53-172, 174-244).
- Inference from the selected coverage: safe subprocess import paths and managed-Qdrant lifecycle controls are cross-module concerns, while this slice primarily guards them through real child/server fixtures and structural scans. This is an inference from test organization and imports, not a repository-wide coverage claim.
