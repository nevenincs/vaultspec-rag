## Capability summary

**Implementation**

- [src/vaultspec_rag/indexer/\_run_ledger_commits.py](../../../../src/vaultspec_rag/indexer/_run_ledger_commits.py) implements publication receipt mutation journaling, generation storage-reset/replay markers, and durable commit-unit evidence. It prepares exact mutation units before a caller's external store operation, records applied and confirmed transitions, seals deltas, and records rollback direction/completion. It also records already storage-confirmed units idempotently, checks file completion, and offers bounded iterators for units and point IDs. Helpers validate stored identities and reject conflicting path, digest, segment, or point ownership evidence. (Entry points and helper groups: 582–855, 857–1237, 1239–1532, 1534–1773.)
- [src/vaultspec_rag/indexer/\_run_ledger_files.py](../../../../src/vaultspec_rag/indexer/_run_ledger_files.py) implements per-path manifest state and retained-point operations. It records indexed or policy-rejected state, requires complete matching storage-confirmed upserts before marking a path indexed, records deleted paths only with deletion-unit evidence, and can forget paths with no commit-unit evidence. It supports superseded-evidence lookup, retained-upsert retirement, drift reopening, bounded state/digest/candidate lookups, and a receipt-scoped effective state/point read that validates sparse receipt outcomes and confirmed mutations. (119–285, 287–529, 531–670, 672–803, 806–1093.)
- [src/vaultspec_rag/indexer/\_run_ledger_finalization.py](../../../../src/vaultspec_rag/indexer/_run_ledger_finalization.py) implements ordered finalization transitions, readiness guards, terminal generation outcomes, and retention compaction. The initial transition checks complete segment sequences, matching indexed state for upserts, deletion/tombstone consistency, and convergent file-state outcomes. Success requires durable publication; compaction only accepts a successful newest generation and preserves generations still referenced by publication or surviving file-state evidence. (59–257, 259–430.)

## Interfaces and data flow

- The principal values are CommitUnit, FileState, publication receipt/delta/candidate models, and finalization enums imported from sibling modules; their definitions and invariants were not inspected. The methods use the SQLite connection/transaction helpers and row converters imported from the ledger model/storage modules.
- Commit evidence flows through commit_units and commit_point_ids; file outcomes and reset/deletion intent flow through file_states and file_state_tombstones. Publication journaling uses publication_receipts, publication_mutation_units, publication_mutation_points, publication_receipt_deltas, and publication_receipt_points. The SQL shows exact fields and joins, while table creation/schema ownership is outside this slice.
- A caller can prepare a receipt mutation, then persist applied and confirmed states; sealing stores deltas and seals mutation ordering. Rollback first persists direction and can close only with exactly matching compensated units. The sequence is enforced by these methods, but caller ordering around external storage is not inspected (commits 857–1237).
- Storage-confirmed units are inserted transactionally and may be retried on contention; exact replay returns no new insertion, while conflicting identity/evidence raises a state error. Indexed file-state writes require complete unit ordinals, a final segment marker, and a matching source digest (commits 1239–1449; files 119–191).
- Effective publication reads run inside an explicit SQLite read transaction and roll it back on exit. They validate receipt-owned sparse local states/tombstones, combine local overrides with canonical publication evidence, and return retained path-qualified candidates (files 672–803).
