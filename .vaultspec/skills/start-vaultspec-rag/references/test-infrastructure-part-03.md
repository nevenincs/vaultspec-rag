## Capability summary

This slice consists of pytest support modules: deterministic fixtures and builders, state probes/assertions, process/service harnesses, and tier-selection gates. It also contains reusable canonical scenario data. Behaviors below are grounded in implementation; documentation claims are separated in Evidence.

- Process ownership and scan support: [src/vaultspec_rag/tests/\_process_probe_guard_helpers.py](../../../../src/vaultspec_rag/tests/_process_probe_guard_helpers.py) builds package-relative production source lists, parses Python ASTs, resolves relative imports, and provides predicates and offender scans for source guard tests. Its allowlist names production modules permitted raw process primitives with reasons (lines 14-36, 39-77, 98-140).
- Real route host: [src/vaultspec_rag/tests/\_production_service.py](../../../../src/vaultspec_rag/tests/_production_service.py) hosts the production route runtime on a loopback uvicorn listener, publishes a discovery record with its token, exposes registry/port/server/thread as `ProductionService`, and resumes/stops/withdraws the record during teardown (lines 49-67, 70-90, 93-142). Its docstring states daemon lifespan, model loading and GPU use are absent (lines 10-11, 93-95).
- Provision outcomes and hard-kill staging: [src/vaultspec_rag/tests/\_provision_fixtures.py](../../../../src/vaultspec_rag/tests/_provision_fixtures.py) finds a step result in a `ProvisionOutcome` (lines 15-22). [src/vaultspec_rag/tests/\_provisioning_child.py](../../../../src/vaultspec_rag/tests/_provisioning_child.py) runs production `provision()` under a pinned stand-in and blocks when a requested progress stage is reported, allowing a parent process to stop it (lines 25-50).
- Publication evidence: [src/vaultspec_rag/tests/\_publication_assertions.py](../../../../src/vaultspec_rag/tests/_publication_assertions.py) acquires a publication snapshot and reads all evidence into a path-to-content-identity map (lines 7-10, 18-27).
- Qdrant provisioning fixtures: [src/vaultspec_rag/tests/\_qdrant_provision_seam.py](../../../../src/vaultspec_rag/tests/_qdrant_provision_seam.py) creates operator binary/digest settings, writes a fixture managed install with a manifest, and monkeypatches the defining provision module with a call recorder that emits progress and a failed report (lines 41-73, 76-116). Its docs explain intended negative-call use and say it does not stage successful installs (lines 3-13).
- Warning capture and quiesce observations: [src/vaultspec_rag/tests/\_qdrant_warnings.py](../../../../src/vaultspec_rag/tests/_qdrant_warnings.py) polls a pytest warning recorder until expected SDK warnings arrive, ignores `ResourceWarning` in its comparison, then asserts exact counts (lines 14-18, 21-55). [src/vaultspec_rag/tests/\_quiesce_helpers.py](../../../../src/vaultspec_rag/tests/_quiesce_helpers.py) waits for registry states or a follower entering the transition-join wait, and builds running/held `QuiesceSnapshot` values (lines 24-67, 69-114).
- Run-ledger test support: [src/vaultspec_rag/tests/\_run_ledger_test_support.py](../../../../src/vaultspec_rag/tests/_run_ledger_test_support.py) constructs repeatable ledger signatures, units, proof compatibility, publication evidence and receipts; checks logical no-mutation and publication schema/index/FK properties; stages lineage and sealed receipts; and coordinates concurrent opens/interleavings with threads and a peer SQLite connection (lines 49-135, 137-269, 271-354, 356-473, 476-541). This is setup/assertion code using `RunLedger`, not evidence that ledger behavior passed.
- Workspace, environment and storage fixtures: [src/vaultspec_rag/tests/\_scaffold.py](../../../../src/vaultspec_rag/tests/_scaffold.py) creates `.vault` and `.vaultspec` workspace markers and round-trips environment-variable state (lines 20-49). [src/vaultspec_rag/tests/\_sqlite_state.py](../../../../src/vaultspec_rag/tests/_sqlite_state.py) snapshots logical SQLite state through a read-only URI, including journal mode, user version, schema and rows, then reports a bounded diff on mutation (lines 34-67). [src/vaultspec_rag/tests/\_store_fixtures.py](../../../../src/vaultspec_rag/tests/_store_fixtures.py) reads all IDs in either store collection under the point lock (lines 17-30).
- Shared readiness cases: [src/vaultspec_rag/tests/\_search_readiness_scenarios.py](../../../../src/vaultspec_rag/tests/_search_readiness_scenarios.py) defines immutable result/failure/scenario values, validates scenario shape and evidence bounds, makes canonical service envelopes, and catalogs current, updating, unavailable, not-built, unverifiable, rebuild-required, timeout, capacity-limited, backend-unavailable, authoritative-empty and mixed outcomes (lines 35-104, 106-156, 159-223, 236-440). Its docstring says later tests apply the service facts independently at public boundaries (lines 1-5); those adapters were outside this slice.
- Pytest process/root lifecycle: [src/vaultspec_rag/tests/\_session_job_anchor.py](../../../../src/vaultspec_rag/tests/_session_job_anchor.py) wraps production service spawn and, on Windows, attempts to assign the returned launcher process to a lazily-created kill-on-close job (lines 43-85, 88-101). [src/vaultspec_rag/tests/\_singleton_root_fixtures.py](../../../../src/vaultspec_rag/tests/_singleton_root_fixtures.py) names per-participant singleton/basetemp paths, decides when to redirect uv's project environment, reclaims owned paths, and sweeps sufficiently old orphan roots (lines 54-63, 66-100, 102-185).
- Archive fixtures: [src/vaultspec_rag/tests/\_stand_in_release.py](../../../../src/vaultspec_rag/tests/_stand_in_release.py) builds deterministic zip/tar.gz releases, makes install requests pinned to fixture digests, temporarily substitutes Qdrant pin tables with restoration in `finally`, serves stand-ins through loopback sources, and creates interrupted-install file states (lines 71-115, 118-169, 179-222). Its docs limit what stand-in tests prove: code against the temporary table, not that committed values match upstream (lines 18-21). [src/vaultspec_rag/tests/\_storage_archive.py](../../../../src/vaultspec_rag/tests/_storage_archive.py) writes a real directory containing snapshot bytes and a manifest with collection identity and publication-proof fixture data (lines 18-103).
- State, lock and watcher fixtures: [src/vaultspec_rag/tests/\_state_fixtures.py](../../../../src/vaultspec_rag/tests/_state_fixtures.py) clears integrity observations, limiters, pressure evaluator, registry and server metrics under associated locks (lines 13-47). [src/vaultspec_rag/tests/\_unnamed_lock_holder.py](../../../../src/vaultspec_rag/tests/_unnamed_lock_holder.py) starts a child interpreter that takes the configured machine lock, writes an unreadable owner record, announces its PID, and waits for release with timeout/kill cleanup (lines 28-48, 51-90). [src/vaultspec_rag/tests/\_watcher_fixtures.py](../../../../src/vaultspec_rag/tests/_watcher_fixtures.py) snapshots held and pending watcher paths under its lock (lines 13-16). [src/vaultspec_rag/tests/\_watcher_job_snapshot.py](../../../../src/vaultspec_rag/tests/_watcher_job_snapshot.py) constructs a fixed watcher-initiated incremental code-index job snapshot for a supplied root, state and timestamps (lines 28-77).
- Tier policy: [src/vaultspec_rag/tests/\_tier_gate.py](../../../../src/vaultspec_rag/tests/_tier_gate.py) centralizes fast/slow marker names and identifies untiered, contradictory and incompatible-device selections (lines 97-165). It provides pytest rejection functions for marker violations, distributed GPU work, subprocess/resident-device co-scheduling, and MPS mixed hardware selections (lines 211-221, 240-301, 303-417). Its docstring says root conftest invokes the gates (lines 11-14, 16-24); that caller was not inspected.
- uv install harness: [src/vaultspec_rag/tests/\_uv_env_harness.py](../../../../src/vaultspec_rag/tests/_uv_env_harness.py) prepares a temp-rooted uv sandbox, creates minimal wheels and a package index, serves wheels on loopback HTTP, holds environments or launchers with child processes, and reads installed distribution names and receipt text (lines 65-110, 113-143, 180-250, 253-271, 279-372, 375-403). Its docs explain why HTTP receipts and a console script matter to intended tests (lines 10-23); no uv command was executed.

Actual CLI/MCP/HTTP adapters are outside this slice.
