## Capability summary

- [dev/devserver.py](../../../../dev/devserver.py) implements a shared frontend development-server harness. It finds a package declaration at the repository root or one level down and validates the portless name, fixed port block, service declarations, commands, health checks, required services, and CI environment values. It discovers listening TCP ports and Windows excluded ranges; tracks processes and service ownership; probes health endpoints; and stores per-app records, lock, and logs outside the checkout. Its Harness sanitizes dead records and stray Vite listeners, evicts replaceable occupiers, starts or reattaches declared services, reports status, follows logs, and stops services. Its static check verifies standard frontend versions, the just recipe and workflow copies, .nvmrc presence when GitHub workflows exist, reserved ports, and literal port references. The CLI also supports CI validation and generated recipe/workflow output. The module docstring describes this as a canonical shared harness and promises an up convergence sequence; that description is a claim in the source, while the functions implement the mechanics.
- [dev/exit_codes.py](../../../../dev/exit_codes.py) declares a shared exit-code vocabulary for command outcomes: success, gating finding, init-specific failures, broken advisory execution, empty selection, and missing tool. FINDINGS_CODES identifies ordinary finding statuses; advisory_result maps success or declared finding statuses to OK and other statuses to ADVISORY_BROKEN. The module says it is standard-library-only and has no dependency on the rest of dev.
- [dev/gates.py](../../../../dev/gates.py) probes CUDA, MPS, and a provisioned Qdrant binary in one cached child-process probe. It exposes missing-capability descriptions and Gate objects for CUDA plus Qdrant, MPS, and the opt-in performance lane. Probe startup, nonzero exit, and parse failures close all gates; per-capability probe exceptions are retained for explanations. The module documentation explains why aggregates should report a closed lane as skipped. The importing callers are outside this slice.
- [dev/generate_cli_reference.py](../../../../dev/generate_cli_reference.py) introspects the live Typer command tree, formats global/command argument and option tables, builds command navigation, adds hand-authored notes for selected commands, and renders a Markdown reference. Its CLI writes [docs/cli.md](../../../../docs/cli.md) or, with --check, compares the generated text and returns a stale/current result. The command notes are documentation claims about runtime CLI behavior, not implementation of those behaviors.
- [dev/guards/\_ci_names.py](../../../../dev/guards/_ci_names.py) is the canonical set of workflow filenames, shared workflow display names, merge gate job/check names, full-run label, same-repository condition text, and measuring just groups. It states why string stability matters to branch protection and workflow guards.
- [dev/guards/\_workflows.py](../../../../dev/guards/_workflows.py) reads workflow YAML and the justfile into a static CI model. It resolves matrix runners and event occasions, represents jobs and their recipe steps, expands just recipes and toolchain target references into final argument vectors, and evaluates the supported GitHub expression subset with true/false/maybe results. Unknown conditions remain maybe/reachable so guards over-report rather than silently omit uncertain jobs. In this assigned slice, the canonical-name, fork-containment, and decoding guards call its workflow/job APIs; it also imports the uninspected dev.toolchain and dev.runner modules.
- [dev/guards/test_advisory_aggregate_holds_no_gate.py](../../../../dev/guards/test_advisory_aggregate_holds_no_gate.py) contains two pytest guard expectations: audit all must not reference a target classified as gating by reports/advisory declarations, and every remaining gating audit target must still be reachable through ci all. Its source defines assertions; no test result was collected here.
- [dev/guards/test_child_output_decoding.py](../../../../dev/guards/test_child_output_decoding.py) statically parses shipped Python modules under src/vaultspec_rag, excluding tests. Its assertions reject subprocess calls that decode text without an explicit encoding, and calls that read sys.stdin as text. It imports \_workflows for the repository root. The test file’s narrative describes the motivating failure; the assertions define the guard expectation.
- [dev/guards/test_ci_canonical_names.py](../../../../dev/guards/test_ci_canonical_names.py) ties workflow files and merge-gate contents to \_ci_names: every canonical workflow must exist, every .yml workflow must be named, the gate job name must match the required check, the gate steps must not repeat the check name, the workflow env must carry the full-run label, and the release step condition must include the expected event/action/label/repository clauses. These are source-level assertions, not evidence that they pass.
- [dev/guards/test_ci_deployed_copies_stand_alone.py](../../../../dev/guards/test_ci_deployed_copies_stand_alone.py) parses [dev/actionlint.py](../../../../dev/actionlint.py) and expects it to import something while importing no relative module or package owned by this repository. The target file itself was not assigned and was not read.
- [dev/guards/test_ci_fork_containment.py](../../../../dev/guards/test_ci_fork_containment.py) asserts that reachable pull-request jobs other than the merge gate carry a trusted-author condition, that ci:full paths require a user-applied label, that the gate refuses untrusted authors and fork commits before reading results, and that hardware workflow callers are unreachable from pull-request events. The tests express source expectations; this report does not establish their current pass status or the external effectiveness of repository settings.

## Interfaces and data flow

- devserver CLI: main(argv) accepts up, restart, stop, status, logs, check, ci, and render, with a service argument for applicable commands. It loads the package declaration, validates/checks it, then routes to Harness or run_ci. Failures are reported through stdout/stderr and the module’s exit constants. The declaration comes from [package.json](../../../../package.json); lock versions come from package-lock.json; optional Vite config, justfile, workflow, and .nvmrc paths participate in checks. Those data files were not inspected.
- devserver service lifecycle: declaration values become App and Service records. Process/port discovery and health probes feed Harness decisions. A per-app file lock serializes changes; JSON state records and log files live under the OS state directory. Start commands inherit the host environment plus the declared hook/CI overlay and DEVSERVER\_\* identifiers. Optional integrations include node/Vite, npm for CI dependency installation, portless aliases, tailscale DNS naming, and Windows netsh reserved-port output. The implementation invokes these tools when the relevant paths are reached; their installed state and external behavior were not checked.
- Exit contract: command classes are represented by constants and advisory_result(code, findings). Actual dispatch callers and their use of these codes are outside this slice, except for devserver’s private exit constants.
- Hardware gates: facts() invokes uv run --no-sync python -c with embedded probe code. That child checks torch.cuda, torch.backends.mps, and Qdrant provisioning and prints JSON. The parent memoizes booleans and diagnostic errors; missing() turns requested false facts into a reason; each Gate pairs a probe with a reason. The child imports vaultspec_rag.qdrant_runtime symbols not inspected here.
- CLI reference generator: the imported vaultspec_rag.cli.\_app.app is converted by Typer to a command tree. render() writes headings, summaries, notes, and parameter tables into a single Markdown document. main() either compares that result with [docs/cli.md](../../../../docs/cli.md) or writes it. Neither the command tree implementation nor the generated document was inspected.
- Workflow model and guards: \_workflows parses .github/workflows/\*.yml and \*.yaml and the root justfile. It produces Job objects, event/binding occasions, recipe groups, and expanded command vectors. The included test modules consume those representations alongside dev.toolchain declarations and raw workflow/YAML data. These workflow files, justfile, and dev.toolchain/dev.runner implementations were outside the assigned ranges.
- Guarded source surfaces: child-output tests scan src/vaultspec_rag Python files; stand-alone tests parse [dev/actionlint.py](../../../../dev/actionlint.py); CI guards read workflow YAML. These are inputs named by the assigned test code, not source reviewed in this slice.

## Boundaries and dependencies

- [dev/devserver.py](../../../../dev/devserver.py) depends on stdlib process, filesystem, JSON, HTTP, and CLI facilities plus psutil and filelock. Runtime integration points include package.json/package-lock.json declarations, Git tracking, node/Vite, npm, portless, tailscale, and on Windows netsh. Their contents or behavior were not independently examined.
- [dev/gates.py](../../../../dev/gates.py) embeds a child program that imports torch and vaultspec_rag.qdrant_runtime.\_constants.QDRANT_SERVER_VERSION and \_resolve.has_provisioned_binary. The project environment, root conftest behavior, and gate callers are uninspected.
- [dev/generate_cli_reference.py](../../../../dev/generate_cli_reference.py) imports vaultspec_rag.cli.\_app.app and Typer. The app command implementations and [docs/cli.md](../../../../docs/cli.md) are uninspected, so COMMAND_NOTES must be treated as authored documentation rather than verified runtime behavior.
- [dev/guards/\_workflows.py](../../../../dev/guards/_workflows.py) imports PyYAML, dev.toolchain, dev.runner, and dev.guards.\_ci_names. The latter is in scope; toolchain and runner internals are not. The parser reads repository workflow YAML and justfile at runtime; neither data source is in the assigned slice.
- The test modules also depend on pytest, source trees and workflow artifacts outside their assigned ranges. Their assertions and explanatory mutation narratives are evidence of intended guard coverage, not evidence that a suite ran or passed.
- The workflow tests describe branch-protection settings and GitHub Actions protections that live outside this repository. The included source can assert local workflow text and model reachability, but it cannot establish the external ruleset value or behavior.
