## Capability summary

This slice is integration-test infrastructure and test specifications for real service, CLI, storage, and search paths. It does not establish that any test passes.

- [src/vaultspec_rag/tests/integration/\_service_lifecycle_helpers.py](../../../../src/vaultspec_rag/tests/integration/_service_lifecycle_helpers.py) provides process and service lifecycle probes: readiness/model-log waits, publication identity checks, port/listener probes, bounded durable-job polling, process cleanup, shutdown assertions, discovery repair/absence checks, and harnesses for signalable services, identity-authenticated health children, POSIX Qdrant ownership, and status-lock contention. `_signalable_live_service` sets offline model variables, launches the real server, publishes status, polls health, yields its port/PID, then releases any storage barrier and delegates bounded cleanup. The module marks its helpers for integration use and exports a named helper set (lines 51-75, 92-708).
- [src/vaultspec_rag/tests/integration/\_service_search_diagnostics_support.py](../../../../src/vaultspec_rag/tests/integration/_service_search_diagnostics_support.py) centralizes real HTTP search probes and bounded failure evidence. It sends authenticated raw `/search` requests, correlates request IDs with structured `/logs/json` lines, polls exact job IDs through running/terminal states, submits clean vault rebuilds, obtains a service token from health, and gathers health/jobs/metrics plus last observations on failure. It redacts the token from health evidence and caps rendered evidence (lines 31-45, 65-428).
- [src/vaultspec_rag/tests/integration/\_shutdown_storage_control.py](../../../../src/vaultspec_rag/tests/integration/_shutdown_storage_control.py) installs a child-local patch around `CodeRunCheckpoint.record_confirmed_segments`: it calls the original storage operation first, then for an armed matching root and positive file-ending insertion publishes a stored marker and waits at a cancellable checkpoint for release. It restores the patch and publishes restoration evidence (lines 19-69).
- [src/vaultspec_rag/tests/integration/\_watcher_test_support.py](../../../../src/vaultspec_rag/tests/integration/_watcher_test_support.py) builds a modified-code `WatcherPathObservation` using current wall time and seeds an empty vault publication through a registry compute lease and full index (lines 17-33).
- Integration [conftest.py](../../../../conftest.py) supplies test-wide CUDA ceiling pinning, bounded startup/teardown accounting, offline model startup checks, machine-lock isolation, synthetic/indexed component fixtures, and reusable real-service fixtures. Startup prepares model snapshots online, starts the daemon with offline variables, waits for authoritative Qdrant publication before health readiness, verifies model-load log markers and absence of the hub endpoint, and uses bounded teardown. Plain service is shared at module scope; watcher-enabled service has a distinct module fixture; attached tests replay that daemon's captured environment. It also creates code-project sample sources and a per-test `CodebaseIndexer`/store fixture (lines 55-83, 109-272, 274-365, 367-850, 852-935).
- [src/vaultspec_rag/tests/integration/test_adversarial_multirepo.py](../../../../src/vaultspec_rag/tests/integration/test_adversarial_multirepo.py) specifies one GPU-backed saturation scenario: two synthetic roots and stores share a GPU lock/model, 24 concurrent vault searches interleave with a reindex of one root, and assertions require all searches to return hits without collected errors; stores close in `finally` (lines 41-110).
- [src/vaultspec_rag/tests/integration/test_adversarial_singleton.py](../../../../src/vaultspec_rag/tests/integration/test_adversarial_singleton.py) specifies machine-lock and Qdrant ownership policy cases: eight spawned workers race for a fresh or orphaned lock and must yield one distinct PID winner; injected foreign, dead-owner, unhealthy, and version-mismatched Qdrant states exercise refusal/reap decisions; a real foreign OS-lock holder must remain authoritative until released (lines 48-193). The module marks these tests `unit` (line 36), despite its directory.
- [src/vaultspec_rag/tests/integration/test_api_integration.py](../../../../src/vaultspec_rag/tests/integration/test_api_integration.py) checks search result shape/type filtering, incremental/full indexing summaries, store lookup/listing and related payloads, status metrics, a public-facade index/status/search/clean flow, and rejection of an unknown clean source before filesystem mutation (lines 23-221). Some tests named for the public API directly instantiate `VaultSearcher` or use `VaultStore`; the facade is directly exercised in `test_facade_end_to_end`.
- [src/vaultspec_rag/tests/integration/test_cli_integration.py](../../../../src/vaultspec_rag/tests/integration/test_cli_integration.py) runs `python -m vaultspec_rag` subprocesses over a shared synthetic CLI vault. It specifies status output, vault/code/all indexing summaries with a production service and GPU borrower option, and fallback-enabled vault/code searches (lines 24-267).
- [src/vaultspec_rag/tests/integration/test_cli_jobs_watch_console_interrupt.py](../../../../src/vaultspec_rag/tests/integration/test_cli_jobs_watch_console_interrupt.py) specifies a Windows real-console Ctrl+C during `server jobs --watch`: wait for the first refresh against a local jobs contract server, interrupt the child's console, require exit 0, and verify alternate-screen and cursor restoration bytes without traceback (lines 50-144).
- [src/vaultspec_rag/tests/integration/test_cli_port_token_fallback.py](../../../../src/vaultspec_rag/tests/integration/test_cli_port_token_fallback.py) checks explicit-port clients against protected machine discovery when status token is missing or stale, and requires unauthorized jobs access when discovery is absent; public health must not expose the service token (lines 24-55). It is marked `unit` (line 21).
- [src/vaultspec_rag/tests/integration/test_cli_startup_interrupt_console.py](../../../../src/vaultspec_rag/tests/integration/test_cli_startup_interrupt_console.py) specifies a Windows real-console interrupt while CLI startup is held inside the command import: require exit 130, the interruption notice on stderr, no traceback/KeyboardInterrupt, and no help output (lines 61-154).

## Interfaces and data flow

- The service lifecycle harness takes a temporary root, Qdrant source paths, and optional storage witness. It creates an ephemeral port, derives the child environment, starts `python -m vaultspec_rag.server --port ...`, writes service status, polls health, and yields `(port, pid)`; cleanup releases the witness and checks daemon/launcher/Qdrant exits ( [src/vaultspec_rag/tests/integration/\_service_lifecycle_helpers.py:300-390](../../../../src/vaultspec_rag/tests/integration/_service_lifecycle_helpers.py#L300)). Its storage-witness bootstrap imports `_shutdown_storage_control.install`, passing the resolved project root and control directory ([src/vaultspec_rag/tests/integration/\_service_lifecycle_helpers.py:329-350](../../../../src/vaultspec_rag/tests/integration/_service_lifecycle_helpers.py#L329); [src/vaultspec_rag/tests/integration/\_shutdown_storage_control.py:19-69](../../../../src/vaultspec_rag/tests/integration/_shutdown_storage_control.py#L19)).
- Durable-state helpers take a state path/job ID/predicate and decode through `load_persisted_state`; the storage confirmation helper combines full-pipeline ownership fields with a positive stored marker ([src/vaultspec_rag/tests/integration/\_service_lifecycle_helpers.py:264-289, 392-428](../../../../src/vaultspec_rag/tests/integration/_service_lifecycle_helpers.py#L264)). Shutdown expectations inspect job/resource release fields and ordered service log events (`:430-460`).
- Search diagnostics use `(port, token, payload)` for `/search`, return `(status, headers, JSON body)`, and use `SearchProbeContext(port, token, job_id, last_job)` to enrich failures. Their HTTP integration is loopback-only and uses the service transport helper for health/jobs/logs/reindex; metrics is fetched with bearer auth ([src/vaultspec_rag/tests/integration/\_service_search_diagnostics_support.py:47-63, 72-226, 259-428](../../../../src/vaultspec_rag/tests/integration/_service_search_diagnostics_support.py#L47)).
- [conftest.py](../../../../conftest.py) uses environment variables for isolated storage/status and offline/model configuration, temp paths for corpus/logs, service status/discovery, and process IDs for lifecycle tracking. The live-service fixture yields `(port, status_dir, applied_env)` internally and attaches tests with `(port, status_dir)` ([conftest.py:594-732, 735-850](../../../../conftest.py#L594)). The code fixture yields paths plus indexer/store/model/reranker (`:896-935`).
- The adversarial tests create independent temporary roots and local stores, or spawned processes for singleton races; the API and CLI files assert expected outputs/state transitions but do not verify production implementations outside their assertions ([src/vaultspec_rag/tests/integration/test_adversarial_multirepo.py:52-110](../../../../src/vaultspec_rag/tests/integration/test_adversarial_multirepo.py#L52); [src/vaultspec_rag/tests/integration/test_adversarial_singleton.py:48-193](../../../../src/vaultspec_rag/tests/integration/test_adversarial_singleton.py#L48); [src/vaultspec_rag/tests/integration/test_api_integration.py:151-221](../../../../src/vaultspec_rag/tests/integration/test_api_integration.py#L151); [src/vaultspec_rag/tests/integration/test_cli_integration.py:36-62, 122-267](../../../../src/vaultspec_rag/tests/integration/test_cli_integration.py#L36)).
