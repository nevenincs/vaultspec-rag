## Capability summary

- [src/vaultspec_rag/cli/\_search.py](../../../../src/vaultspec_rag/cli/_search.py) registers and implements the `search` command. It validates type, filters, preference and freshness options; supports code, vault, extracted-document, and combined requests; routes through the discovered data-plane service first; permits local execution only with `--allow-fallback` or configured local-only mode; and emits human or JSON results. The local path measures index counts/readiness state, calls the public search APIs, serializes results to the service result shape, renders empty/partial outcomes, applies a timeout, and closes the project registry in `finally` (implementation: 371-611, 614-712, 768-872, 889-1057, 1059-1487). Help text describes query markers and filter options (documentation claim: 1059-1095, 1098-1318).
- [src/vaultspec_rag/cli/\_search_readiness_render.py](../../../../src/vaultspec_rag/cli/_search_readiness_render.py) formats canonical readiness payload fields for human output. It bounds identifiers/remediation text, caps evidence and wait items, renders aggregate/source states and wait summaries, and deduplicates remediation; it does not derive a readiness verdict (implementation: 16-149).
- [src/vaultspec_rag/cli/\_service_doctor.py](../../../../src/vaultspec_rag/cli/_service_doctor.py) registers `server doctor`, which combines installed-dependency readiness, live-service state, and the `vaultspec-rag` workspace mode/version-floor axis. It emits one JSON snapshot or separate human-readable blocks for service, dependencies, receipt, compute repair, environment holders, and provisioning; its exit code reflects below-floor, dead-service, mismatch, and incompatible-release conditions (implementation: 62-163, 166-349, 352-603). The command help/docstrings describe deep cached-model verification and a read-only two-axis report (documentation claims: 62-93).
- [src/vaultspec_rag/cli/\_service_inventory.py](../../../../src/vaultspec_rag/cli/_service_inventory.py) registers `server inventory OPERATION PARAMETERS`. It bounds and validates a JSON string parameter object, calls the inventory reader, and emits a JSON success or classified error envelope (implementation: 15-46).
- [src/vaultspec_rag/cli/\_service_jobs_collection.py](../../../../src/vaultspec_rag/cli/_service_jobs_collection.py) defines `ServiceJobsOptions`, installs a custom Typer command schema for `server jobs`, resolves filters and service port, then fetches, optionally watches, filters client-side, and renders/serializes job collections (implementation: 61-250). The option help documents supported filters and JSON/watch guidance (documentation claim: 85-167).
- [src/vaultspec_rag/cli/\_service_jobs_control.py](../../../../src/vaultspec_rag/cli/_service_jobs_control.py) registers singular `server job` commands: `show`, `pause`, `resume`, `stop`, `retry`, and `delete`. It resolves the service port, resolves human prefixes to one exact ID, validates fetched job resources and revision before state changes, sends control requests, and renders JSON or human outcomes/errors (implementation: 26-319, 321-419). Command docstrings describe requested control semantics (documentation claims: 327-409).

## Interfaces and data flow

- `handle_search(ctx, query, ...)` takes a CLI target from `CLIState`, search type (default `combined`), limit, code/vault/document filters, scores, service port, fallback, timeout, JSON, and freshness options (interface: 1098-1318). The help says the default search covers ADRs and code while explicit combined search can include all three domains (documentation: 1101-1113); implementation sets `include_documents` based on whether `--type` was explicitly supplied (1330-1357).
- Search validates freshness and filters before resolving service availability. A reachable incompatible service is refused; otherwise it uses `try_http_search` with the query, filters, target, timeout, and freshness parameters. A failed/unavailable service leads to an error unless local search is mandated. Local execution rejects bounded freshness, checks GPU ownership, wraps the in-process route in a deadline, renders results, and closes the project registry (implementation: 1317-1479). `_try_in_process_search` issues `CodebaseSearchRequest`, `VaultSearchRequest`, `DocumentSearchRequest`, or `CombinedSearchRequest` to the corresponding public API (432-605). The exact lower-layer request and transport semantics are outside this slice.
- Service and local search output converge on CLI renderers. Service JSON adds query/type/via/advisory; human service output renders results or an empty explanation plus readiness, shortfall, and partial-domain notices (150-213, 220-309). Local JSON serializes result items and includes envelope/index-state data; human output renders equivalent results and warnings (768-872). The readiness formatter consumes `readiness.aggregate`, `readiness.sources`, evidence, waits, and remediation fields without making a new verdict (110-149).
- Doctor probes the interpreter selected for the daemon, asks `get_readiness` for dependency/model readiness, collects live-service and workspace-mode axes, then emits JSON or a composed human report (97-132). Its `ready`/`status` combines dependency readiness with service presence/liveness/starting state (242-264); exit severity is separately folded by `_doctor_exit_code` (135-163).
- Inventory accepts two positional strings: operation and JSON parameters. Parameters must encode to at most 8,192 UTF-8 bytes, decode to an object whose keys and values are strings, and use only `root`/`limit` plus `status`/`fresh` for `storage/survey`; then `read_inventory` supplies the response (15-46). The actual inventory sources and operation schemas are uninspected.
- Jobs collection parses limit/state/index/started-by/query/failed/job-id/since/port/json/watch/interval into `ServiceJobsOptions`; it resolves service port and filters, creates `JobsQuery`, and either passes a fetch callback to `watch_jobs` or fetches once, applies client state filtering, and renders/serializes (61-250). Control commands use HTTP admin/get/set/retry/delete transport helpers. Human controls first query by reference and require a unique match; JSON controls pass the supplied identifier directly to exact-job retrieval. State mutation includes the fetched positive revision and graceful/force mode (111-227, 295-319, 379-419).

## Boundaries and dependencies

- Search is the CLI adapter: it imports the app/state, public API request types, operator commands, service discovery/transport, GPU refusal helpers, and renderers (14-61). It directly calls public `vaultspec_rag.search_*` functions only on the local route (431-440, 521-593). The imported API/search, store, config, service client, server availability, and GPU helpers were not inspected; their internal guarantees are unknown here.
- Search readiness presentation is delegated to the assigned [src/vaultspec_rag/cli/\_search_readiness_render.py](../../../../src/vaultspec_rag/cli/_search_readiness_render.py); search output and index state originate from CLI payloads or `_try_in_process_search`'s count/snapshot path (220-226, 451-513).
- Doctor composes service-domain lifecycle, discovery, environment/provisioning, readiness, and workspace collectors, with CLI-specific rendering (28-56, 94-132, 181-184, 317-349). Those lower-layer modules were not inspected. There is a source-level tension: top-level/command docs say doctor mutates nothing (14-17, 85-93), while `_live_service_axis` says its reused `_evaluate_service_signals` helper removes a confirmed-dead stale discovery file (176-179). Whether that side effect actually occurs depends on the uninspected `_status_render._evaluate_service_signals` implementation.
- Inventory delegates persisted projection reading to `monitor_inventory.read_inventory` and does not itself operate a service (10-20, 38-46). The delegated reader's storage or mutation behavior is uninspected.
- Jobs collection delegates filter parsing, querying, not-running/invalid-option exits, watch behavior, client-side filtering, and presentation to `_service_jobs_query`, `_service_jobs_watch`, and `_service_jobs_presentation` (20-35, 203-250). Job controls delegate HTTP protocol behavior to `serviceclient._transport` and display details to `_service_jobs_presentation` (14-24, 117-227, 311-318, 321-419). No claims about endpoint implementation or service-side state transitions are made.
