## Capability summary

**Implementation.**

- [src/vaultspec_rag/job_manager/\_control.py](../../../../src/vaultspec_rag/job_manager/_control.py) defines `JobManagerControl`, extending `JobManagerQuiesceControl`. It validates and applies pause, resume, and cancel intent; handles revision conflicts, terminal/missing targets and unsupported force mode; persists state before sending cooperative signals; acknowledges attempt unwind; commits attempt outcomes; admits linked retries; resolves successful retry ancestry; deletes retained terminal history; and logs rejections. Main entry points include `set_desired_state`, `set_desired_state_async`, `acknowledge_control`, `finish_attempt`, `fail_unstarted`, `retry`, and `delete` (lines 121-173, 254-409, 481-549, 665-915, 985-1022).
- [src/vaultspec_rag/job_manager/\_control_quiesce.py](../../../../src/vaultspec_rag/job_manager/_control_quiesce.py) defines `JobManagerQuiesceControl` over `JobManagerState`. It defers queued work during quiesce, requests cooperative quiesce from running attempts, prepares held jobs for recovery, and schedules prepared work through per-job claims keyed by attempt, binding nonce, and generation (lines 54-152, 154-243, 245-336).
- [src/vaultspec_rag/job_manager/\_execution.py](../../../../src/vaultspec_rag/job_manager/_execution.py) defines `JobManagerExecution` over `JobManagerState`. It binds runners, admits and dispatches attempts on an event loop (including handoff from loopless threads), waits for attempts and shutdown, runs synchronous work in AnyIO worker threads behind encode/index limiters, publishes resource ownership, commits exits, and invokes start/finish observers (lines 90-145, 146-240, 247-435, 437-583, 584-989).
- [src/vaultspec_rag/job_manager/\_persistence.py](../../../../src/vaultspec_rag/job_manager/_persistence.py) defines `JobManagerPersistence` over `JobManagerState`. It restores snapshots and history, recovers eligible interrupted/live work, enforces restored history limits and reports capacity overflow, preserves invalid or newer-version files under sibling names, writes full generations, batches progress-only writes, rolls back unpublished failed transitions, and orders timestamps within each job (lines 68-445, 446-668, 670-801).

**Inline documentation claims.** The quiesce module describes claims as protection against duplicate resume dispatch (lines 1-7); execution comments describe durable-before-execution ordering and resource release before ownership is cleared (lines 377-384, 646-660); persistence comments describe synchronous lifecycle durability and a 0.2-second progress flush budget (lines 41-58, 556-651). These are source comments/docstrings, not independently checked contracts. The restore docstring says quarantining history leaves index data unaffected (lines 312-355); the storage implementation behind that statement was not inspected.

**Test expectations.** No test files were read, so no test expectations or passing-test claims are made.

**Inference.** The four files divide control, quiesce, execution, and persistence responsibilities, and call one another through methods on their manager-like owner. The actual composed `JobManager` class and public entry-point callers were not inspected.

## Interfaces and data flow

- Control requests take a job ID and desired state, with optional expected revision and mode, and return `JobOutcome`. The synchronous path resolves the target under the manager lock, mutates a snapshot, persists, then applies a pause/cancel/resume signal; it may schedule dispatch and notify a controller target after releasing the lock. The async wrapper runs the synchronous persistence path in a worker thread and can call `dispatch_async` for a bound queued job (control lines 289-409; persistence-before-signal lines 254-287).
- Control acknowledgement and completion are tied to both attempt number and exact asyncio task, so stale callbacks are ignored. Acknowledgement requires the worker and held resources to be released before changing state; a resumed pause can queue a reconciliation attempt, while pause/cancel acknowledgement updates or archives the job (control lines 481-663). `finish_attempt` accepts `AttemptTerminal` and preserves an already archived first terminal outcome (control lines 110-119, 665-742).
- Retry accepts a terminal job ID and optional initiator. It requires retryable state, capacity, and no equivalent active work; it creates a queued snapshot with a new ID and parent link. A successful linked attempt marks retryable terminal ancestors superseded. Delete accepts only a retained terminal job (control lines 807-983, 985-1022).
- Dispatch binds a runner and optional observers, validates execution authority/state, creates an asyncio task, and persists attempt start through `start_attempt`. A loopless caller hands admission to the adopted service loop and waits up to 30 seconds for that handoff (execution lines 109-145, 146-240, 247-375). `dispatch_async` gates the created task until `start_attempt` completes in a worker thread (lines 377-435).
- An attempt builds `JobAttemptContext`, selects an encode or index limiter from the job spec, runs the bound synchronous runner in a worker thread, and publishes worker/capacity/GPU-wait resource updates. Its exit carries result, control signal, error, duration, and whether release was persisted. The completion callback acknowledges control or commits success/failure/interruption, retries a failed persistence flush, notifies observers, and dispatches a requeued resume (execution lines 584-745, 747-989).
- Shutdown closes dispatch, clears pending quiesce claims, requests shutdown from live attempts, joins the requested tasks within a timeout, flushes persistence, and reports surviving resource owners (execution lines 499-557). `undispatched` returns queued snapshots only when lifecycle, startup restore, and quiesce admission conditions permit (lines 559-582).
- Quiesce preparation requires the controller to be in the expected state. It returns a typed result for no work, prepared work, or persistence failure; dispatch occurs only for a durable prepared result after controller state is RUNNING. Claims are consumed against the exact current attempt and binding before dispatch (quiesce lines 154-243, 245-336).
- Restore reads `_state_path` through `job_persistence`; no configured path or missing state returns a successful no-state outcome. Invalid content is renamed aside as invalid; a newer-version file is renamed aside with a distinct suffix; an OS read failure returns an error. Valid snapshots are restored all-or-nothing into an empty manager and then persisted (persistence lines 197-233, 272-444). Full state writes serialize active and terminal snapshots; progress-only writes serialize a generation under a single-flight write lock and are eligible after the configured budget (lines 547-651).

## Boundaries and dependencies

- Internal relationships visible in this slice: `JobManagerControl` extends `JobManagerQuiesceControl`, and that class extends `JobManagerState` (control lines 33-43, 121; quiesce lines 30-34, 54). `JobManagerExecution` and `JobManagerPersistence` also extend `JobManagerState` (execution lines 54-62, 90; persistence lines 31-37, 68). Quiesce calls the resumed-attempt queue helper and execution dispatch; control calls persistence, dispatch scheduling, and state helpers. Persistence also supplies `SnapshotTransition` used by the control owners.
- The composition and method resolution of these owner classes are not established by this slice. Execution itself comments that it is mixed into `JobManager`, but points to uninspected `job_manager/manager.py` (execution lines 597-603).
- Imported contracts are uninspected: `job_models`, `job_persistence`, `job_control`, `service_quiesce`, `concurrency`, `config`, `_job_errors`, `logging_config`, `indexer._run_ledger_models`, and `.models` / `.state`. In particular, this report does not establish persistence format or atomicity, controller lifecycle semantics, runner behavior, limiter sizing, or the definitions of the state helpers used here.
- No public API, HTTP/CLI caller, test, or user documentation was read. Method names and inline docs alone do not establish external call frequency or caller guarantees.
