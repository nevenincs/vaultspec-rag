## Capability summary

- [src/vaultspec_rag/tests/test_index_run_ledger_publication_reads.py](../../../../src/vaultspec_rag/tests/test_index_run_ledger_publication_reads.py) exercises canonical projection stability during generation start; bounded proof/evidence/point reads; effective receipt reads folding canonical evidence, sparse file states, tombstones, and confirmed mutations; rejection of oversized, wrong-generation, or ambiguous state; and atomic replacement between sparse state and deletion tombstones. Its callers include `RunLedger` publication read and receipt methods and test-support lineage builders.
- [src/vaultspec_rag/tests/test_index_run_ledger_publication_receipts.py](../../../../src/vaultspec_rag/tests/test_index_run_ledger_publication_receipts.py) exercises receipt value invariants and lifecycle: reservation/read-token fencing, monotonic idempotent mutation preparation/application/confirmation, exact mutation-to-delta sealing and point ownership, rollback with exact confirmed compensation, and commit after stale reconciliation. It calls `RunLedger` APIs and inspects one commit method's source for forbidden allocation queries.
- [src/vaultspec_rag/tests/test_index_run_ledger_recovery.py](../../../../src/vaultspec_rag/tests/test_index_run_ledger_recovery.py) exercises typed indexed-path collisions, compatibility/corruption refusal, recovery of a drifted indexed path by superseding only matching stale upserts while preserving deletion evidence and sibling state, and refusal to reopen after finalization.
- [src/vaultspec_rag/tests/test_index_run_ledger_schema.py](../../../../src/vaultspec_rag/tests/test_index_run_ledger_schema.py) pins publication schema version 9 and named schema fields; checks normalized tables, indexes, foreign keys and constraints; and exercises non-mutating rebuild refusal, atomic/retryable creation, concurrent openers, consistent preflight snapshots, and refusal of unexpected or mismatched schema objects.
- [src/vaultspec_rag/tests/test_indexer_unit.py](../../../../src/vaultspec_rag/tests/test_indexer_unit.py) covers document title/feature preparation, `IndexResult`, binary probing and a 10 MiB file limit, AST/splitter chunking and metadata, UTF-8 line/name/text handling, scan exclusions and ignore-pattern composition, canonical breadth refusal without publication proof, and shared bookkeeping-root resolution for code/document indexers. Several named test classes are empty placeholders in this range (`TestIncrementalIndexMetadata`, `TestIncrementalIndexUnhashedFiles`, `TestHashingPermissionError`, `TestCodebaseMetaRoundTrip`).

## Interfaces and data flow

- The ledger tests construct `RunLedger(path)` and call generation, proof, receipt, mutation, file-state, and finalization methods. Inputs include compatibility keys, generation IDs, bounded path/candidate sequences, `CommitUnit`s, `ProofEvidence`, and `PathDelta`s; assertions inspect typed results, errors, and idempotent replay (publication reads 51-497; receipts 50-610; recovery 63-287).
- SQLite is the tested durable boundary. Assertions/read fixtures name `publication_proofs`, `publication_evidence`, `publication_points`, `publication_receipts`, `publication_mutation_units`, `publication_mutation_points`, `publication_receipt_deltas`, `publication_receipt_points`, `file_states`, and `file_state_tombstones` (schema 40-220; reads 75-126, 269-333, 403-497). Receipt preparation and state changes are represented in the tests as mutation journal transitions, then sealed deltas and proof commits (receipts 249-378, 487-610).
- Indexer tests call `prepare_document`, `ASTChunker`, `TextSplitter`, `CodebaseIndexer.scan_files()`/`_scan_codebase()`, `workspace_volume_path`, and `acquire_code_breadth_snapshot`. Inputs are temporary roots/files, source text, and ignore files; asserted outputs are document/chunk metadata, scanned paths, ledger errors, and resolved paths (indexer unit 137-169, 210-271, 334-428, 472-533, 663-819, 821-957).
- No external vector-store write/read integration is exercised directly in the inspected ranges. The ledger tests use SQLite and represent storage changes through `CommitUnit` APIs; implementation-side integration behavior is unknown.
