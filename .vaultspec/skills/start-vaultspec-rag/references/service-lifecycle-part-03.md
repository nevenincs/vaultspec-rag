## Capability summary

- [src/vaultspec_rag/cli/\_service_start.py](../../../../src/vaultspec_rag/cli/_service_start.py) owns the server start CLI flow. It registers the options, detects and attaches to an existing owned service, checks the daemon environment and machine/port/GPU preconditions, ensures runtime dependencies before spawn, forwards launch settings, records discovery state, polls readiness, and renders success/failure outcomes. It distinguishes a serving degraded service from one that is not yet serving, and reports timeout/death/interruption outcomes.
- [src/vaultspec_rag/cli/\_service_status.py](../../../../src/vaultspec_rag/cli/_service_status.py) owns CLI-side status writes and related log helpers. It provides the configured log path, phase extraction, status initialization, merging daemon token/metadata, and appending a CLI shutdown attribution line. Read-only discovery functions are imported from serviceclient.\_discovery and re-exported for compatibility; the write helpers remain here.
- [src/vaultspec_rag/cli/\_service_stop.py](../../../../src/vaultspec_rag/cli/_service_stop.py) owns server stop: stopping a service by status record or explicit port, reclaiming a machine-lock holder without a discoverable status file, and optionally reaping surplus same-port daemon processes. It confirms target identity and termination before claiming success; unconfirmed live processes and incomplete reaps are failures. Stop success also attempts to stop a recorded monitor process.

## Interfaces and data flow

- Start CLI inputs are --port (default 8766, EnvVar.PORT), --updates/--no-updates, --update-delay-ms, --repeat-update-delay-s, --local-only, --qdrant/--no-qdrant, --qdrant-auto-provision/--no-qdrant-auto-provision, --no-preprocess, and --json (start options in \_ServiceStartCommand.__init__, lines 215-331). The custom command's invoke creates \_ServiceStartOptions and calls \_run_service_start (315-331). The command is registered as server start at 943-959.
- Start order is: progress announcement; attach to an existing serving or warming daemon; resolve and judge the daemon interpreter; check port, machine lock, and GPU owner; decide backend and ensure dependencies; resolve target root; create log directory; spawn; write initial service status; poll HTTP health until serving or failure (962-1065). Dependency provisioning occurs before spawn and a declined/failed provision is rendered as a start failure (343-436). Readiness timeout is derived from the Qdrant supervisor's readiness ceiling plus a 300-second overhead allowance (145-177).
- Start readiness uses structured health fields: models must be loaded, and server-mode Qdrant must be alive (1117-1142). Success records health-reported token and process metadata, startup duration, typesafe state, and degraded reasons where present (1234-1282). It writes human output or a shared lifecycle envelope through imported helpers (551-613). Failure paths include incompatible running release, missing GPU capability, dependency failure, occupied port/machine/GPU, spawn denial, daemon exit, interrupt, and timeout (616-684, 721-913, 914-941, 1204-1231, 1285-1380).
- [src/vaultspec_rag/cli/\_service_status.py](../../../../src/vaultspec_rag/cli/_service_status.py) builds initial discovery fields from schema/version, PID, port, timestamp, and local package version, then calls the imported merge writer (102-127). Token and non-null daemon metadata updates merge into the existing file (129-173). \_log_file resolves the configured log under the managed status directory (52-65); the shutdown helper appends a UTC cli.lifecycle line (67-100).
- Stop inputs are optional --port, --json, and --orphans (916-957). --orphans resolves a singleton port and runs the scoped reap; explicit --port stops the service identified on that port; otherwise stop uses the status record or tries machine-lock reclaim when no record exists (988-1095). For an answering service, health supplies serving PID and token (384-415); for a not-yet-serving target it uses matching lock/status evidence (506-553). Identity checks bracket the launch check with process start-time checks (555-573).
- Termination is bounded by a 20-second POSIX drain / platform-specific Windows drain and a 45-second termination budget, followed by exit confirmation. A survivor keeps discovery state and produces a failure; confirmed death triggers machine-pointer cleanup and a CLI shutdown log (69-84, 240-299, 343-382). Orphan reap is limited to daemon launch witnesses for the selected port and protects the process, machine-lock holder, discovery PID, serving PID, and matched shim relatives; an unidentifiable listener or failed process scan prevents a success claim (650-746, 760-913).

## Boundaries and dependencies

- The start and stop command functions are registered on the shared server_root_app; start delegates parsed options through its custom Typer command, while stop handles parsed arguments directly (start 215-331, 943-963; stop 916-1000).
- Both start and stop use serviceclient.\_discovery for discovery reads/removal and serviceclient.\_transport for health. The storage/ownership semantics of those imported functions were not inspected. [src/vaultspec_rag/cli/\_service_status.py](../../../../src/vaultspec_rag/cli/_service_status.py) imports the discovery schema and merge helpers; its atomic-write and ownership details are delegated and uninspected.
- Lifecycle JSON/human rendering is delegated to cli.\_service_lifecycle; start also delegates progress, rendering, process spawning, and health probing to other CLI modules. Stop delegates process identity/termination to cli.\_process and \_process_probe, machine ownership to \_machine_lock, and monitor cleanup to monitor_process. Their internals were not inspected.
- Start's backend/provision decisions, interpreter capability judgment, Qdrant timeout policy, preprocessing state, and GPU ownership are delegated to commands.\_provision, operator_state.\_service_environment, qdrant_runtime.\_supervise, indexer.\_preprocess_config, and \_gpu_owner, respectively; those implementations are uninspected. No behavior behind these imports is asserted here.
