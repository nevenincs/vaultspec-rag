# `service-quiesce` research: `Cooperative contention-aware GPU quiesce for the resident service`

The resident RAG daemon, the self-hosted GPU CI runner, and the local test suite share one physical RTX 4080 SUPER (16 GiB) and contend for it indefinitely, causing OOM and CI wedges. The goal is an elegant global pause the daemon can hold with **zero CPU** (no idle spin, no busy-poll) that even deeply in-flight work threads honor promptly, so an ephemeral external GPU consumer (CI, tests) can borrow the whole device and the daemon resumes afterward. This research frames the primitive, the cross-process signal, the yield policy, and the crash-safety envelope; the evidence favors a `threading.Event`-gated cooperative checkpoint, a lease-bound quiesce signal beside the existing machine lock, and a service-yields policy - but the ADR decides.

The dominant finding: the project already owns every needed part. `RunControl` (`src/vaultspec_rag/job_control.py`) is a cooperative-cancellation token threaded through every indexer at safe checkpoints; `_machine_lock.py` is a crash-safe, cross-platform, lease-based machine-scoped coordination surface with an atomic discovery pointer. Quiesce is a small additive layer over both, not new infrastructure. The honest bound on "promptly" is set by the same physics that already bound `RunControl` cancellation: sub-second, at the next checkpoint / slice boundary, never mid-kernel.

## Findings

### The two pause semantics are different and must coexist, not merge

Today's `RunControl` pause is **unwinding**: `checkpoint()` raises `PauseRequested` (`src/vaultspec_rag/job_control.py:163-167`, `:57-60`), a `BaseException` subclass (`:42-49`) that aborts the attempt so orchestration can reconcile desired state. Quiesce needs the opposite: **hold-and-resume** - block the thread in the kernel at a checkpoint, consume zero CPU, then continue the *same* attempt when released. These are complementary, not competing. Pause/cancel/shutdown answer "should this attempt keep existing?"; quiesce answers "may any GPU work proceed *right now*?" A clean model is a second, orthogonal gate the checkpoint consults: at each `checkpoint()` the worker first honors the quiesce gate (block while paused), then evaluates the existing unwind signal. The existing token's `protected()` span (`:169-199`) - which defers unwind across an indivisible mutation - is the natural precedent: quiesce must likewise never block inside a `protected()` region or while holding a store write, or it deadlocks the writer lock (the `gpu-consumer-single-thread` shutdown-hang failure class). Open question for the ADR: whether quiesce is a method on the existing `RunControl` protocol or a separate injected gate object the checkpoint calls first.

### Primitive: `threading.Event.wait()` is the zero-CPU professional choice

A `threading.Event` with the convention **set = running, clear = paused** gives exactly the required semantics: a worker calls `event.wait()` at a checkpoint and, if the event is clear, blocks in the OS futex/condition - zero CPU, zero wakeups - until another thread calls `event.set()`, which wakes all waiters immediately. This is CPython's documented behavior: `Event.wait()` blocks on an internal `Condition`, and `Condition.wait()` releases the GIL and parks the thread on the OS primitive (no polling). Contrast the rejected alternatives explicitly:

- **`while paused: time.sleep(0.1)`** - burns a wakeup every interval on every worker, adds up to the interval of latency to resume, and scales CPU with worker count. This is precisely the "idle while-loop / busy-poll" the requirement forbids.
- **`threading.Condition` with a predicate** - correct and also zero-CPU, but strictly more machinery than an `Event` for a single boolean gate; an `Event` *is* a Condition-plus-flag specialized for exactly this. Prefer `Event` unless the gate must carry state beyond the boolean (it does not).
- **A lock the worker tries to acquire** - a paused daemon would hold the lock across an unbounded external window, and lock ownership is thread-bound (the releaser must be the acquirer), which does not match a controller-sets/worker-waits topology. `Event` cleanly decouples signaller from waiter.

`Event` is also **torch-free pure-`threading`**, satisfying the hard constraint that the gate primitive carries no torch import (`index-workers-stay-cpu-only`, `torch-loads-through-centralized-gpu-gate`). `torch.cuda.empty_cache()` to actually release VRAM on quiesce is a *separate* daemon-side action behind `_gpu.load_torch()`, invoked once by the daemon after it observes the gate close - never inside the gate primitive or the worker checkpoint.

### The promptness bound is real and already precedented

"Respond promptly" cannot mean "instantly." A CUDA kernel already dispatched to the SMs cannot be preempted from Python mid-kernel; the consumer GPU has no MIG partitioning to force it (see MIG/MPS finding). So the honest guarantee is: a paused worker stops at the **next checkpoint or slice boundary** it reaches - sub-second in practice, because checkpoints already bracket every indexer batch/group/slice (`src/vaultspec_rag/indexer/_codebase_indexer.py` has ~20 `checkpoint()` sites, e.g. `:1409-1441` around batch groups). This is *identical* to the latency the existing `RunControl` cancellation already exhibits and the project already accepts. Search is the gap: `_searcher.py` acquires `gpu_lock` directly in `_gpu_section` (`src/vaultspec_rag/search/_searcher.py:164-178`) and does **not** consult `run_control`, so an in-flight search's encode+rerank cannot be quiesced mid-request - but a single search is short (one encode, one bounded rerank), so gating search at request *admission* (before it takes the GPU section) is sufficient and avoids mid-forward-pass interruption entirely. The ADR must decide whether quiesce blocks new searches at admission only, or also inserts a checkpoint between a search's encode and rerank forward passes.

### In-process vs cross-process: an Event alone pauses only the daemon

A `threading.Event` lives in one process; it makes the daemon's own threads pause but is invisible to an external CI/test process that wants the GPU. Bridging to cross-process needs a **machine-scoped signal the daemon's checkpoint observes** and an external actor sets. Three mechanisms, weighed:

- **(a) Quiesce-request file under the managed dir (favored).** The external actor writes a small JSON sentinel (e.g. `service.quiesce.json`) beside the existing machine lock; the daemon flips its in-process `Event` clear and blocks its workers. Reuses `_machine_lock.py`'s exact anchoring discipline - `machine_lock_path().parent` (`src/vaultspec_rag/_machine_lock.py:98-114`) is already the STATUS_DIR-independent machine-global directory both parties can find without sharing `VAULTSPEC_RAG_STATUS_DIR`, and the atomic temp-write-then-`os.replace` publisher (`:156-201`) is a ready-made crash-safe write pattern. Cross-platform: plain files work identically on Windows and POSIX. **Crash-safety is the weakness** and must be designed: a bare file persists if the CI process dies mid-quiesce, wedging the daemon forever - the file MUST carry an expiry/lease (see crash-safety finding).
- **(b) Named OS event.** A Windows named event (`CreateEvent`) maps naturally to the paused/running boolean and the daemon could wait on it with zero CPU cross-process. But it has **no clean POSIX equivalent** (POSIX named semaphores differ in semantics and cleanup), forcing two code paths, and a named event's lifetime/cleanup on abandonment is itself fiddly. Rejected as the primary mechanism for cross-platform cost; the in-process `Event` remains the intra-daemon primitive regardless.
- **(c) Extend the machine lock into a GPU lease both parties respect.** Conceptually clean - the machine lock is already the GPU/Qdrant singleton authority - but the current lock is a single exclusive OS advisory lock the *daemon holds for its whole lifetime* (`:265-302`). A CI process cannot acquire it without the daemon releasing it, and the daemon releasing its singleton lock would let a *second daemon* start. So a GPU lease must be a **distinct** lock/file from the identity lock, not an overload of it. This collapses into option (a) with lease semantics: a separate `service.gpu-lease` the CI process takes and the daemon's checkpoint observes. Favored framing: (a) *is* (c) done as a lease-bound file.

The `storage-maintenance-is-lifecycle-inert` rule is a nearby caution: quiesce must not become a channel by which one actor *terminates* another - it pauses, it never stops or kills. The daemon yields the GPU; it stays alive.

### Yield policy: the long-lived service yields to ephemeral work

The professional pattern for a persistent server vs. short bursty jobs is **priority by lifetime**: the ephemeral, time-bounded consumer (CI job, test run) preempts the long-lived pausable service. Sequence: external consumer signals intent -> daemon quiesces at next checkpoint -> daemon calls `torch.cuda.empty_cache()` to hand back reclaimable VRAM -> external work runs on the freed device -> external work clears the signal -> daemon resumes. This matches the CI ADR's world model: the GPU CI job (`2026-07-23-ci-self-hosted-gpu-runner-adr`) already runs under the *default machine service account*, deliberately isolated from the developer's per-user resident service, and already serializes `subprocess_gpu` tests into a separate pytest invocation because 16 GiB cannot co-schedule out-of-lock process VRAM (that ADR's Constraints). Quiesce is the missing cooperative handshake that makes that isolation active rather than best-effort. Alternatives:

- **Manual `server pause` / `server resume` toggle only.** Simplest; an operator or a CI pre-step runs `server pause`, the GPU job runs, a post-step runs `server resume`. Zero automatic detection. Worth shipping as the *control surface* regardless (it is the CLI verb pair over the same gate), but on its own it has no crash-safety net - a failed CI job never runs its resume step. Favored as the operator-facing veneer *plus* a lease expiry underneath.
- **NVIDIA MPS / MIG.** Ruled out. MIG (hardware partitioning) is enterprise-only - A100/H100/data-center class - and explicitly absent on consumer GeForce including the RTX 4080 (NVIDIA restricts MIG to data-center products; https://forums.developer.nvidia.com/t/why-nvidia-doesnt-want-individual-consumers-to-try-the-great-mig-technology/297371, https://en.wikipedia.org/wiki/GeForce_RTX_40_series). CUDA MPS (Multi-Process Service) is a **Linux-only** control daemon (no Windows/WDDM support; the workstation and GPU CI runner are Windows-native) and, critically, MPS provides spatial SM sharing but **no VRAM isolation** - co-resident clients still OOM each other, the exact failure this feature exists to prevent. Neither solves the 16 GiB contention.
- **Job schedulers (Slurm `gres=gpu`, Kubernetes device plugins, Ray).** The industrial answer to multi-tenant GPU arbitration, but each is a heavyweight cluster control plane (a scheduler daemon, resource specs, a submission model) grossly disproportionate to one developer workstation with one GPU and a companion CLI tool. Named for completeness; rejected as overkill.

### Crash-safety: the quiesce MUST auto-expire, or a dead CI process wedges the daemon forever

This is the load-bearing safety requirement. If quiesce is a plain persistent signal and the CI/test process dies (crash, Ctrl-C, killed job) between "quiesce" and "resume," the daemon stays paused indefinitely with zero self-recovery - turning a contention fix into a self-inflicted outage. Two crash-safety designs, both viable:

- **Lease with a wall-clock expiry (favored for the file mechanism).** The quiesce sentinel carries a deadline (`expires_at`) and/or a heartbeat the external actor renews; the daemon treats an expired lease as absent and resumes. A dead actor stops renewing; the lease lapses; the daemon un-wedges on its own. This mirrors the heartbeat-staleness contract the discovery pointer already uses (`read_machine_discovery`, `src/vaultspec_rag/_machine_lock.py:117-131`, "the caller applies the heartbeat staleness contract the payload carries"). It requires the daemon to re-check the deadline while parked - so the daemon's *observer* cannot itself be a pure infinite `Event.wait()`; it needs a bounded `Event.wait(timeout=...)` re-check OR an OS-level file/handle wait. Note the tension with the codebase's standing "no background sweeper/timer threads" preference (`2026-06-12-service-concurrency-adr` Constraints): the ADR must decide whether a bounded lease-expiry re-check is an acceptable exception (it is traffic-adjacent, not a free-running timer) or whether expiry is evaluated lazily only when a worker reaches a checkpoint.
- **OS-held lease via the advisory lock (strongest crash-safety, favored for the lock mechanism).** If the quiesce lease is a *second* OS advisory lock (`fcntl.flock` / `msvcrt.locking`, the exact pattern at `src/vaultspec_rag/_machine_lock.py:231-248`) that the **CI process holds** for the duration of its GPU work, then the OS releases it automatically when that process dies - the same crash-safety the machine lock already relies on ("a crashed daemon never strands the lock," `:11-17`). The daemon's checkpoint probes whether the GPU-lease is held (a non-blocking try-lock, like `machine_lock_live_holder`, `:353-387`): held -> quiesce; free -> run. No expiry clock needed; process death *is* the release. The cost: the daemon must probe the lock at checkpoints (cheap, side-effect-free acquire-then-release) rather than block purely on an in-process `Event`, so the in-process `Event` becomes a latched cache of the last probe rather than the sole source of truth. This is the most robust option and reuses the most existing, already-hardened machinery.

Either way the invariant for the ADR: **no external actor's death can leave the daemon paused.** A lease that expires or an OS lock that auto-releases both satisfy it; a bare persistent flag does not.

### Testability: a green GPU-free unit boundary exists; GPU-live is contended

The gate primitive is pure `threading`/OS code with **no torch and no GPU**, so the whole of it - Event set/clear/wait semantics, checkpoint-blocks-then-releases, lease expiry, OS lock auto-release on process death (via a spawned child that exits), the file publish/read round-trip - is unit-testable green on any host, GPU or not. This is the boundary to prioritize. Per `guard-tests-prove-they-can-fail`, the two core assertions are **guards** needing both-direction proof: (1) "a worker blocks when quiesced" must be shown to *fail* if the gate is stubbed open (worker proceeds), and (2) "a worker resumes when released" must be shown to *fail* if release is broken (worker stays blocked) - each verified red-then-green in one sequence, recorded in the execution record. The cross-process crash-safety guard ("dead actor un-wedges the daemon") is provable green without the GPU by killing a child holding the lease / letting a lease expire and asserting the observer resumes. Only the *end-to-end* "daemon actually frees VRAM and CI succeeds" assertion needs the live contended GPU, which requires a coordinated maintenance window (the resident service holds several GiB and any GPU-live test co-schedules against it - the exact 16 GiB OOM hazard). Flag: schedule that verification, do not block the unit boundary on it.

### Recommended positions (grounding for the ADR)

- **Primitive:** in-process `threading.Event` (set = running, clear = paused), consulted at every existing `checkpoint()`; zero-CPU, torch-free.
- **Cross-process mechanism:** a lease-bound quiesce signal in the machine-global managed dir beside `service.lock`. Two live candidates the ADR must choose between: a JSON file with an `expires_at` heartbeat lease, or a second OS advisory lock the external actor holds (strongest crash-safety, most reuse of `_machine_lock.py`). Named OS events and a job scheduler are rejected.
- **Yield policy:** service-yields-to-ephemeral (priority by lifetime); daemon quiesces at next checkpoint and `empty_cache()`s reclaimable VRAM; `server pause`/`server resume` is the operator veneer over the same gate but never the sole crash-safety mechanism.
- **Sequencing:** ship the in-process `Event` gate + checkpoint integration + `server pause`/`resume` first (fully unit-testable, immediately solves daemon-internal contention and manual CI coordination), then layer the lease-bound cross-process auto-quiesce on top. This staged path keeps a green GPU-free unit boundary at each step.

### Open questions the ADR must settle

- Quiesce as a new method on the `RunControl` protocol vs. a separate injected gate the checkpoint calls first.
- Search: gate at admission only, or also insert a checkpoint between encode and rerank.
- Lease shape: expiry-heartbeat JSON file vs. second OS advisory lock (crash-safety vs. observability trade-off).
- Daemon observer while quiesced: bounded `Event.wait(timeout)` re-check vs. lazy expiry at checkpoints, reconciled against the "no free-running timer threads" preference.
- Whether MPS is weighed at all, or dismissed outright on the Windows + no-VRAM-isolation grounds above.
- Interaction with the idle-eviction sweep and the hourly auto-prune tick: must a quiesced daemon still run non-GPU maintenance, or freeze wholesale.
