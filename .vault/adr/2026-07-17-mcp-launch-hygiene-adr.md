# `mcp-launch-hygiene` adr: `rag binds to core's static-launch contract: tool spec token and placement-aware extra` | (**status:** `accepted`)

## Problem Statement

Core made every rendered MCP launch a side-effect-free static execution
(core `2026-07-17-mcp-static-launch-adr`). Rag's side has three gaps
(issue 231): the tokenized builtin lacks the tool-mode extra spec, so
tool-mode renders produce an mcp-less environment that cannot import the
server; the installer's ensure-mcp-extra step ignores the declared
provisioning mode and leaks `vaultspec-rag[mcp]` into runtime
`[project.dependencies]` on dev-mode hosts; and the seed-refresh remediation
for pre-parity workspaces is untested and undocumented.

## Considerations

- Core's renderer consumes `_vaultspec_mode_tool_spec` precisely for
  packages whose MCP surface lives behind an extra; rag is the motivating
  case (mcp-optional-dependency ADR keeps `mcp` out of the base install).
- The installer resolves the mode before the extra step runs, so the fix is
  threading the resolved placement, not re-deriving it.
- `uv add --group <name>` updates an existing entry of that group in place;
  a bare `uv add` targets runtime dependencies. Detecting where the host
  already declares rag (runtime deps vs a dependency group) beats trusting
  the mode alone, because operators move packages between groups.
- `seed_builtins(force=force or upgrade)` already refreshes stale seeds by
  content comparison; the invariant needs a pinning test, not code.

## Considered options

- **Make `mcp` a core dependency again:** rejected - re-imports the pywin32
  install breakage the optional-extra ADR fixed.
- **Trust the declared mode only for extra placement (no pyproject
  inspection):** rejected - misplaces the extra when the operator moved rag
  to a custom group; inspecting the host's actual placement is one tomlkit
  read the installer already performs for torch.
- **Chosen:** add the tool-spec token to the builtin seed; make the extra
  step placement-aware (existing placement wins, declared mode is the
  fallback, tool mode never runs `uv add`); pin seed-refresh with a
  regression test and document the `install --upgrade` remediation.

## Constraints

- The builtin seed is the single source; the committed workspace mirror in
  `.vaultspec/mcps/` must be refreshed through the seeder, never hand-edited.
- The extra step stays non-fatal (warnings, never aborts install) and its
  classifier stays subprocess-free for tests.
- Rag never edits shared host files directly beyond what `uv add` performs
  (companion delegation model).

## Implementation

Seed gains `"_vaultspec_mode_tool_spec": "vaultspec-rag[mcp]"`; the
workspace mirror is regenerated by the seeder. `_run_uv_add_mcp_extra`
gains a placement argument resolved at the call site: detect rag's current
declaration in the host pyproject (runtime deps -> bare add; a dependency
group -> `uv add --group <that group>`); fall back to the declared mode
(dev -> `--group dev`, dependency -> bare); tool mode skips the step (the
tool spec covers it). Tests pin the placement matrix and the
stale-seed-refresh path; docs record the pre-parity remediation
(`vaultspec-rag install --upgrade`).

## Rationale

R1-R3 in the grounding research; the chosen shape keeps mcp optional,
respects the host's actual layout over declared intent, and turns the
already-correct upgrade behavior into a tested contract.

## Consequences

- Tool-mode MCP works out of the box; dev-mode installs stop polluting
  published dependency lists; pre-parity workspaces have a documented
  one-command remediation.
- The placement inspection adds a tomlkit read to install; negligible.
- Core's PR 224 and this change are independently landable; the tool spec
  token is inert for older cores (unknown keys are preserved).
