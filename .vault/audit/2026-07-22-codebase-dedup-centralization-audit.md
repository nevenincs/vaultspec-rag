# `codebase-dedup-centralization` audit: `duplication and centralization drift sweep`

## Scope

A semantic-search-led duplication sweep across every major subsystem of the package: indexer, store, search, the CLI, server, MCP and service-client adapter layers, watcher, jobs, install, content and run policy, GPU diagnostics, embeddings, registry and cache singletons, storage lifecycle, and provisioning. Roughly thirty targeted queries were run production-biased, each candidate confirmed by reading the epicentre rather than by match count alone.

The sweep deliberately excluded the generated provider mirrors under the agent, assistant, and harness rule directories. Those carry one copy of every rule per provider by design; counting them as duplication would bury the real findings.

The headline result is a negative one worth recording: the codebase holds a consistent thin-adapter-over-single-owner discipline, and it survived adversarial re-checking. Candidates that looked duplicative resolved as deliberate layering - engine versus orchestration in the watcher, command wiring versus command implementation in install, a front door delegating to a provisioning backend, and a three-layer content, resolved, and run policy pipeline. Three genuine findings survived.

## Findings

### code-kind-admission-guard | medium | The code-kind admission guard was hand-rolled at four call sites instead of having one owner

The worker module raised the same invariant independently at three code entry points and once more on the document side, with two divergent message strings for what is one rule. The duplication was not cosmetic: it was the direct cause of fourteen unit-test failures, because fixtures written for the pre-boundary unified worker tripped a guard whose enforcement had tightened in only some of its copies. This finding is already remediated under the code and document index boundary plan, where the four copies were collapsed into a single helper that renders the existing messages byte-identically, preserving the batch-versus-single diagnostic distinction while giving the invariant one owner.

### dual-health-clients | medium | Two independently maintained clients call the same health endpoint

The CLI process module carries a hand-rolled health probe built on a custom opener that explicitly refuses redirects, consumed at seven or more call sites across status rendering, service start, service stop, and integration helpers. The service-client transport module carries a second, separate implementation whose own module docstring claims that every call from both the CLI and the MCP funnels through it, and which reaches the same endpoint internally. The two disagree on error envelope shape and on redirect handling. The split may be deliberate - the CLI probe can run before a service status file exists, which the transport assumes - but that intent is recorded nowhere, and a docstring asserting singularity while a second client exists is drift that will mislead the next reader.

### lifecycle-outcome-envelope-helpers | medium | The structured start and stop outcome envelopes are duplicated once per verb

The service start and service stop command modules each define their own near-identical pair of success and failure envelope helpers, with matching signatures and matching purpose: rendering the structured outcome envelope that the broker-facing outcome rule mandates. The shared render module already owns the generic envelope primitives both pairs build upon, so the natural home is one generalized pair there rather than one bespoke pair per lifecycle verb. The risk is specific rather than aesthetic: the governing rule requires exactly one envelope on every exit path and requires an already-satisfied request to succeed, and two independent implementations of that contract can drift apart on a branch that only one of them covers.

### broker-outcome-rule-doc-drift | low | The governing rule document names a module that does not hold the helpers it describes

The broker-facing outcome rule cites the four envelope helpers as living in the service lifecycle module. They do not; they are split across the service start and service stop command modules, and the lifecycle module is a small orchestration unit. The rule remains correct in substance and the code still honours it, but a rule that points at the wrong location degrades as documentation and weakens the next reader's ability to verify compliance.

### bounded-query-param-clamp | low | The bounded integer query-parameter clamp is implemented twice

The storage survey route and the managed-log configuration each parse an optional string query parameter, substitute a default when absent, and clamp the result into a bounded window. Two instances, different callers, different bounds. Recorded for completeness rather than escalated: a shared bounded-integer primitive would remove the repetition, but neither copy is load-bearing for a documented invariant.

### cli-service-qdrant-second-readyz-probe | low | a second, independent `/readyz` HTTP prober duplicates the canonical qdrant endpoint probe instead of reusing it

`_readyz_probe` in `src/vaultspec_rag/cli/_service_qdrant.py:37-46` opens `http://127.0.0.1:{port}/readyz` directly via `urllib.request.urlopen` and returns `resp.status == 200`, feeding the `ready` field of `server qdrant status` (`_qdrant_status_payload`, `src/vaultspec_rag/cli/_service_qdrant.py:162`). This reimplements a strict subset of the canonical `probe_qdrant_endpoint` in `src/vaultspec_rag/qdrant_runtime/_resolve.py:92-134`, which already owns loopback `/readyz` probing (used by `_supervise.py::wait_ready` and `cli/_process.py`'s reap/reconciliation paths) and is more careful about the failure taxonomy: it distinguishes "nothing listening" (`URLError`/`OSError`/`ValueError`, i.e. connection refused) from "listening but answering non-200" (`HTTPError`, still `listening=True`), whereas the CLI's private prober collapses every failure mode into a single boolean and never surfaces `listening` separately. Functionally the two agree on the common-case 200-vs-not outcome today, but the CLI's status view now has a second, unowned copy of "what counts as ready" that can silently diverge from the runtime's own definition (e.g. if the ready criterion ever needs an extra check, such as version match) since nothing forces `_readyz_probe` to track `probe_qdrant_endpoint`. `server qdrant status` should call `probe_qdrant_endpoint(port).ready` instead of maintaining its own urllib call. Same shape as the already-recorded two-independent-`/health`-clients finding, but for `/readyz`.

### job-manager-retry-duplicates-create-job-construction | medium | `JobManager.retry` reimplements `JobManager.create`'s job-record construction and persist-then-rollback sequence instead of sharing one owner

`create` (`src/vaultspec_rag/job_manager.py:1141-1200`, roughly) and `retry` (`src/vaultspec_rag/job_manager.py:2150-2247`) each independently: allocate a fresh id, build a `JobSnapshot` with the same field set (`revision=1`, `spec`, `state`, `desired_state`, `capabilities=self._capabilities_for(...)`, `attempt=JobAttempt(...)`, `timestamps=JobTimestamps(created_at=now, state_changed_at=now)`, `progress=None`, `result=None`, `error_kind=None`, `initiator`, `runtime=self._process_runtime_snapshot()`, `resources=JobResourceSnapshot(started=None, finished=None)`), wrap it in `_ManagedJob(snapshot=..., runtime=_JobRuntimeOwner(task=None, control=None))`, insert into `self._active`, call `self._persist_locked()`, and on a persistence failure either `self._restore_state_locked(backup)` (unpublished) or return `self._persistence_error(...)` (published) - the exact same three-way branch, written twice with only cosmetic differences (retry's attempt carries `parent_job_id`, retry skips the idempotency-key bind that only `create` needs). This is precisely the shape called out by the storage/lifecycle discipline elsewhere in this codebase: a persist-then-notify sequence that should have one owner. Nothing forces the two copies to stay in sync - a future field added to `JobSnapshot` construction, or a change to the persistence-error branch (e.g. the `2026-07-21` disk-exhaustion hardening pattern used in `_store_writes.py`), can land in one call site and be missed in the other. Extracting a shared `_create_job_record_locked(spec, state, desired_state, attempt, initiator, *, resolved_id=None) -> (JobSnapshot, persist-or-error)` helper (or similar) that both `create` and `retry` call would remove the duplicate maintenance surface. Not filed as high: both current copies are correct and tested (`test_jobs_registry.py`, `test_jobs_unit.py`), so there is no live defect today - the risk is future drift, not a present-tense bug.

### watcher-duplicate-exponential-backoff-formula | low | two independent exponential-backoff implementations in the watcher subsystem share the same formula shape with no common owner

`WatcherRetryPolicy._retry_delay` (`src/vaultspec_rag/watcher_retry.py:627-631`) and `_schedule_replacement` (`src/vaultspec_rag/watcher.py:1895-1922`) both compute `base * 2**(streak-1)` capped at a max-seconds constant - the identical exponential-backoff shape, written independently. `_retry_delay` is the persisted, jittered circuit-breaker delay for job-attempt failures (state written to the per-source retry-state file, consumed on the next idle tick); `_schedule_replacement` is an in-memory, unjittered delay for watcher-slot orchestration-replacement failures (a distinct failure class - the watcher's own bookkeeping wedging, not a job attempt failing). The two serve genuinely different scopes (one persists and jitters, one doesn't need to), so this is a milder case than a true single-owner violation, but the core backoff arithmetic - `min(max_seconds, base * 2**exponent)` - is duplicated rather than shared via one small helper (e.g. a module-level `_capped_exponential(base, streak, max_seconds)`). If the backoff shape is ever revisited (e.g. capping the exponent, changing the base) one site can be updated and the other missed, since nothing ties them together. Low severity: no live defect, both are correct and independently tested (`test_watcher_retry.py`); filed for future-drift visibility per the pattern the team is tracking in `job_manager.py`.

### jobs-start-reindex-vault-codebase-duplicate-orchestration | medium | `start_reindex_vault` and `start_reindex_codebase` duplicate the admit-bind-dispatch-and-handle-each-failure sequence instead of sharing one owner

`start_reindex_vault` and `start_reindex_codebase` in `src/vaultspec_rag/jobs.py` (near the end of the file) are near-identical bodies: both call `_admit_index_job(...)`, early-return the existing `job_id` when not newly `created`, call `_bind_index_dispatch(manager, job_id, code_preflight=..., document_preflight=None)`, and on a bind error call `manager.fail_unstarted` + `record_finish(error=...)` + `raise RuntimeError`, then call `manager.dispatch(job_id)` and repeat the identical fail_unstarted/record_finish/raise handling a second time (with the same `dispatch_stopped` early-return carve-out) for the dispatch failure. The only real difference is that `start_reindex_codebase` calls `validate_code_job_admission(root)` first and threads `code_preflight` through instead of `None`. This is the same shape as the `JobManager.create`/`retry` duplication already filed this session (`job-manager-retry-duplicates-create-job-construction`) - a persist/bind-then-notify sequence duplicated across two call sites with no shared owner - and it is worth noting as corroborating evidence: `activate_index_job` (also in this file) is the newer, async, single-function version of this exact admit-bind-dispatch-and-fail-on-error sequence that already handles vault, code, *and* document domains uniformly via `code_preflight`/`document_preflight` parameters - `start_reindex_vault`/`start_reindex_codebase` look like the pre-`activate_index_job` synchronous predecessor that was never retired once the unified async path landed. A future `start_reindex_document` would either duplicate a third copy or (better) finally collapse all three onto `activate_index_job`. Not filed as high: both functions are correct and covered by existing tests (`test_jobs_registry.py`, `test_watcher_retry.py` call paths), so this is a maintenance-surface / future-drift concern rather than a live defect.

### embeddings-duplicate-oom-halving-ladder | low | the CUDA-OOM batch-halving retry loop is implemented independently for dense and sparse encoding

`EmbeddingModel._encode_documents_output` (`src/vaultspec_rag/embeddings.py:568-609`, the shared body behind both `encode_documents` and `encode_documents_on_device`) and `EmbeddingModel.encode_documents_sparse` (`src/vaultspec_rag/embeddings.py:670-770`) both implement the same recovery policy independently: `while True: try: <encode> except torch.cuda.OutOfMemoryError: torch.cuda.empty_cache(); if batch_size <= 1: raise; batch_size = max(1, batch_size // 2); logger.warning(...)`. The dense path already has one owner shared by its two callers (`_encode_documents_output`); the sparse path re-implements the identical halving/floor/empty_cache/log skeleton rather than reusing it, with the actual per-batch encode work (sub-batch loop, optional `gpu_lock`, tensor lifetime management) interleaved inside the same loop. This is a narrower, harder-to-extract case than the dense-path's own internal sharing (the sparse loop's per-sub-batch tensor bookkeeping makes a clean shared helper more than a one-line change), but the recovery *policy* itself - halve on OOM, floor at 1, clear the cache, log - is duplicated logic that could silently diverge (e.g. a future change to the floor, the cache-clear call, or the halving factor landing in one copy and not the other). Rated low: both copies are correct and covered by existing GPU test paths, and unlike the `job_manager`/`jobs.py` findings this one is genuinely harder to consolidate given the sparse path's extra per-batch complexity - filed for visibility, not as an urgent refactor.

### codebase-indexer-incremental-scoped-duplicate-orchestration | medium | `_incremental_index_locked` and `_scoped_incremental_locked` duplicate the entire checkpoint-open/publish/commit pipeline

`CodebaseIndexer._incremental_index_locked` (`src/vaultspec_rag/indexer/_codebase_indexer.py`, body from ~L3319-3429) and `_scoped_incremental_locked` (~L3521-3629) duplicate roughly 80 lines of identical orchestration: `start = time.time()` -> `self._begin_preprocess_run(policy, ...)` -> `self._load_meta()` -> discover new/modified/deleted sets -> early-return `_unchanged_incremental_result` when nothing changed -> `self._resolve_code_pipeline_limits()` -> `self._open_run_checkpoint(..., run_control=run_control)` wrapped in the identical `except RunLedgerCompatibilityError: log + fall back to self._full_index_locked(...)` -> `self._resume_pending_finalization(...)` with the identical early-return -> `self._incremental_prior_ids_by_path(...)` -> `existing_ids` computed the identical way -> `self._publish_incremental_paths(...)` -> `self._commit_incremental_replacement(...)` -> `self.store.count_code()` -> an `IndexResult(...)` built from the identical field set. The only real difference between the two functions is the discovery step (`_scan_and_hash_incremental_inputs` for the full-tree path vs. `_scan_changed_paths` + `_hash_changed_paths` for the scoped/watcher path) and the `RunOperation` enum value passed to `_open_run_checkpoint` (`INCREMENTAL` vs `SCOPED_INCREMENTAL`). A subtle divergence already exists between the two duplicated tails: the full-tree path's `IndexResult.removed` is `len(deleted_files)`, while the scoped path's is `len(delete_files.intersection(previous_metadata))` - functionally near-equivalent today (both sets are derived from `previous_metadata`) but exactly the kind of drift that duplicated logic invites, since nobody is forced to keep the two counts' semantics aligned when one is edited. This is the largest duplicated orchestration surface found this session (job_manager's create/retry and jobs.py's start_reindex_vault/codebase are comparable in shape but roughly a third the size) - a change to checkpoint opening, the ledger-compatibility fallback, or the publish/commit sequence has to be made in two places by hand. Filed as medium given the surface size and the concurrency-sensitive lifecycle it duplicates (`RunLedgerCompatibilityError` handling, resumed-publication interception), though both copies are currently correct and covered (`test_indexer_unit.py`, `tests/integration/test_indexer_integration.py`, `tests/integration/test_targeted_reindex_integration.py`).

### transport-health-follows-redirects | high | The shared transport reaches the health endpoint with an opener that follows redirects, contradicting a deliberate security control on that same endpoint

The CLI's own health probe is built on an opener that explicitly refuses redirects, carrying an inline comment stating the purpose: rejecting redirects to prevent server-side request forgery through the health endpoint. The shared service-client transport reaches the same endpoint twice - once when fetching a token after an unauthorized response, once on the general send path - using the bare default opener, which follows them. The project has already decided, in writing, that redirects on this endpoint are a risk; one of the two clients honours that decision and the other silently does not.

The consequence is not theoretical, because of what the health response is used for. In the service stop path the sequence is: resolve the process identifier and token from the health endpoint, confirm identity against them, then terminate that process identifier. A followed redirect means the identifier selected for termination can come from whatever host the redirect pointed at. The severity is bounded by the fact that no route in the server emits a redirect, so the service itself never triggers this; exploitation requires a hostile or confused listener on the target port, reachable through an explicit port argument or by another process claiming the default port before the daemon binds. It is nonetheless a live defect with a one-line fix, and it must be fixed BEFORE any consolidation, not during it - folding a security correction into a tidiness refactor buries it.

### stop-path-identity-gate-is-tautological | high | The service stop path confirms identity by comparing the health response against itself

The stop path resolves a process identifier and a service token from the health endpoint, then calls an identity confirmation helper passing that same token as the expected value. The helper re-probes the health endpoint and compares the token in the response to the one it was given. Both sides of the comparison therefore originate from the same source, and any listener that answers consistently satisfies the check. The gate cannot distinguish our service from any other process that responds stably on that port.

This matters most in combination with the preceding finding: the no-redirect opener on the CLI probe is currently the control that keeps the answering listener local, and it is doing work the identity gate is not. Consolidating the probe onto the redirect-following transport would therefore remove the only control that presently holds. The two findings must be sequenced together, and the identity gate deserves its own remediation rather than being treated as satisfied.

### transport-unbounded-default-timeout | medium | The shared transport's request timeout defaults to unbounded, where the client it would replace defaults to bounded

The transport's call helper takes an optional timeout that defaults to absent, and an absent timeout reaches the underlying request as no timeout at all, so the call blocks on the socket default indefinitely. Every current caller of the health endpoint passes an explicit timeout, so the hazard is latent rather than active. The CLI probe it would replace defaults to a five-second bound and cannot hang. Consolidation would point this footgun at nine additional call sites, several of them in lifecycle verbs where a hung command is the worst outcome, so a bounded default belongs in the transport before it takes on those callers. Related: the token-fetch path uses a thirty-second timeout for what is a liveness-shaped request.

### job-dispatch-code-document-attempt-duplicate-runner | medium | `_run_code_attempt` and `_run_document_attempt` duplicate the admission/lease/resilience-publish attempt-runner shape

`_run_code_attempt` and `_run_document_attempt` in `src/vaultspec_rag/job_dispatch.py` are near-identical ~35-line bodies: both call `context.control.checkpoint()`, resolve a domain preflight (`validate_code_job_admission` / `validate_document_job_admission`), call `context.set_resilience(_admitted_resilience(<domain>))`, `registry.load_model()`, enter `registry.lease(root)`, set `writer_lock_held=True, pipeline_active=True` on the context, build a `JobProgressReporter`, branch on `clean` to call `<indexer>.full_index(...)` vs `<indexer>.incremental_index(...)` with the same `resumed`-detection logic, publish a resilience snapshot in a `finally` via `_publish_resilience(context, lambda: _code_resilience(...)/_document_resilience(...))`, unwind resources in nested `finally` blocks, and build the identical `JobExecutionResult` summary format (`+{added} /{updated} -{removed} ({duration_ms}ms){skipped_suffix}`) with the same preprocess fields. The only real differences are which indexer/preflight/resilience-snapshot function is threaded through. `_run_vault_attempt` is a simpler cousin of the same shape (no preflight, no resilience tracking, no `pipeline_active`) that could plausibly diverge further from the other two as vault gains features. This is the same recurring pattern already filed twice this session (`job-manager-retry-duplicates-create-job-construction`, `jobs-start-reindex-vault-codebase-duplicate-orchestration`) and once more in `codebase-indexer-incremental-scoped-duplicate-orchestration`: this codebase's job/index orchestration layer consistently duplicates a domain-parametrized sequence across sibling call sites (vault/code/document, or full/scoped) rather than factoring the shared attempt-runner shape into one function taking a small domain-adapter struct (indexer accessor, preflight validator, resilience-snapshot function, admission-kind). Filed as medium for the same reason as its siblings: no live defect (both bodies are correct and exercised by `tests/integration/test_indexer_integration.py` / `test_document_store.py`), but a real and now clearly recurring future-drift and maintenance-cost pattern across this session's findings - worth treating as one consolidation opportunity spanning `job_manager.py`, `jobs.py`, and `job_dispatch.py` rather than four separate ones.

### search-integration-tests-cannot-detect-empty-results | high | Five search integration tests assert only that a list came back, so a search path returning nothing or returning garbage passes all of them

The most consequential is a snippet test whose assertion is nested inside a truthiness check on the result list. If the vault search were broken and returned an empty list on every call, the guarded body never executes, no assertion runs, and the test passes green. A test named for verifying that results carry a snippet is structurally incapable of detecting the single failure mode most worth catching, which is search returning nothing at all.

Four further tests in the same module - empty query, special characters in query, very long query, and an end-to-end check of the sparse-search toggle - each terminate in an assertion that the returned value is a list. Reaching that line already proves no exception was raised, and the return annotation already guarantees the type on any non-raising return, so the assertion adds nothing whatsoever. Each of their docstrings frames the intent as not crashing, but none checks the behaviour named in the test: whether an empty query yields sensible results, whether special characters are handled meaningfully rather than silently producing noise, and above all whether disabling sparse retrieval changes the outcome at all. The last of those promises end-to-end verification of a feature toggle in its own name and delivers only that a list was returned.

The consequence is specific and it sits on the product surface: a broken embedding path, a silently ignored sparse-enabled flag, or a query-sanitisation regression returning irrelevant results would pass all five without complaint. This is rated high because it is the search quality the project exists to provide, and because the tests create the impression of coverage where none exists.

### deterministic-self-comparison-tests | low | Two tests compare a pure function's output to itself, so any consistently wrong implementation passes

One calls a content-epoch helper twice with the same literal argument and asserts the two results are equal; the other does the same with the collection-prefix helper and one path. For a deterministic pure function that assertion holds regardless of whether the function is correct - an implementation that ignored its argument, hashed the wrong fields, or returned a constant would satisfy it. They can only fail if the function becomes accidentally non-deterministic through a clock, a random salt, or mutable global state.

In both cases the sibling test does the real work and already subsumes them: one asserts the epoch CHANGES across different inputs, the other asserts differently spelled but equivalent paths produce the SAME prefix, which is the stronger property that same-input-twice is a special case of. These are redundant scaffolding beside genuine tests rather than independent checks. Low severity precisely because the coverage they appear to add is already provided next to them.

### transport-redirect-forwards-bearer-token | high | A followed redirect on the shared transport transmits the service bearer token to the redirect target

This extends the redirect finding recorded above, and it is the more serious half. The standard library's redirect handler builds its follow-up request by copying every header from the original except content length and content type, with no host comparison and no credential stripping. Unlike some third-party clients, which drop authorization headers when a redirect crosses hosts, the standard library forwards them unchanged. The transport sets an authorization header carrying a bearer token and passes that header mapping directly into the request object, so the token is present in exactly the mapping the handler copies.

The consequence of following a redirect on the transport's general request path is therefore not merely that an unintended host answers the call: the service token is disclosed to whatever host the redirect names. That is credential exfiltration to an attacker-chosen destination, materially worse than the process-identifier confusion on the health path, and it argues for refusing redirects across the whole transport rather than only on the health endpoint - the credential-bearing path is the one with more to lose.

The same mitigations apply as for the sibling finding: the service itself emits no redirects, so this requires a hostile or confused listener holding the target port. The severity reflects the outcome if that premise is met, not the likelihood of meeting it. Verified against the interpreter's own standard-library source rather than assumed from documentation.

### missing-guard-reranker-full-content-invariant | high | no test would fail if the reranker silently reverted to scoring the display snippet instead of full content

The `rerankers-score-real-content` rule exists because of a documented incident: the CrossEncoder scored 200-character display snippets while full content sat in memory. The production line enforcing the fix is `src/vaultspec_rag/search/_searcher.py:265`: `pairs = [(query, (r.rerank_text or r.snippet)[:char_cap]) for r in results]`. I searched every test referencing `rerank_text` or the `_rerank` method and found none that would fail if this line reverted to `r.snippet` alone, or if the upstream result-mapping step (`_searcher.py:476`, `rerank_text=content or None`) stopped populating `rerank_text`. The only tests that exercise `_rerank` directly (`tests/integration/test_search_integration.py::TestRerank`, all three tests) construct `SearchResult` objects by hand without passing `rerank_text` at all - it defaults to `None`, so `r.rerank_text or r.snippet` always falls through to `r.snippet` in these tests regardless of whether the production wiring between search-result-mapping and reranking is correct. These tests assert re-sort behavior and score types, which pass identically whether the reranker sees `rerank_text` or `snippet` - they cannot distinguish the fixed behavior from the regressed one. The only other `rerank_text=` usage in the test tree is `tests/test_server.py:297`, which checks that the field is excluded from a Pydantic model's wire serialization (`model_dump()`) - unrelated to reranker input selection. No test anywhere populates `rerank_text` with content that differs from `snippet` and then verifies the reranker's behavior differs accordingly (e.g. that a query matching only the full content, not the snippet, still surfaces the result). This is exactly the shape of regression the rule was written to prevent, and it would currently pass every test in the suite.

### missing-guard-gpu-lock-scope-invariant | medium | no test asserts the GPU lock is released before storage I/O, pair assembly, or score conversion

The `gpu-lock-wraps-forward-passes-only` rule requires tokenization-adjacent prep, pair assembly, score conversion, and storage I/O to run outside `with gpu_lock:`. Grepped the full test tree for `_gpu_section` (the context manager that scopes the lock in `search/_searcher.py`) and for any lock-scope-specific test name (`lock.*scope`, `forward.*lock`) - zero matches. `tests/test_service_registry.py::TestGpuLock` (3 tests) only verifies the lock object is the SAME shared instance across searchers (`slot_a.searcher._gpu_lock is slot_b.searcher._gpu_lock`), never that any specific operation is excluded from its scope. `tests/integration/test_index_job_control.py` uses `gpu_lock.acquire()`/`.locked()` for job-pause/dispatch contention tests, not to verify what code runs inside vs. outside the lock during a real rerank or encode call. No test would fail if a future edit wrapped a Qdrant upsert, the pair-assembly char-cap slicing, or the post-rerank score-to-float conversion inside the same `with self._gpu_section():` block as the forward call.

### missing-guard-index-workers-spawn-method-invariant | medium | nothing tests that the chunk-worker process pool uses the spawn start method

The `index-workers-stay-cpu-only` rule requires the chunk-worker `ProcessPoolExecutor` to be built via `multiprocessing.get_context("spawn")` so a forked worker never inherits a parent CUDA context. Grepped the full test tree for `get_context("spawn")`, `start_method`, and the literal `"spawn"` - zero matches anywhere in `tests/`. The existing guard (`test_worker_import_does_not_load_torch` in `test_chunk_worker_parity.py`, and `test_torch_load_centralized.py`'s import-graph checks) verifies torch is absent from the worker's import chain, which is necessary but not sufficient: if `_codebase_indexer.py`'s pool construction were changed from `multiprocessing.get_context("spawn")` to the platform default (`fork` on Linux), no test would catch it, even though fork is exactly the failure mode the rule exists to prevent (a forked worker inheriting a live CUDA context and crashing with 'Cannot re-initialize CUDA in forked subprocess').

### missing-guard-single-gpu-consumer-thread-invariant | medium | no test would catch a second GPU consumer thread or a second CUDA stream

The `gpu-consumer-single-thread` rule requires exactly one dedicated GPU consumer thread; a second consumer thread or separate CUDA streams for dense/sparse only serialise on one saturated device and add overhead, not correctness risk, which is exactly why nothing currently catches it. `tests/integration/test_gpu_pipeline_integration.py` (the file whose own docstring names "the dedicated GPU consumer-thread pipeline") only asserts output parity between the parallel and serial paths (`test_parallel_pipeline_matches_serial`) and correct error propagation on a real dimension mismatch (`test_dimension_mismatch_raises`) - neither counts active consumer threads, inspects `threading.enumerate()`, or checks CUDA stream usage. A second consumer thread or a second stream would still produce byte-identical upserted chunks and would still propagate a genuine consumer failure correctly, so both existing tests would pass unchanged under a violation of this invariant.

### missing-guard-storage-lock-ordering-invariant | low | the lifecycle-before-collection lock order is exercised but never adversarially tested

Invoking the real entry point directly showed both the canonical value and the alias resolving correctly against the same running daemon.

The severity is about what it costs to trust a test rather than about a defect in shipped code - there is no defect here. A verification that silently exercises the wrong binary is worse than no verification, because it produces confident evidence for a false conclusion, and the failure is invisible: the command exists, runs, and answers. Every command-line observation in a session like this one is suspect until the invocation path is established.

Remediation is to regenerate the environment's console scripts. Recording it because the footgun is structural rather than incidental - the invocation that looks most careful, the environment-scoped one with synchronisation disabled, is exactly the one that fails silently.

## Recommendations

Collapse the duplicated lifecycle outcome-envelope helpers onto the shared render module as one generalized success and failure pair, so the broker-facing outcome contract has a single implementation that cannot drift per verb. This is a refactor within a settled decision, not a new decision, and belongs to the service and CLI domain rather than to the indexing boundary work currently in flight.

Resolve the dual health clients by deciding, and then recording, which of two things is true: either the bootstrap probe is a genuine second client justified by running before a service status file exists, in which case the transport module docstring must stop claiming singularity and the split must be documented at both sites; or it is redundant, in which case the CLI probe folds into the transport and the redirect and error-envelope behaviours are reconciled. A decision that changes which module owns the health call is architecturally significant and warrants a follow-on decision record; simply documenting an existing deliberate split is not.

Correct the broker-facing outcome rule document to name the modules that actually hold the helpers. Edit the rule source under the harness rules directory and re-sync, never the generated provider mirrors.

Leave the bounded query-parameter clamp alone unless one of those routes is being modified for another reason; consolidating two small clamps in isolation costs more review attention than the repetition costs.

The code-kind admission guard finding needs no further recommendation - it is remediated under the in-flight boundary plan and is recorded here only so the sweep's result set is complete.

The dual health-client recommendation recorded above is superseded by research and must not be actioned as written. It offered a clean either-or: the split is load-bearing and gets documented, or it is redundant and ownership moves. Neither branch survives contact with the code.

The justification for the split is false. The transport does not depend on the service status file: the port is an explicit caller-supplied parameter, the status-file token reader tolerates absence by returning empty, the token fetch on an unauthorized response returns empty on any failure so the request still proceeds, and the transport already serves the health endpoint itself with a short timeout. There is no bootstrap ordering barrier, so the second client cannot be justified on the grounds that it must run before a status file exists.

But the duplication is not simply redundant either, because the two clients differ in three behaviours and the CLI's are the correct ones in every case: it refuses redirects, it always bounds its timeout, and it never raises - returning a sentinel for unreachable and a structured payload for answered-but-unhealthy, which every one of its nine call sites branches on. The shared transport raises on connection-level failure, so moving ownership rewrites error handling at all nine sites, two of which sit in lifecycle verbs governed by the rule requiring exactly one structured envelope on every exit path. An exception leaking through a stop branch is precisely what that rule exists to prevent.

The corrected sequence is three separable pieces. First, fix the redirect defect in the transport on its own merits, immediately, with its own record - it stands alone, it is small, and it makes the transport safe to consolidate onto later. Second, remediate the tautological stop-path identity gate, recognising that the no-redirect opener is currently compensating for it. Only then is the ownership question genuinely open, and it is architecturally significant enough to require its own decision record rather than being taken as a refactor, because it moves nine call sites and changes an error contract across two broker-facing lifecycle verbs. Independently of how that decision lands, the transport's docstring claim that every call from both the CLI and the MCP funnels through it is false today - nine CLI call sites bypass it - and should be corrected now rather than left asserting an invariant the code does not hold.

Treat the four job and index orchestration findings as ONE consolidation opportunity, not four refactors. They are independent code locations with no double-counting, but they are the same shape repeated: a pair of near-identical paths differing only in which domain they serve or which discovery step they use. The pairs are create versus retry in the job manager, vault versus codebase reindex start in the jobs module, full-tree versus scoped incremental in the codebase indexer, and code versus document attempt running in the job dispatcher. Each pair duplicates not merely construction but the surrounding error handling, fallback, and publication sequence.

The evidence that this is a live cost rather than an aesthetic one is already on the page: the two incremental paths compute their removal count differently - one counts the deleted set, the other counts its intersection with prior metadata - and nothing forces those to stay aligned. That is the drift duplication invites, occurring in code where both copies are currently correct and tested.

One further signal raises this above ordinary repetition: in the jobs module the unified replacement ALREADY EXISTS. A single activation function handles vault, code, and document uniformly through preflight parameters, while the older per-domain start functions remain live beside it. That is a superseded pattern that was never retired, which is a different and more actionable problem than duplication that simply grew.

The shape of the fix is a domain-parametrized attempt runner spanning the job manager, the jobs module, and the job dispatcher, with the discovery step and domain preflight passed in rather than branched on. This is architecturally significant - it changes the ownership of the orchestration sequence across three modules - and warrants its own decision record and plan rather than being taken as opportunistic cleanup. It should not be started while the index and document boundary work is in flight, since both touch the same orchestration surface.

The three remaining findings - the duplicated readiness probe, the duplicated backoff curve, and the second out-of-memory halving ladder - are genuinely unrelated to that cluster and to each other. They are individually small and should be taken opportunistically when their files are next modified, not batched into a campaign.

**Tier 4: independent, safe to run in parallel with everything above.** The seven missing-invariant-guard findings have remedy sketches already filed and touch no code the other tiers are contending over. Internal order, ranked by silent-regression risk times how directly the consequence lands on the product:

1. `missing-guard-reranker-full-content-invariant` - write this one first if only one gets written. Three things separate it from the other six: the invariant has already regressed once in this exact codebase, which is the only reason the rule exists; the current tests do not merely fail to cover it, they actively execute the regressed code path (`rerank_text` always `None`, always falling through to `snippet`) and report green; and the failure mode has zero observable symptom - no crash, no error, no metric moves, search just gets quietly worse in a way nobody would think to attribute to this line. Every other guard in this list either self-diagnoses loudly on violation (spawn-method reversion crashes on first CUDA re-init), is a performance-only consequence discoverable by benchmarking (GPU lock scope, single consumer thread), or requires a rarer trigger condition to manifest at all (archive failure, a lock-ordering race). The reranker path runs on every search, on every project, with no gate between the regression and the user.
2. `missing-guard-archive-before-delete-failure-branch` - second because the consequence if it silently regresses is irreversible data loss, which outranks everything else on this list except the reranker's near-certainty of eventually mattering. Rarer trigger (an actual archive failure) than the reranker, which is why it is not first.
3. `missing-guard-storage-lock-ordering-invariant` - cheap to write (a source-scan AST check, no GPU, no fixture setup) and guards a deadlock, which is catastrophic but self-announcing (a hung process gets noticed fast). 4. `missing-guard-gpu-lock-scope-invariant` - a silent throughput regression under concurrent load, not a correctness bug; real but slower to notice than the above three.
5. `missing-guard-index-workers-spawn-method-invariant` - self-diagnosing (a fork-mode violation crashes loudly the first time CUDA is touched in a worker), so the guard's value is catching it in CI before a user does, not preventing an otherwise-silent failure.

7. `missing-guard-document-reindex-completion-coverage` - cheapest to write (a direct copy of an existing passing test's shape) and lowest urgency, since the duplicated-but-tested sibling path means a bug here is only invisible if it is specific to the untested branch, not shared with the tested one.
