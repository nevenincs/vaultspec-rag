## Capability summary

All points below describe test expectations, not verified production behavior.

- [src/vaultspec_rag/tests/test_typesafe_policy.py](../../../../src/vaultspec_rag/tests/test_typesafe_policy.py) specifies the isolated Typesafe policy contract: bounded overlapping candidate batches; query assessment and filter-aware hints; abstention on unavailable provider, invalid-size query, or transport failure; request and session budgets; use of complete candidate content and metadata; confidence-sensitive drop/soft-ranking behavior; atomic failure fallback; score replacement while preserving result identity and locators; bounded verbatim query clauses; and aggregation of request, token, cache, coalescing, and timing metrics. Its principal direct callers are prepare_query, ClassificationSession.rank, candidate_limit, query_clauses, candidate_questions, and the transport evaluator (lines 45-76, 115-237, 240-392, 396-550).
- [src/vaultspec_rag/tests/test_typesafe_search.py](../../../../src/vaultspec_rag/tests/test_typesafe_search.py) specifies the search integration through VaultSearcher and public combined search. Its mock-backed cases cover keyless preservation of the legacy result budget and scores, no enrollment for empty/filter-only requests, classification over full content before snippet truncation, bounded candidate widening, deterministic fallback after classification failure, authoritative explicit filters and intent, per-domain failure preservation, private notes, and timing attribution (lines 78-110, 119-234, 236-324, 327-420, 451-475, 478-558). The mock store means these cases chiefly specify orchestration around search calls.
- [src/vaultspec_rag/tests/test_typesafe_status.py](../../../../src/vaultspec_rag/tests/test_typesafe_status.py) specifies that health exposes daemon enrollment state without exposing a credential, start and status output share a daemon-derived label, JSON start output carries the same snapshot, and absent health evidence is rendered as not reported despite a client environment value (lines 23-76).
- [src/vaultspec_rag/tests/test_typesafe_transport.py](../../../../src/vaultspec_rag/tests/test_typesafe_transport.py) specifies typed evaluation validation, enrollment-state reads, credential rotation and circuit behavior, safe failure categories, request/deadline/concurrency bounds, refusal to follow redirects, request and response size limits, response normalization without mutating the input, persistent connection reuse and expiry, exact response-cache keys and bounds, duplicate-request coalescing, and handling of late success/failure. Its HTTP tests use a loopback server; the fixture redirects the configured endpoint to a local address (lines 49-97, 99-154, 156-339, 342-479, 481-532, 534-699).
- [src/vaultspec_rag/tests/test_unbuilt_index_diagnostics.py](../../../../src/vaultspec_rag/tests/test_unbuilt_index_diagnostics.py) specifies route classification and CLI/MCP presentation for missing, unreadable, updating, and verified-empty index evidence. It checks that relevant rebuild jobs remain visible, unrelated or terminal jobs do not mask an unbuilt index, first-index guidance is preserved by API and in-process renderers, reason values are constrained, and a combined response retains all source facts (lines 45-95, 98-176, 179-243, 245-281, 284-362).
- [src/vaultspec_rag/tests/test_undispatched_job_health.py](../../../../src/vaultspec_rag/tests/test_undispatched_job_health.py) specifies when queued work is listed as undispatched and when it degrades job health: an open manager with queued work is listed; a running attempt, paused admission, startup restore, quiesce, or shutdown suppresses that listing; health reports a queued job only at or beyond the stall threshold (lines 78-120, 122-194, 196-238).

## Interfaces and data flow

- Typesafe policy tests construct SearchResult or DocumentSearchResult values with retrieval scores, display snippets, full rerank content, and paths; they patch the transport evaluator and assert rankings, preserved originals, session state, and metric fields. Search integration tests replace store fetches and query encoding with controlled fixtures, then call per-surface search methods or \_public_search.search_combined_timed; asserted outputs include ranked results, fallback timings, partial-domain outcomes, and unchanged diagnostic notes.
- Transport tests pass a state mapping and question schema to evaluate; expected outputs are typed answers plus usage and timing metadata. The local HTTP handler captures request state/questions and returns controlled status/body/framing. Tests also directly manipulate isolated cache, pool, circuit, slot, and in-flight state to assert lifecycle behavior.
- Status tests call the HTTP app's /health endpoint and pass its feature snapshot to CLI start/status renderers. Expected output is a state label or JSON data envelope with no credential material.
- Readiness tests assemble integrity and index-state inputs, job snapshots, request facts, and optionally a published-generation readiness snapshot; classification produces a source fact and response that are then sent through MCP, HTTP-backed CLI, or in-process CLI rendering.
- Job-health tests create an indexing JobSpec, start a real JobManager through startup methods, and pass queued timestamps to \_jobs_health; expected outputs are an undispatched count and degradation reasons. The tests explicitly choose an in-memory manager for several cases.
- Install tests create a temporary consumer workspace, invoke install/uninstall functions or Typer commands, and inspect reports, warnings, exit status, help text, and filesystem contents. The sync tests exercise a pure result classifier plus a subprocess wrapper and one install path with an empty PATH.
- Vault audit/checkpoint tests use temporary roots and VaultStore, record confirmed chunk units, publish proof/generation transitions, mutate payloads, and inspect audit counts, checkpoint state, pending chunks, or reconciliation results. Checkpoint exposure tests observe checkpoints via observe_checkpoint_progress while invoking VaultIndexer operations with a placeholder embedding model and null progress reporter.
- The interfaces and flow descriptions in this section are inferred from test setup and calls; their production implementation was not inspected.
