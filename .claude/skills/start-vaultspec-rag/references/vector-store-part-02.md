## Capability summary

- [src/vaultspec_rag/store_schema.py](../../../../src/vaultspec_rag/store_schema.py) is the canonical Qdrant storage contract: bare collection names; vector names, dimension and distance; typed payloads; index and filter-key sets; effective model/dimension configuration; JSON-compatible schema description and compatibility verdicts; and persisted collection-identity/conformance types and evaluation (lines 1-19, 63-115, 127-331, 334-463, 466-563, 566-804).
- [src/vaultspec_rag/store_runtime.py](../../../../src/vaultspec_rag/store_runtime.py) defines VaultStore, its construction and client lifecycle, backend identity, local/server naming and locks, interpreter/dependency guard, retry-wrapped read/delete helpers, and point-operation lock policy. It composes the search, catalog, collection, ingest, and donor mixins (lines 60-91, 239-273, 276-394, 395-469, 471-680, 682-806).
- [src/vaultspec_rag/store_collections.py](../../../../src/vaultspec_rag/store_collections.py) supplies collection creation, payload-index reconciliation, deletion/reset, code-generation target validation, served-collection conformance checks, and best-effort server manifest updates. Reads reconcile an existing collection but do not create an absent one (lines 85-159, 161-290, 292-342, 344-454, 456-582).
- [src/vaultspec_rag/store_donors.py](../../../../src/vaultspec_rag/store_donors.py) provides read-only donor-vector lookup. It restricts local reads to collections already owned by the handle, batches ID retrieval, treats missing points/collections and unusable dense vectors as misses, and converts valid stored dense/sparse vectors and payloads into DonorPoint values (lines 26-44, 47-83, 85-177, 179-225).
- [src/vaultspec_rag/store_ingest.py](../../../../src/vaultspec_rag/store_ingest.py) builds vector and payload records; upserts vault, code, and document chunks; overwrites vault payloads while retaining vectors; applies server-mode ingest fences and exact-count verification; checks disk headroom; and deletes points by payload or stable IDs, including journaled publication and migration-origin deletions (lines 42-56, 105-131, 133-388, 390-465, 467-602).

## Interfaces and data flow

- VaultStore(root_dir, embedding_dim=None) checks the supported interpreter and Qdrant dependency, reads configuration, chooses local or server mode, resolves per-root collection names in server mode, opens the relevant client, establishes lock state, and derives a backend identity. Its mixins provide the collection, ingest, donor, catalog, and search surface (runtime lines 276-394). Search/catalog implementations are outside this slice.
- The storage schema is shared by collection creation and ingest: named dense/sparse vectors and payload/index definitions come from store_schema; store_ingest turns chunk inputs into Qdrant points and uses ensure methods before writes (schema lines 79-104, 127-331; collections lines 344-415; ingest lines 42-56, 156-182, 280-307, 309-388).
- Collection ensure creates if absent, applies declared indexes, evaluates stored identity against expected identity and live dense width, caches the verdict, then sets the ensure latch. Fatal sparse-model or geometry mismatches raise; dense-model mismatch at matching geometry is retained as a nonconforming verdict and logged (collections lines 401-415, 485-519; schema lines 699-804).
- Normal writes acquire a collection-specific write lock, check disk headroom, and run the upsert through the bounded write retry helper. In server mode, callers may defer apply with wait=False; apply_ingest_barrier fences earlier WAL work with a reserved sentinel deletion and compares exact point count to the caller's expected count before terminal actions (ingest lines 346-388, 390-455).
- Local storage uses {root}/{data_dir}/{qdrant_dir} and an exclusive file lock. Server storage uses a shared Qdrant endpoint with root-prefixed collection names, a configured storage-probe path, and no client-side point lock. Lifecycle operations remain guarded; local point operations use per-collection reentrant locks (runtime lines 285-295, 330-378, 395-457, 653-680).
- Donor calls accept a collection and string chunk IDs, hash IDs through the store's stable-ID method, retrieve bounded batches with payloads and vectors, and return found valid records keyed by original string ID. The stable-ID implementation itself is outside this slice (donors lines 85-136).
- store_schema.describe_storage_schema() produces a JSON-serializable descriptor; assert_compatible checks version, dense vector name, and expected dimension. evaluate_conformance additionally compares collection provenance and live dense width (schema lines 397-463, 489-563, 699-804).
