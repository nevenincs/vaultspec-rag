## Capability summary

This slice maps search, readiness, service lifecycle, and CLI expectations through tests; it does not contain inspected production implementation.

- [src/vaultspec_rag/tests/test_search_conformance_refusal.py](../../../../src/vaultspec_rag/tests/test_search_conformance_refusal.py) builds populated local `VaultStore` collections and mutates sidecar identity to exercise typed handling of storage incompatibility for vault, code, and document searches. It expects fatal geometry/sparse-model mismatches to produce a non-retryable 409 rebuild response with actionable remediation and non-authoritative absence; dense-model provenance differences alone remain searchable. It also covers collection-scoped verification, unknown exceptions remaining unclassified, combined partial results and total failure, empty compatible results not claiming authority when another source failed, and count failures carrying the same source fact. (1-439)
- [src/vaultspec_rag/tests/test_search_freshness_config.py](../../../../src/vaultspec_rag/tests/test_search_freshness_config.py) specifies the `search_freshness_wait_max_seconds` configuration contract: default 30 seconds, environment and explicit-setting precedence, inclusive 0–300 bounds, and errors for non-finite, malformed, boolean, or out-of-range values. (1-111)
- [src/vaultspec_rag/tests/test_search_noise.py](../../../../src/vaultspec_rag/tests/test_search_noise.py) specifies code-search noise-policy resolution and application: default hidden/demoted domains and penalty; include, exclude, and only filters; query-token parsing; domain-filter validation for code searches; hard filtering from payload or path classification; and score demotion. (1-223)
- [src/vaultspec_rag/tests/test_search_orientation.py](../../../../src/vaultspec_rag/tests/test_search_orientation.py) covers combined-search source orientation. It expects document inclusion to be explicit, the default vault selection to favor ADRs for an untyped locking query, combined hits to rank across vault and code while retaining partial failures, and requested-source readiness to reflect the selected domains. It also covers CLI request selection and advisory output, MCP `search_combined` schema/advisory, strict boolean route validation, exclusion of document work when not requested, and document filters requiring explicit document selection. (31-267)
- [src/vaultspec_rag/tests/test_search_outcomes.py](../../../../src/vaultspec_rag/tests/test_search_outcomes.py) specifies `SearchDomainOutcome` and `CombinedSearchOutcome` expectations: a failed domain cannot carry hits; partial outcomes retain successful hits and expose per-domain readiness; all-domain failure differs from empty success; absence is authoritative only when each included source supports it; source/fact identity is checked; and dominant failure selection is stable. AST-based guards check centralized combined-failure vocabulary and account for route activity outcomes. (35-341)
- [src/vaultspec_rag/tests/test_search_quality_fixes_unit.py](../../../../src/vaultspec_rag/tests/test_search_quality_fixes_unit.py) covers vault document path prefix normalization and AST chunk-merge identity: a class-tail chunk must not adopt a neighboring module function, while genuine method and structureless-chunk identity is retained. (1-80)
- [src/vaultspec_rag/tests/test_search_quiesce_admission.py](../../../../src/vaultspec_rag/tests/test_search_quiesce_admission.py) specifies service quiesce behavior at the search boundary. All four search types are expected to receive the retryable 503 admission-closed envelope and one unavailable activity record, with no project/model/reranker construction. A loopback transport test expects the service response to pass through unchanged. Other cases cover active-ticket drain before quiescence and lease rejection before project or compute construction. (31-246)
- [src/vaultspec_rag/tests/test_search_readiness.py](../../../../src/vaultspec_rag/tests/test_search_readiness.py) covers revision-target readiness waits: immediate and zero-timeout fast paths, lock/GPU responsiveness while waits are pending, satisfaction checks around deadlines, observer registration/re-registration/cleanup, cancellation and registry close, all-target completion for multiple sources, isolation by root and source, monotonic revisions and generation matching, and rejection of terminal job transitions as publication. It also expects document and code generation publication callbacks to notify only after durable publication and exactly once, including resumed code finalization. (63-649)
- [src/vaultspec_rag/tests/test_search_readiness_responsiveness.py](../../../../src/vaultspec_rag/tests/test_search_readiness_responsiveness.py) expects cold publication-proof reads not to block the async search handler/event loop, for each `FreshnessWaitPolicy`, and expects an empty-document result to complete successfully after the proof reader is released. (27-93)
- [src/vaultspec_rag/tests/test_search_readiness_restore.py](../../../../src/vaultspec_rag/tests/test_search_readiness_restore.py) covers restart restoration from compatible durable publication proofs, including empty-index authority and already-satisfied bounded targets. It expects restored baselines not to satisfy newer controller targets; no-op publication to preserve parent proof identity; and unreadable, incompatible, open, changed, or generation-mismatched proof states not to restore or assert authoritative absence. It also checks active-job freshness, concurrent publication during restore, and that missing publication state does not create a ledger. (76-698)
- [src/vaultspec_rag/tests/test_search_service_first.py](../../../../src/vaultspec_rag/tests/test_search_service_first.py) specifies CLI mandate and routing behavior: local search is enabled by explicit fallback or configured local-only mode; absent/dead services without a mandate fail without loading heavy libraries; a mandated local operation has a wall-clock deadline whose timeout emits a JSON error and exits, and whose timer is cancelled on normal exit. (50-285)

## Interfaces and data flow

- **Search request and selection.** Tests construct `CombinedSearchRequest` and server `SearchRequest`, with query, root, top-k, search type, payload/filter options, document inclusion, request ID, and freshness policy. The expected orientation dispatch asks for an ADR-oriented vault search and code search when documents are excluded; document work is omitted. CLI tests inspect the JSON request sent to a service fixture, while MCP tests inspect tool schema and advisory text. ([src/vaultspec_rag/tests/test_search_orientation.py:40-70, 124-174, 196-231](../../../../src/vaultspec_rag/tests/test_search_orientation.py#L40))
- **Availability and outcomes.** Tests feed source facts, readiness snapshots, job snapshots, counts, and search callbacks into route availability/classification and outcome objects. Expected outputs include result lists, per-domain status/readiness, partial/total failure, absence authority, HTTP status, retryability, and rebuild remediation. ([src/vaultspec_rag/tests/test_search_conformance_refusal.py:125-183, 265-338](../../../../src/vaultspec_rag/tests/test_search_conformance_refusal.py#L125); [src/vaultspec_rag/tests/test_search_outcomes.py:70-106, 119-199](../../../../src/vaultspec_rag/tests/test_search_outcomes.py#L70))
- **Freshness and publication state.** Tests use root/source/revision/generation targets with a `ReadinessRevisionRegistry`; publication and controller notifications are separate inputs. Expected effects include rechecking after notifications, waiting until every requested target is published, and unregistering observers on completion, timeout, cancellation, or close. Other tests acquire publication snapshots/proofs and exercise callback notification after durable code/document publication. ([src/vaultspec_rag/tests/test_search_readiness.py:63-76, 128-248, 251-389, 391-500, 520-649](../../../../src/vaultspec_rag/tests/test_search_readiness.py#L63); [src/vaultspec_rag/tests/test_search_readiness_restore.py:159-262, 520-698](../../../../src/vaultspec_rag/tests/test_search_readiness_restore.py#L159))
- **State and integrations represented by fixtures.** The tests write/read a Qdrant sidecar identity and count real local collections; construct run-ledger/checkpoint records and SQLite publication state; manipulate environment-backed configuration; exercise service quiesce and the search activity ledger; and use Starlette clients, loopback HTTP, or fresh Python subprocesses for transport/CLI cases. These are test fixture interactions, not a complete implementation trace. ([src/vaultspec_rag/tests/test_search_conformance_refusal.py:59-95, 148-183](../../../../src/vaultspec_rag/tests/test_search_conformance_refusal.py#L59); [src/vaultspec_rag/tests/test_search_readiness_restore.py:76-129, 413-464](../../../../src/vaultspec_rag/tests/test_search_readiness_restore.py#L76); [src/vaultspec_rag/tests/test_search_quiesce_admission.py:114-209](../../../../src/vaultspec_rag/tests/test_search_quiesce_admission.py#L114); [src/vaultspec_rag/tests/test_search_service_first.py:133-157, 204-285](../../../../src/vaultspec_rag/tests/test_search_service_first.py#L133))
