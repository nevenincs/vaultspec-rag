## Capability summary

- [src/vaultspec_rag/tests/test_cli_qdrant.py](../../../../src/vaultspec_rag/tests/test_cli_qdrant.py) exercises the operator-facing Qdrant commands through the CLI app: help language; human and JSON status for absent, operator-supplied, invalid, and unverified managed binaries; paired operator binary path/digest settings; install dry runs from release metadata or local archives; unknown legacy `--binary`; and clean dry-run output. Tests use temporary paths, an occupied/closed loopback port, and test provisioning/TLS seams. Coverage visible here includes clean dry-run only, not a successful destructive clean. (lines 1-498)
- [src/vaultspec_rag/tests/test_cli_refusal_channel.py](../../../../src/vaultspec_rag/tests/test_cli_refusal_channel.py) launches `python -m vaultspec_rag` in a subprocess with an invalid logging-level environment value, checking that pre-command refusal is one JSON envelope on stdout in JSON mode and an `Error:` diagnostic on stderr in plain mode. Its scaffold creates an enrolled workspace. (lines 1-102)
- [src/vaultspec_rag/tests/test_cli_root_settings_flags.py](../../../../src/vaultspec_rag/tests/test_cli_root_settings_flags.py) checks that root path/log flags seed values subsequently visible through `get_config()`, both on a workspace command and on the `server status` path that does not resolve a workspace. It resets the settings singleton around each test. (lines 1-105)
- [src/vaultspec_rag/tests/test_cli_search.py](../../../../src/vaultspec_rag/tests/test_cli_search.py) covers search timeout defaults; readiness freshness option validation and service request/payload handling; human readiness and failure rendering with bounded display fields; HTTP search source/filter validation and transport outcomes; combined in-process failure rendering; result line formatting; and `sys.argv` path/query glob-expansion behavior. Its local HTTP stubs capture requests and can return canonical envelopes, malformed responses, or stalled responses. (lines 1-1265)
- [src/vaultspec_rag/tests/test_cli_search_safety.py](../../../../src/vaultspec_rag/tests/test_cli_search_safety.py) covers service-first/fail-hard search expectations and explicit local fallback; search request mapping and result/empty-result rendering; local-store lock diagnostics in human and JSON modes; transport-only timeout errors; breadth-shortfall warnings and JSON preservation; and rendering behavior when source files are undecodable, missing, or changed since indexing. (lines 1-823)

## Interfaces and data flow

- CLI entry points observed in tests: the Typer `app` is invoked with `CliRunner` for most command checks; refusal-channel tests invoke the package module in child processes. Qdrant tests use `server qdrant status|install|clean`, plus `server start`; search tests use `search` and a readiness subcommand; root settings tests also exercise `preprocess status`, `index`, and `server status`. These are tested invocations, not a complete command inventory. (qdrant 60-498; refusal 47-102; root flags 47-105; search 166-181, 798-823, 1214-1265; safety 55-346)
- Inputs include CLI options, environment settings, temporary project/status/storage paths, JSON envelopes returned from local HTTP servers, and synthetic result/index metadata. Tests capture human text, JSON, exit status, HTTP request bodies, process stdout/stderr, and configuration values. (qdrant 86-257, 284-337, 341-446; root flags 58-82; search 210-408, 415-519; safety 128-210, 262-310, 549-592)
- Test fixtures isolate filesystem state under temporary directories. Search transport/readiness tests use loopback HTTP servers; refusal-channel tests use subprocess streams; locked-store tests claim to hold a store in another process. This describes test setup and assertions only; underlying storage and service implementation were not inspected. (refusal 47-77; search 37-116, 166-181; safety 358-457, 533-592)
- Imported/called interfaces identify likely local boundaries: `cli.app`, config settings/types, search transport and render helpers, search outcome/state types, and Qdrant constants/provisioning seams. Their implementations are uninspected. (qdrant 11-15; root flags 26-29; search 22-32, 842-856, 931-975, 999-1005, 1181-1188; safety 12-27, 350-350, 745-745)

## Boundaries and dependencies

- The tests assert that search HTTP requests carry query, top-k, project root, source type, optional filters, and freshness settings; they assert service responses are preserved and timeout failures do not acquire client-synthesized readiness/remediation facts. The actual protocol implementation is not present in this slice. ([src/vaultspec_rag/tests/test_cli_search.py](../../../../src/vaultspec_rag/tests/test_cli_search.py) 233-283, 415-478, 479-519)
- Corpus-specific filter expectations distinguish code filters (such as path, language, structure, include/exclude paths, locale deduplication, and preference) from vault/document filters; several tests assert wrong-corpus use is rejected before transport. These expectations are not an independently verified CLI specification. ([src/vaultspec_rag/tests/test_cli_search.py](../../../../src/vaultspec_rag/tests/test_cli_search.py) 539-785)
- Qdrant tests treat the binary path and SHA-256 as a paired operator setting and expect unverified managed binaries to be reported unusable; fixture helpers and runtime verification code were not inspected. ([src/vaultspec_rag/tests/test_cli_qdrant.py](../../../../src/vaultspec_rag/tests/test_cli_qdrant.py) 157-257, 260-337, 406-446)
