## Capability summary

These are integration/unit test responsibilities and expected contracts, not verified implementation behavior.

- [src/vaultspec_rag/tests/integration/test_service_jobs_routes_collection.py](../../../../src/vaultspec_rag/tests/integration/test_service_jobs_routes_collection.py) seeds job records through the jobs API and exercises authenticated `GET /jobs`: limit behavior and ordering of running/failed jobs, phase/source/trigger/query filtering, `codebase` source alias normalization, failed/job-id/since filters, query matching runtime/initiator, progress-update time for `since`, and prefixes matching multiple IDs. It re-exports route-app and clean-jobs fixtures from uninspected helpers.
- [src/vaultspec_rag/tests/integration/test_service_jobs_routes_controls.py](../../../../src/vaultspec_rag/tests/integration/test_service_jobs_routes_controls.py) checks route-level exact-ID handling, paused-job filtering, retry/delete, control conflicts, cancellation by expected revision, nonterminal capacity (including the expected 429 `job_capacity_exceeded` response), and `/reindex` validation of type and explicit mode-matched authority.
- [src/vaultspec_rag/tests/integration/test_service_jobs_routes_mutations.py](../../../../src/vaultspec_rag/tests/integration/test_service_jobs_routes_mutations.py) checks generic index-request authority preservation/rejection, attempt-dispatch authority/mode checks and check ordering, then uses an in-process ASGI client against the real app to assert invalid reindex requests are refused and durable admission/cancel/retry/delete mutations allow an independent unauthenticated request to run during the mutation.
- [src/vaultspec_rag/tests/integration/test_service_lifecycle_discovery.py](../../../../src/vaultspec_rag/tests/integration/test_service_lifecycle_discovery.py) exercises `server reconcile` against legacy or incomplete discovery identity, heartbeat repair of status and machine-pointer views, shutdown cleanup staying terminal, reconciliation of deleted/stale/foreign pointers while preserving daemon identity, and a singleton-claim loser’s forced-exit evidence.
- [src/vaultspec_rag/tests/integration/test_service_lifecycle_orphan_reap.py](../../../../src/vaultspec_rag/tests/integration/test_service_lifecycle_orphan_reap.py) covers `server stop --orphans`: one structured envelope on JSON paths, no envelope in human mode, idempotent empty reap, refusal when port scope cannot be resolved, and an out-of-process reap naming actual terminated PIDs. The test’s process witness and helpers are imported from uninspected test modules.
- [src/vaultspec_rag/tests/integration/test_service_lifecycle_runtime.py](../../../../src/vaultspec_rag/tests/integration/test_service_lifecycle_runtime.py) covers health/start/stop, durable queued and paused job state over two daemon lives, shutdown interruption after confirmed storage and worker release followed by store reopen, retaining incremental rows with an unverifiable integrity receipt, already-running/stale-status starts, stop with/without a status file, human/JSON running status details, and two-project search isolation through direct HTTP calls shaped as one MCP tool call.
- [src/vaultspec_rag/tests/integration/test_service_lifecycle_startup.py](../../../../src/vaultspec_rag/tests/integration/test_service_lifecycle_startup.py) covers subsecond health deadlines; startup spawn, status-publication, and readiness failures with bounded diagnostics and cleanup; running-phase failure rollback; publication and cleanup of pre-readiness Qdrant identity; Windows late-spawn cleanup and unrelated-process protection; Qdrant incarnation/witness validation; and POSIX ordinary/forced orphan-reap safety and detached-child cleanup. OS-specific cases are guarded by platform conditions.

## Interfaces and data flow

- Route tests invoke `/jobs`, `/reindex`, `/search`, and `/jobs/{id}/desired-state`, `/retry`, and `DELETE /jobs/{id}` via a fixture-backed Starlette test client or `httpx` ASGI transport; requests pass bearer tokens or query tokens, job specs, filters, and expected revisions. Assertions inspect JSON job/spec/outcome fields and status codes. The route-app fixture implementation was not read.
- Lifecycle tests invoke the Typer CLI through `CliRunner` (`server start`, `stop`, `status`, `reconcile`, and `stop --orphans`), or spawn `python -m vaultspec_rag.server` and poll HTTP health. Health assertions use fields such as service token, PID, readiness, models/features, and project count.
- Test state is mostly under `tmp_path`: service status JSON, machine discovery pointer, job-state JSON, Qdrant identity, logs, synthetic projects, and marker files. Tests also use a machine singleton lock, process/PID probes, loopback ports, an optional provisioned Qdrant source fixture, and subprocesses. The lifecycle tests assert relationships among launcher, daemon, and Qdrant PIDs and listener ports; ownership mechanisms themselves were not inspected.
- No production caller graph can be established from these test files. Visible callers are tests invoking imported app/API/helper symbols; helper and fixture implementations are uninspected.

## Boundaries and dependencies

- Jobs-route coverage is split across collection, controls, and mutation concerns. Lifecycle coverage is split across discovery convergence, orphan reaping, runtime behavior, and startup/rollback behavior.
- The tests directly import production-facing symbols from jobs, job manager/models/dispatch, server routes/app, CLI/process/status, machine-lock, service/quiesce, and Qdrant runtime modules. They also depend on test helpers, fixtures, and corpus/model setup. No behavior behind those imports is inferred as implementation fact.
- Module docstrings describe several lifecycle suites as using real subprocesses, model loading, and Qdrant, with stated TESTGAP identifiers. These are test-source descriptions, not independently verified execution results or product documentation.
