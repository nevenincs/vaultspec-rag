## Capability summary

- **Configuration reference — [docs/configuration.md](../../../../docs/configuration.md).** Documents environment-variable and CLI precedence, parsing, defaults, project selection, backend/server provisioning, model and download controls, service and indexing limits, search/update/storage maintenance knobs, optional Typesafe enrollment, and tuning examples. It describes credential and executable trust boundaries as documentation claims (25-79, 80-164, 166-530, 533-586).
- **Retrieval recipes — [docs/examples.md](../../../../docs/examples.md).** Shows vault and code searches, ADR/feature/type filters, path exclusion and language narrowing, and score inspection. It explains that results are ranked passages, tests may match, and search results do not establish complete file coverage or currentness (9-137).
- **First-run workflow — [docs/getting-started.md](../../../../docs/getting-started.md).** Guides an operator through host installation, service startup, asynchronous index submission and job monitoring, initial code search, path filtering, and service shutdown; it links failures to verification and query guidance (5-115).
- **Vocabulary — [docs/glossary.md](../../../../docs/glossary.md).** Defines the product's documented concepts: host/client installs, service and MCP surfaces, content/noise domains, chunks and generations, accelerator/model terms, storage modes, freshness, preprocessing approval, search and watcher behavior (7-189).
- **Pipeline and retrieval internals — [docs/indexing.md](../../../../docs/indexing.md).** Explains documented source admission and ownership routing, chunking and encoding, model placement, vector storage, hybrid search/reranking, worktree vector reuse, incremental/rebuild behavior, watcher behavior, and index-health signals (14-94, 96-186, 188-305, 306-351).
- Across the slice, the documented user-facing capabilities are indexing and searching three content domains (vault, code, extracted documents), serving work through a resident service or command process, filtering/ranking results, and observing jobs/readiness/freshness. This is a synthesis of the documentation, not an implementation finding ([docs/glossary.md:31-33](../../../../docs/glossary.md#L31), [docs/indexing.md:188-228](../../../../docs/indexing.md#L188), [docs/getting-started.md:27-89](../../../../docs/getting-started.md#L27)).

## Interfaces and data flow

- **Configuration inputs:** CLI flags outrank session environment; selected settings also use credential-only workspace .env, persisted configuration, or defaults. Root/log/watchdog have shared-framework fallbacks. Most variables use typed validation; root, preprocessing, watchdog, logging, and Typesafe credentials have call-site-specific behavior. The reference says invalid standard settings make settings construction fail at startup ([docs/configuration.md:25-79](../../../../docs/configuration.md#L25)).
- **Documented command callers:** The tutorial and examples call the vaultspec-rag CLI for server start, index, server jobs --watch, search, and server stop. Index submissions return job IDs and continue after the command returns; search returns passages which can be narrowed by type or exact project-relative path ([docs/getting-started.md:27-101](../../../../docs/getting-started.md#L27); [docs/examples.md:9-106](../../../../docs/examples.md#L9)). Examples assume an indexed project and do not themselves establish runtime success.
- **Documented index inputs and flow:** The indexing guide says vault indexing scans Markdown below .vault/, reads frontmatter/H1, hashes content, and skips unchanged files; code/document discovery uses a shared versioned policy, explicit ownership routes, ignores, and separate code/document fingerprints. Code chunks use parser-aware or structure-aware splitting; extractor-owned document text follows a validated document path. CPU chunk producers feed a bounded queue to one accelerator consumer, and publication waits for durable chunks, deletions, metadata, schema evidence, and generation finalization ([docs/indexing.md:34-94](../../../../docs/indexing.md#L34)).
- **Representations and retrieval:** The guides describe dense and sparse vectors per item and separate vault/code/document collections. Search encodes a query through both channels, fuses candidate lists, then reranks; vault results additionally receive document grouping, graph/intent adjustments, status filtering, and passage selection. Sparse or hybrid failures are documented as falling back to dense retrieval ([docs/indexing.md:16-32, 188-228](../../../../docs/indexing.md#L16)).
- **Service and persistence:** The glossary describes a host installation running a resident HTTP daemon and a same-machine client installation delegating search/index work to it; the stdio MCP shim delegates over the service REST API. The indexing guide describes Qdrant server or embedded local storage, per-root namespaces in server mode, and independent code/document/vault collections. These are documentation descriptions; the service protocol and store code were not inspected ([docs/glossary.md:23-25, 67-73, 151-161, 171-173](../../../../docs/glossary.md#L23); [docs/indexing.md:188-252](../../../../docs/indexing.md#L188)).
- **State and operator feedback:** The docs identify CLI job IDs, status/jobs/doctor surfaces, per-domain freshness/readiness, Typesafe enrollment state, and service health/logs as observable outputs. The tutorial's operator sequence waits for submitted jobs to finish before searching; the indexing guide says ordinary search may read the last published generation while work is active ([docs/getting-started.md:36-52](../../../../docs/getting-started.md#L36); [docs/indexing.md:285-332](../../../../docs/indexing.md#L285); [docs/configuration.md:107-124](../../../../docs/configuration.md#L107)).

## Boundaries and dependencies

- The docs distinguish code, vault, and extracted-document ownership; ignored paths take priority, and directory names or parser availability alone do not establish ownership. Shipped installs are documented as using the conventional source profile, while explicit-only admission is described as a caller-supplied policy ([docs/indexing.md:47-75](../../../../docs/indexing.md#L47)).
- The docs describe accelerator inference on CUDA or Apple MPS, with no CPU placement/fallback; the dense/sparse encoders and reranker have separate loading and toggle behavior. They also describe optional paid Typesafe processing of queries/candidate content when enrolled ([docs/glossary.md:7-13, 35-41](../../../../docs/glossary.md#L7); [docs/indexing.md:96-186](../../../../docs/indexing.md#L96); [docs/configuration.md:80-164](../../../../docs/configuration.md#L80)).
- External/documented dependencies include Qdrant, Hugging Face model downloads, PyTorch/CUDA or MPS, tree-sitter, and optional Typesafe. Their actual dependency declarations, exact call graph, and failure handling are outside this slice ([docs/configuration.md:206-223, 287-329, 509-519](../../../../docs/configuration.md#L206); [docs/indexing.md:36-94, 118-186, 230-251](../../../../docs/indexing.md#L36)).
- Related pages such as installation.md, search-and-index.md, service-mode.md, backends.md, preprocessing-hooks.md, verification.md, and automatic-convergence.md are linked but were not read. Their details remain uninspected.
