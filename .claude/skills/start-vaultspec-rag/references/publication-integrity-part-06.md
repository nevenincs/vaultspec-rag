## Capability summary

- [src/vaultspec_rag/tests/test_code_consumer_progress.py](../../../../src/vaultspec_rag/tests/test_code_consumer_progress.py) exercises consumer progress reporting at two levels: completed files and acknowledged chunk operations. It sets up a deterministic dense encoder and a recording store around the production consumer pipeline (88-155, 216-242). Tests expect file progress only after confirmed writes, expose forward windows and per-bucket encode progress/retry counts (244-589), and account for donor reuse, failed writes, and control unwinding after store return (591-728). Threaded replay tests use a real resume fixture and ledger to cover committed segments, changed digests, malformed/oversized replay, resolved zero-chunk outcomes, and ordered progress publication (738-1121).
- [src/vaultspec_rag/tests/test_code_file_security.py](../../../../src/vaultspec_rag/tests/test_code_file_security.py) sends authenticated POST requests through the HTTP app's `/code-file` route. Its cases expect denial for sensitive targets reached by file or directory aliases (48-101), denial for sensitive caller names that alias safe files (103-119), readable content for safe relative/absolute/normalized/alias paths (122-145), root-relative handling of absolute paths under hidden workspace parents (148-179), and rejection of aliases outside the workspace (181-196).
- [src/vaultspec_rag/tests/test_code_index_symlinks.py](../../../../src/vaultspec_rag/tests/test_code_index_symlinks.py) covers admission, preflight, worker reads, and digests around symlink aliases. Cases expect ignored targets and chained/transformed aliases to stay out of membership (36-68), preflight and workers to reject aliases introduced before or during open (71-128, 173-237), digest paths to reject aliases (131-155, 305-326), and ordinary sources plus symlinked project roots to remain usable (141-171). Additional cases cover safe/outside/missing targets and transformed single/batch processing (239-303).
- [src/vaultspec_rag/tests/test_code_pipeline_retained_ids.py](../../../../src/vaultspec_rag/tests/test_code_pipeline_retained_ids.py) uses local `VaultStore`, generation lifecycle/checkpoint, and a deterministic CPU encoder to exercise resumed identity retention. It covers unchanged, changed, round-trip, and removed sources (175-241); partial edits across batching/path counts and collision cases (243-327); deletion identities versus retained upserts after reopening (329-401); and an unfinished-file upsert prefix (403-442).
- [src/vaultspec_rag/tests/test_code_rebuild_stale_evidence.py](../../../../src/vaultspec_rag/tests/test_code_rebuild_stale_evidence.py) constructs a clean resumed rebuild after an embedding-model change, with local storage, publication evidence, and a deterministic external model boundary (107-207). It expects reconciliation to use the resumed generation's own manifest, preserve old published storage, and publish verified survivor evidence (210-267); deletion failures to preserve evidence, deletion units to stay out of retained lookup, and incremental receipts to retain strict compatibility checks (269-341); full-owner recovery of removed sources and interrupted deletion/prefix cases (343-444); and fail-closed behavior when a present source lacks acknowledged points (447-486).

## Interfaces and data flow

- Progress test setup enters `CodeConsumerPipeline._consume_weighted_slice` directly for isolated slices, supplying `WeightedCodeSlice`, limits, reporter, and a `MemoryProbe` (244-376, 378-457). Its store double observes job progress and confirmed chunk progress at upsert time, then records IDs or raises (124-165). Separate replay cases start the threaded consumer with `_spawn_weighted_consumer`, enqueue producer results or raw segments, join the thread, and inspect job progress, checkpoint ledger state, encoder calls, and exceptions (738-811, 819-947).
- Progress and encoding test inputs include file segments and chunk IDs, replayed `EncodeBucketProgress` boundaries, source digests, and optional donor points. Expected outputs/state include telemetry blocks named `forward` and `encode`, completed-file counts, acknowledged chunk counts, `new_ids`, ledger confirmations, and durable file states (459-589, 613-728, 819-1042).
- Security tests use the route client request body fields `path` and `project_root`; expected JSON is either `content` or an error, with status assertions (63-82, 95-100, 114-145, 170-196).
- Symlink tests create filesystem source/target layouts, call discovery/preflight, chunk/hash, or digest entry points, and inspect membership, admission reason, digest, chunks, and preprocessing status (39-68, 71-155, 239-326).
- Retention and rebuild tests drive local store upserts, checkpoint confirmations, lifecycle reopen/run/publish, then compare live IDs with retained ledger IDs and publication snapshots/proofs (189-241, 265-326, 338-442; 136-207, 210-267).

Details of each integration remain uninspected.
