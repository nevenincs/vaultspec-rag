## Capability summary

- [src/vaultspec_rag/tests/test_qdrant_download_faults.py](../../../../src/vaultspec_rag/tests/test_qdrant_download_faults.py): exercises `download_https` and `_install` against loopback TLS sources, including retry bounds, transfer deadlines, byte caps, disk-write failures, redirect and certificate failures, free-space checks, undelimited bodies, cleanup, preservation of a prior install, and successful subsequent installation. The tests also assert actionable failure reports and retry counts. These are test expectations, not verified implementation guarantees. (145–225, 238–400, 403–489, 492–707, 710–899, 902–1020)
- [src/vaultspec_rag/tests/test_qdrant_executable_hold.py](../../../../src/vaultspec_rag/tests/test_qdrant_executable_hold.py): guards `held_executable` behavior for regular-file eligibility, hashing, path identity, and resistance to replacement during the hash-to-launch window. Windows cases check denied writes/renames and simultaneous readers; Linux cases launch through a held descriptor; other non-Windows cases check that path replacement is detected. (47–225)
- [src/vaultspec_rag/tests/test_qdrant_identity.py](../../../../src/vaultspec_rag/tests/test_qdrant_identity.py): checks identity sidecar write/read and legacy/missing sidecars; attachability gates for readiness, version, storage, endpoint identity; and owner PID start-time witness/classification behavior. (38–265)
- [src/vaultspec_rag/tests/test_qdrant_install.py](../../../../src/vaultspec_rag/tests/test_qdrant_install.py): exercises verified archive installation and replacement, digest and extraction failures, previous-install preservation, interrupt cleanup, symlink handling, Windows in-use reporting, install-state decisions from executable bytes, provisioning lock behavior, concurrent callers, re-planning after waiting, abandoned-file cleanup, and unsupported platform outcomes. (130–433, 436–450, 453–640, 642–914)
- [src/vaultspec_rag/tests/test_qdrant_install_recovery.py](../../../../src/vaultspec_rag/tests/test_qdrant_install_recovery.py): exercises whole `provision` calls over healthy, mismatched, unreadable, or structurally obstructed managed directories; repairs for missing/wrong manifests; recovery after hard-killed child runs; stale staging-file cleanup; and two-start adoption after lock contention. (89–137, 140–264, 266–421, 424–709)
- [src/vaultspec_rag/tests/test_qdrant_load_concurrency.py](../../../../src/vaultspec_rag/tests/test_qdrant_load_concurrency.py): checks positive-integer validation for the collection-load concurrency setting and that the configured value reaches the managed child's native environment. Its docstring says these cases use no process or storage; the test constructs the supervisor and inspects `_child_env`. (24–93)
- [src/vaultspec_rag/tests/test_qdrant_local_client.py](../../../../src/vaultspec_rag/tests/test_qdrant_local_client.py): uses a fresh interpreter to check local-client SQLite sharing-mode configuration and connection cleanup, then statically scans package Python files for direct on-disk `QdrantClient(path=...)` construction outside the designated constructor module. (23–140)

## Boundaries and dependencies

The slice establishes test relationships only. Download/install behavior is observed through `download_https`, `_install`, `provision`, and related imported interfaces; identity and executable-hold suites call their named interfaces; load-concurrency checks the supervisor's generated child environment; local-client tests call `open_local_client` in a fresh process and scan source syntax. These tests depend on loopback TLS/release fixtures, config/environment fixtures, child-process helpers, stand-in executables/releases, and imported package code. Their implementations were not inspected.
