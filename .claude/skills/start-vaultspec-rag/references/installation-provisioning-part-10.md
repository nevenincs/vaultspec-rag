## Capability summary

- [src/vaultspec_rag/tests/test_tool_env_provisioning_hostile.py](../../../../src/vaultspec_rag/tests/test_tool_env_provisioning_hostile.py) defines expectations for a real-uv tool-environment repair cycle using a temporary uv sandbox, locally built stand-in wheels, and a loopback index (1-6, 78-125). It covers recording CUDA index policy in the receipt and classifying it (156-192); in-place repair while the environment or launcher is held and a subsequent package upgrade retaining the accelerated torch build (194-241, 432-493); use of the target environment’s interpreter and refusal of mismatched/foreign targets (245-299, 392-415); resolve, ABI-tag, and offline failures that should preserve or avoid creating an environment (331-390); and Windows-only destructive cases for forced or mismatched replacement (269-329, 495-531). These are test expectations and test docstring claims; they do not establish that uv or the product currently behaves this way.
- [src/vaultspec_rag/tests/test_tool_torch_repair.py](../../../../src/vaultspec_rag/tests/test_tool_torch_repair.py) exercises the repair decision/outcome surface for persistent uv tools: which compute states merit a torch reinstall, handoff and install blocking, target checks, consent, dry-run, release lookup, post-repair verification, receipt durability, and restart guidance (107-195, 196-371, 374-422, 544-635, 860-937). Additional expectations cover recorded extras and fallback package requirements (424-464), rendering handoff details in plain install output (466-542), holder identification and actionable process descriptions (637-679, 722-858), and distinguishing a torch-free install from a GPU-stack install whose torch is missing (682-719).
- [src/vaultspec_rag/tests/test_torch_config.py](../../../../src/vaultspec_rag/tests/test_torch_config.py) specifies test contracts for the torch configuration helpers: classify missing, canonical, customized, and absent project-file states; apply/remove the canonical CUDA 13.0 index/source configuration; reject conflicting TOML shapes; and preserve user content through edits (94-325, 845-1063). It also covers manual snippet validity and consistency with the project’s own pyproject (334-360), scattered TOML/table-proxy shapes (363-517), detection and management of direct torch dependencies across PEP 621, Poetry, PDM, Hatch, and uv declarations (519-838), and BOM/line endings/trailing-newline and inline-table cases (1065-1221).
- [src/vaultspec_rag/tests/test_torch_load_centralized.py](../../../../src/vaultspec_rag/tests/test_torch_load_centralized.py) sets import and runtime expectations around the accelerator gate: local-mode imports and model-free preflights should not load torch/heavy models (34-179); compute modules should not have a module-scope torch import (52-101); resolution should prefer CUDA, select MPS only without CPU fallback, and fail hard when no supported accelerator is available (182-249). It checks half-precision accumulation switch scoping and backend behavior (251-351), the real-interpreter load contract (354-395), and a CUDA-marked configured allocator-fraction expectation (397-411).
- [src/vaultspec_rag/tests/test_torch_pin_single_source.py](../../../../src/vaultspec_rag/tests/test_torch_pin_single_source.py) specifies that a missing or ambiguous lockfile must raise LockedTorchVersionError rather than guess an accelerated torch version (1-25).

## Interfaces and data flow

- The hostile-environment tests construct package wheels and indexes under tmp_path, invoke the uv sandbox harness, inspect installed distributions and receipt text, and pass the product-generated repair steps to the harness (78-155, 156-241, 432-493). Their observable inputs include a tool interpreter path, uv receipt, wheel/index contents, held processes/launchers, and uv command outcomes; assertions inspect return codes, versions, receipt classification, and environment contents. The harness implementation was not inspected.
- Repair tests construct ToolRepairRequest values and invoke repair_tool_torch, \_repair_defective_tool, or related helpers. Their observed outcome fields include action, blocks_install, commands, detail, steps, receipt, and holders (125-195, 300-371, 544-635, 637-679). Several tests replace probes, subprocess calls, receipt classifiers, or process-table data with controlled doubles, while one holder test uses the uv harness (196-269, 300-371, 637-679, 774-858).
- Torch-config tests write TOML to temporary [pyproject.toml](../../../../pyproject.toml) files, call state/dependency/configuration helpers, and inspect action/location/conflict results plus serialized bytes, parsed tables, comments, sibling sections, and line endings (94-325, 687-838, 845-1221). The tests expose expected helper names and result fields, not implementation details.
- Centralized-load tests use fresh Python subprocesses for import/preflight checks and AST inspection for source-level import placement (64-179). Other tests pass synthetic torch-shaped objects to resolver/context helpers, or call the gate against the real interpreter; the CUDA allocator test reads configured state before checking torch’s reported fraction (182-411).
- All five files are test modules marked unit at module or test level, with the allocator-fraction case specifically marked cuda ([src/vaultspec_rag/tests/test_tool_env_provisioning_hostile.py:61](../../../../src/vaultspec_rag/tests/test_tool_env_provisioning_hostile.py#L61); [src/vaultspec_rag/tests/test_tool_torch_repair.py:25](../../../../src/vaultspec_rag/tests/test_tool_torch_repair.py#L25); [src/vaultspec_rag/tests/test_torch_config.py:22](../../../../src/vaultspec_rag/tests/test_torch_config.py#L22); [src/vaultspec_rag/tests/test_torch_load_centralized.py:64-65, 397-400](../../../../src/vaultspec_rag/tests/test_torch_load_centralized.py#L64); [src/vaultspec_rag/tests/test_torch_pin_single_source.py:19](../../../../src/vaultspec_rag/tests/test_torch_pin_single_source.py#L19)).

## Boundaries and dependencies

- These are tests, not production implementations or user-facing documentation. Their docstrings narrate intended guarantees and past regression rationale; treat those passages as claims made by test authors. Assertions specify expected behavior but do not prove the tests pass or that untested callers meet the contract.
- Production dependencies were identified only from imports and references in the assigned source. They were not followed: commands.\_tool_torch; operator_state.\_provisioning, \_environment_probe, \_compute, \_installation, \_models, \_topology; torch_config.\_constants, \_direct_dep, \_index, \_inspect, \_mutate, \_lockfile; \_gpu; and, in the embedded preflight driver, \_job_admission, api, \_public_index, and indexer.\_preprocess_config. Test helpers .\_uv_env_harness and .\_planted_programs, CLI renderers/models, and \_process_probe are also uninspected.
- Thus no claim is made here about implementation internals, production call graphs beyond test call sites, live host state, test outcomes, or behavior hidden behind imports. The “callers” visible here are test call sites and embedded subprocess-driver calls.
