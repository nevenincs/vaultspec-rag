## Capability summary

This slice describes integration coverage for stdio lifetime, storage deletion, scheduled maintenance, storage operations and attribution, archive/restore, and a read-only service survey. All six files are test harnesses; they do not implement these capabilities.

- [src/vaultspec_rag/tests/integration/test_stdio_lifetime_e2e.py](../../../../src/vaultspec_rag/tests/integration/test_stdio_lifetime_e2e.py) exercises a spawned vaultspec_rag.server.main process over line-delimited JSON-RPC. Its scenarios expect an initialize handshake and tool listing before clean EOF exit, service-down guidance from search_vault when the daemon is unreachable, immediate shim cleanup when its pipe-creating client dies, and (on Windows) self-reaping by an orphan after repeated watchdog confirmation rounds. The source’s module docstring calls the surface “five-tool” at lines 3-8, while EXPECTED_TOOLS lists twelve names at lines 34-47 and the test compares the complete returned set with that constant at lines 146-154. Treat the count discrepancy as an unresolved source inconsistency.
- [src/vaultspec_rag/tests/integration/test_storage_delete_addressing.py](../../../../src/vaultspec_rag/tests/integration/test_storage_delete_addressing.py) covers the server storage delete CLI with either a collection prefix or a root path, against a real managed Qdrant server. Expectations include rejecting both/neither address forms, deleting only the namespace registered to a root, treating an absent namespace as success, preserving unattributed data, omitting queried_root for prefix input, and retaining the attributed root in a deletion result for later eviction (lines 128-288).
- [src/vaultspec_rag/tests/integration/test_storage_maintenance.py](../../../../src/vaultspec_rag/tests/integration/test_storage_maintenance.py) stages aged, fresh, and reappearing roots in the manifest, then observes a background service’s scheduled maintenance through /jobs. Its expectations are that an aged empty orphan is removed, a fresh orphan remains within its grace window, a returning root’s orphan timestamp clears, and completed scheduled jobs expose a rollup (lines 84-172).
- [src/vaultspec_rag/tests/integration/test_storage_ops_integration.py](../../../../src/vaultspec_rag/tests/integration/test_storage_ops_integration.py) has several responsibilities:
  - Real-server survey classification and safe delete/prune behavior for live, orphaned, and unknown namespaces; root registration through VaultStore.ensure_table; migration copy, pagination, idempotency, and missing-source reporting; manifest reconciliation and backend re-keying (lines 127-459).
  - Geometry reconciliation expectations: reclaimed disk bytes with point/search preservation, convergence and idempotency, no premature reclaim figures when not awaited, dry-run behavior, and cap/defer behavior (lines 541-783).
  - Ownership guards: invalid or missing manifest attribution, exact collection names, revalidation before optimizer update, direct reconciliation, maintenance reconciliation, and backend mismatch (lines 798-1087).
  - Archive and identity coverage: archive manifest identity, rejection of a write during a multi-collection archive, refusal when a real snapshot artifact is missing, and carry of identity across a migrated collection name (lines 1091-1345).
- [src/vaultspec_rag/tests/integration/test_storage_restore_integration.py](../../../../src/vaultspec_rag/tests/integration/test_storage_restore_integration.py) covers real-Qdrant archive and restore contracts: preview before apply, identity recovery, refusal for local mode or a populated destination, rollback after a later corrupt snapshot, refusal when an archive/member is replaced by a link after validation, and a searchable round trip that expects the same ranked payloads after restore. The source expects a platform-specific refusal on Windows (lines 97-453).
- [src/vaultspec_rag/tests/integration/test_storage_survey_service.py](../../../../src/vaultspec_rag/tests/integration/test_storage_survey_service.py) covers a read-only survey route and a service-client adapter. Assertions expect a bounded response envelope, status/limit/root filters, authoritative root-prefix lookup, freshness metadata, cache reuse and reseeding, and internally consistent collection/backlog/unverified totals (lines 31-405). The module docstring additionally claims coverage of the MCP survey_storage tool and a service-first CLI path (lines 1-8); this file’s visible assertions call the HTTP route and \_try_http_admin("get_storage_survey", ...), with no direct assertion for either named surface.

## Interfaces and data flow

- The stdio tests launch python -c "from vaultspec_rag.server import main; main()", write JSON-RPC requests to stdin, and parse stdout responses. Inputs include initialize, notifications/initialized, tools/list, and a tools/call for search_vault; expected outputs include server identity, a tool-name set, process exit status, and degraded-mode text (lines 49-65, 83-143, 146-210).
- Storage-delete tests invoke the CLI with a prefix or --root, optionally --json and --yes; they inspect exit codes, human output, JSON envelopes, live Qdrant collection names, and deletion-result fields (test file lines 128-288).
- Storage tests create real Qdrant collections and points, register roots and collection identities in the persisted manifest, and compare survey/reconcile/archive/restore results with the resulting server or filesystem state. The test source names the relevant API calls directly: gather_survey, delete_prefix, prune_orphaned, migrate_collections, reconcile_collections, archive_prefix, read_archive, and restore_archive (storage-ops lines 127-1345; restore lines 74-94, 145-172).
- Maintenance and survey service tests address the running service by port. Maintenance polls /jobs; survey calls /storage/survey with root, status, limit, or fresh query parameters, and an indexing setup uses /reindex before querying the survey (maintenance lines 59-81, 100-172; survey lines 31-54, 57-225, 337-405).
- The tests treat the manifest, Qdrant collections/points, snapshot files, and service job records as state that can be inspected after each operation. This describes the test data flow and assertions; it does not establish production ownership or transaction guarantees.

## Boundaries and dependencies

- The slice’s observed responsibility is verification through integration harnesses. Production responsibilities are outside scope. In particular, server startup, JSON-RPC dispatch, watchdog logic, CLI command implementation, survey route handling, Qdrant addressing, manifest rules, reconciliation, archive verification, restore rollback, and identity transfer are imported or invoked but not inspected.
- Exact uninspected production symbols referenced by these tests include server.main; server.\_stdio_lifetime.install_stdio_lifetime_watchdog and its process-snapshot/ancestor helpers; storage_manifest root, identity, snapshot, reconciliation, and removal functions; storage_survey_ops survey/delete/prune functions; storage_reconciliation.read_geometry and reconcile_collection(s); storage_reclamation.run_maintenance_cycle; storage_archive.archive_prefix and \_verify_completed_archive; storage_restore.restore_archive and read_archive; storage_migration.migrate_collections and carry_migrated_identity; storage_identity.record_identity and load_identity; and store_runtime.VaultStore.ensure_table.

The slice intentionally does not infer how these helpers provision processes or isolate state.
- The storage and service tests use real Qdrant servers and persisted state according to their setup code, while stdio tests create child processes. This is a description of the test setup, not a claim that the assigned tests were run.
