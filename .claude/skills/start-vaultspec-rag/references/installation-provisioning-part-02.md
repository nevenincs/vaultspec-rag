## Capability summary

- [docs/installation.md](../../../../docs/installation.md) is the end-to-end installation and operations guide. It explains the host/client split, supported GPU and Python platforms, standalone-tool, project-dependency, and prebuilt-binary routes, per-repository setup, MCP enrollment, model and Qdrant provisioning, service checks, clients, coordinated upgrades, troubleshooting, uninstall, and archive/platform details. It distinguishes host packages that can run inference and start the service from model-free clients that call a same-user service and must match its release. Its appendices describe package extras and archive contents. (Documentation claims: 18–55, 57–92, 138–220, 340–442, 446–680, 682–1028, 1055–1125.)
- [docs/mcp.md](../../../../docs/mcp.md) explains the stdio MCP adapter and its client configuration. It documents twelve tools: six read tools (`search_vault`, `search_codebase`, `search_documents`, `search_combined`, `get_code_file`, `get_index_status`) and six mutation tools (four reindex operations and two clean operations). It covers read-only tool withholding, the project-root environment, manually configured Claude Desktop/Code clients, troubleshooting, and process lifetime. (Documentation claims: 19–71, 73–139, 141–245, 246–330.)
- [docs/preprocessing-hooks.md](../../../../docs/preprocessing-hooks.md) specifies project-owned extraction hooks for files routed explicitly to the `code` or `document` index domain. It documents versioned rule configuration, approval and revocation, single-file commands or entry points, an invocation envelope, a validated JSON output contract, optional batches, extraction caching, incremental and watcher behavior, surfaced success/failure counts, bounds, and security properties. It also gives project-side extractor sketches, explicitly labeled as examples that are not shipped dependencies. (Documentation claims: 1–35, 37–178, 180–245, 246–395, 397–477, 479–525.)

## Interfaces and data flow

- Installation documentation presents `vaultspec-rag install` as repository setup: it may configure an assistant integration, create `.vault/`, adjust PyTorch configuration when applicable, and provision models/Qdrant according to host readiness, backend choice, and flags. Host `server start` is described as fetching missing selected-backend assets, loading models, and waiting for readiness; `server status`, `server doctor`, and repository `status` report different service, installation-readiness, and index questions. Install/uninstall JSON and provisioning step fields are documented. (Documentation claims: [docs/installation.md:340-442](../../../../docs/installation.md#L340), `446-495`.)
- The documented host/client interface requires the same OS user and exact service/client release. A client installation has no GPU or model stack and routes commands to the host service; clients cannot start or upgrade that service. (Documentation claims: [docs/installation.md:20-55](../../../../docs/installation.md#L20), `497-579`, `581-680`, `1057-1077`.)
- The MCP launch interface is stdio: the assistant starts `vaultspec-search-mcp` (or the documented `uvx`/`uv` module forms); the child resolves its project root from `VAULTSPEC_RAG_ROOT`, falling back to `VAULTSPEC_TARGET_DIR`, then forwards calls to the HTTP service with that root. The docs say the service itself exposes REST rather than MCP, and MCP does not load models. `--read-only` withholds mutation tool schemas. (Documentation claims: [docs/mcp.md:73-89](../../../../docs/mcp.md#L73), `91-139`, `141-188`.)
- Hook configuration is a project-root `.vaultragpreprocess.toml`. After explicit approval, a matching file is sent to the configured subprocess; an extractor reads the documented invocation JSON from `VAULTSPEC_PREPROCESS_INVOCATION` and emits one output object, or an array for a batch. The indexer validates and routes extracted text to the declared domain, preserving optional units, anchors, locators, and metadata. Search is documented to return source paths with anchors rather than line numbers for these chunks. (Documentation claims: [docs/preprocessing-hooks.md:19-35](../../../../docs/preprocessing-hooks.md#L19), `45-111`, `154-179`, `180-245`, `255-299`.)
- Hook results are documented as cached per file using source identity/content and an execution fingerprint; only successful results are cached. Index, job, log, and reindex response surfaces expose preprocessing success/failure counts or hook preflight state. Watcher changes to a matching file use the same extraction route. These are documentation claims; the backing response schemas and persistence implementation were not inspected. (Documentation claims: [docs/preprocessing-hooks.md:325-356](../../../../docs/preprocessing-hooks.md#L325), `358-386`.)
- Storage and integrations named by the guides include the `.vault/` folder for local-only index data, shared managed Qdrant storage, the Hugging Face model cache, service data under `~/.vaultspec-rag`, PyTorch/CUDA or MPS, and assistant MCP configuration. Their implementation details are outside this slice. (Documentation claims: [docs/installation.md:63-89](../../../../docs/installation.md#L63), `113-133`, `378-406`, `986-1028`, [docs/mcp.md:19-52](../../../../docs/mcp.md#L19), [docs/preprocessing-hooks.md:332-344](../../../../docs/preprocessing-hooks.md#L332), `425-426`.)

## Boundaries and dependencies

- The docs assign inference and service startup to a GPU-capable host. Client packages are described as model-free request forwarders; the service is loopback-only and is not a documented cross-machine deployment. A remote Qdrant URL does not remove the host GPU requirement. (Documentation claims: [docs/installation.md:20-30](../../../../docs/installation.md#L20), `497-579`, `1057-1077`.)
- The MCP adapter is documented as a stdio child process; service administration remains in the `server` CLI, and the HTTP service is not an MCP endpoint. The adapter forwards requests and tags each with its resolved project root. (Documentation claims: [docs/mcp.md:73-89](../../../../docs/mcp.md#L73), `137-139`.)
- Preprocessing rules explicitly choose one owning domain; parser capability alone does not admit a file as code. `.gitignore` and `.vaultragignore` exclusion wins over a matching preprocess rule. The documented rule runner has no sandbox: approval is consent to execute the rule with service-account privileges. Documentation separately claims credential stripping and process/time/output bounds, but says these are not a security boundary. (Documentation claims: [docs/preprocessing-hooks.md:33-43](../../../../docs/preprocessing-hooks.md#L33), `397-468`, `470-477`.)
- The docs point to additional guides (`configuration.md`, `service-mode.md`, `backends.md`, `cli.md`, `search-and-index.md`, among others), but those files and their linked implementation are uninspected and are not treated as corroborating evidence. The example extractor dependencies are project-side examples, not dependencies shipped by vaultspec-rag. (Documentation claims: [docs/installation.md:1030-1053](../../../../docs/installation.md#L1030), [docs/preprocessing-hooks.md:479-525](../../../../docs/preprocessing-hooks.md#L479).)
- Inference: repository setup appears to bridge package installation and project integration, while MCP and preprocessing are separate request/extraction interfaces into indexing and service functionality. This is inferred only from how the three guides describe their respective workflows; no call graph was inspected.
