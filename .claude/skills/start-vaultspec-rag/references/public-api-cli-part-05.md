## Capability summary

These four unit-marked modules specify expected behavior for a Textual server-watch interface in rendered frames and against a controlled service fixture. The assertions chiefly exercise application behavior through `run_test`, key presses, direct action calls, and explicit result application; module and test docstrings explain the scenarios and claimed regression mechanisms but are not independent evidence that those mechanisms were reproduced here.

- [src/vaultspec_rag/tests/test_cli_jobs_tui.py](../../../../src/vaultspec_rag/tests/test_cli_jobs_tui.py) covers the jobs view: visible project path, elapsed/remaining time and progress sizing; wide/narrow table and log composition; idle versus active animation; selection and pending-state reconciliation as jobs change; ETA unknown/absent distinctions and countdown refresh; and teardown of timers and late job/log answers. The late-result cases explicitly call private application methods as well as driving the Textual session.
- [src/vaultspec_rag/tests/test_cli_jobs_tui_controls.py](../../../../src/vaultspec_rag/tests/test_cli_jobs_tui_controls.py) covers permission gating and disabled-action feedback; requested, sent, confirmed, and refused control states; service-visible deletion and other action outcomes; refresh/control worker independence; and protection against a pre-control poll settling a newer request.
- [src/vaultspec_rag/tests/test_cli_jobs_tui_header.py](../../../../src/vaultspec_rag/tests/test_cli_jobs_tui_header.py) covers service-error retention and stale-payload ordering; total and per-state counts; health, degradation, GPU, pressure, and quiesce indicators; daemon identity/version; pill rendering, color-theme switching, and older-service compatibility for missing versus null fields and capabilities.
- [src/vaultspec_rag/tests/test_cli_jobs_tui_lanes.py](../../../../src/vaultspec_rag/tests/test_cli_jobs_tui_lanes.py) covers per-job log selection; jobs and served-search lanes at wide and narrow sizes; lane focus and guards against job controls acting on retained/hidden selections; global log access; redacted-query payload validation/rendering; and disclosure when the served search projection is shorter than its total.

## Interfaces and data flow

The tests create an app either through the imported `_app` harness helper or, in focused cases, directly as `ServerWatchApp`; they enter `app.run_test(...)`, send keys through Textual's pilot, and inspect `_screen_text`, row/header helpers, classes, selected IDs, or other named app fields. They also invoke actions such as `action_job_delete` directly to cover paths that bypass key bindings. These are test call sites, not a traced production caller graph.

`_JobService` is the fixture interface used by the tests. The visible calls configure job lists, search activity, GPU/pressure/quiesce payloads, and event gates; assertions inspect recorded requests, paths, and service-held jobs. The core and header suites import `_try_http_admin` and use it for explicit job/log fetch answers. The tests therefore intend to compare rendered UI with service-held or service-returned state. The harness and transport implementations were not inspected, so their internal data flow and guarantees remain unknown.

The observed UI inputs include job payload shapes, search records, service status fields, terminal size, keyboard focus, and asynchronous request timing. Observed outputs are painted text/cells, app state accessed by tests, and recorded fixture requests/state. No persistent storage is exercised or established by these files. Search activity is treated as a separate lane from raw logs by assertions in the dual-lane tests.
