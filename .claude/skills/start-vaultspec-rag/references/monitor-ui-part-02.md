## Capability summary

- `index.html` supplies the local monitor document shell, favicon, title, root element, and `/main.tsx` entry. [src/monitor/main.tsx](../../../../src/monitor/main.tsx) loads the React app and styles, verifies the root exists, and renders `App` in `StrictMode`.
- [src/monitor/App.tsx](../../../../src/monitor/App.tsx) is the monitor shell and page router. It provides hash navigation for Dashboard, Index Requests, Queries, Repositories, Storage, Clients, Performance, and Logs; responsive navigation; light/system/dark theme selection persisted in local storage; manual refresh and live-update pause; service status and observation freshness; and route-level composition of health, work, inventory, logs, and runtime views. It polls health and, on relevant pages, lifecycle, runtime observations, jobs, and search activity.
- [src/monitor/use-polling.ts](../../../../src/monitor/use-polling.ts) owns one scoped polling observation per hook. It avoids overlapping requests, skips polling while the document is hidden, aborts on hidden state or scope cleanup, supports explicit refresh and interval/timeout inputs, and retains same-path data when recording a later error. The UI can therefore show prior data alongside a stale/error indication.
- [src/monitor/model.ts](../../../../src/monitor/model.ts) defines work/log payload shapes and shared decoding/display/request helpers. It extracts the monitor capability from the URL fragment into session storage, sends authenticated no-store JSON requests through `/api/monitor`, validates health, jobs, serving activity, and bounded log groups, creates log URLs, sanitizes terminal controls in logs, and formats values, timestamps, job progress, roots, and initiators.
- [src/monitor/Health.tsx](../../../../src/monitor/Health.tsx) renders CPU, RAM, GPU-memory, and disk meters; formats byte readings; and presents service, model/integration, admission, and capacity details from health/runtime payloads. [src/monitor/presentation.tsx](../../../../src/monitor/presentation.tsx) maps states to status indicators and provides shared property tables and count metrics.
- [src/monitor/DataTree.tsx](../../../../src/monitor/DataTree.tsx) renders nested records and arrays as expandable tables, with per-table sorting and field-path expansion state. It is reused for runtime, inventory, logs, request parameters/results, and diagnostics.
- [src/monitor/Work.tsx](../../../../src/monitor/Work.tsx) presents indexing jobs and search requests with status metrics, filters, responsive desktop/mobile layouts, expandable request details, pagination, and per-record job controls/logs. [src/monitor/RequestDetails.tsx](../../../../src/monitor/RequestDetails.tsx) displays request summaries, progress or query text, failures, results, input parameters, timing, and diagnostics. [src/monitor/JobControls.tsx](../../../../src/monitor/JobControls.tsx) exposes pause/resume/stop/retry/delete only when record capability flags allow them; it supplies expected revisions for state changes, asks for delete confirmation, aborts its pending request on unmount, and refreshes after completion. [src/monitor/ListFilters.tsx](../../../../src/monitor/ListFilters.tsx) supplies reusable search, status, sort, and order controls that reset the page when changed.
- [src/monitor/Logs.tsx](../../../../src/monitor/Logs.tsx) displays service/Qdrant logs or a selected job/query's service logs, with message search, source selection for global logs, order and page-size controls, pagination, truncation notices, and `Evidence` status messaging for loading, paused, or stale observations.
- [src/monitor/Inventory.tsx](../../../../src/monitor/Inventory.tsx) displays repositories/worktrees or storage namespaces from bounded inventory requests. It filters rows, exposes service-seat and storage detail trees, charts storage footprint, distinguishes unavailable live usage, offers storage refresh and repository enrollment, and provides a resident-seat release action. Mutations report feedback and trigger refresh.
- [src/monitor/ServiceControls.tsx](../../../../src/monitor/ServiceControls.tsx) exposes start, pause, resume, and confirmed stop actions based on health/lifecycle state; it reports pending/results and refreshes after action completion.
- `server/local-service.ts` is the local API bridge. It issues a per-process capability link, restricts access to loopback clients and matching local hosts/origins, authenticates bearer requests, allows only monitor routes/methods, bounds request/response sizes and durations, forwards requests to the discovered local service with its service token, redacts sensitive fields from replies, routes lifecycle controls through the owner CLI, and falls back to owner-CLI persisted inventory when live inventory forwarding fails.
- `server/standalone.ts` starts the embedded monitor HTTP server, validates CLI options, binds on loopback (allowing managed port selection above the preferred port), serves embedded assets and build metadata, supports GET/HEAD, handles termination, and prints the capability-bearing access link. `server/vite-plugin.ts` installs the same monitor middleware and upgrade check for Vite dev and preview servers and announces the access link.
- [src/monitor/monitor.scss](../../../../src/monitor/monitor.scss) styles the monitor’s layout, tables, tiles, status/detail views, navigation, charts, controls, and responsive mobile layouts; it also includes reduced-motion behavior and focus/overflow handling.

## Interfaces and data flow

- Entry/data path: `index.html` → [src/monitor/main.tsx](../../../../src/monitor/main.tsx) → `App`. UI state and page selection live in React state; the theme preference is persisted as `monitor-theme`, and the monitor capability is held as `monitor-capability` in session storage after extraction from `#capability=...` ([src/monitor/model.ts:95-108](../../../../src/monitor/model.ts#L95)).
- Browser requests go through `request()` to `/api/monitor${path}` with JSON content type, `Authorization: Bearer …`, no-store cache behavior, abort/timeout support, JSON-object validation, and bounded error messages ([src/monitor/model.ts:110-140](../../../../src/monitor/model.ts#L110)). `usePolling` supplies GET observations and decoders; action components call the same request helper with POST/PUT/DELETE ([src/monitor/JobControls.tsx:24-79](../../../../src/monitor/JobControls.tsx#L24), [src/monitor/ServiceControls.tsx:36-49](../../../../src/monitor/ServiceControls.tsx#L36), [src/monitor/Inventory.tsx:99-107](../../../../src/monitor/Inventory.tsx#L99)).
- `App` polls `/health` continuously while live updates are enabled; `/lifecycle` is enabled when health errors; `/runtime-observations` is enabled on dashboard/performance/clients when service is reachable; `/jobs` and `/search-activity` are page-scoped and use query parameters from list options ([src/monitor/App.tsx:132-209](../../../../src/monitor/App.tsx#L132)). The `Observation` shape carries optional `data`, `observedAt`, and `error` ([src/monitor/use-polling.ts:4-5](../../../../src/monitor/use-polling.ts#L4)).
- Work-list requests decode into `Jobs` or `Activity`; the UI consumes `records`, counts/summary, and matched totals. Query activity validation checks lane state, query disclosure/redaction consistency, unique request identities, and summary counts ([src/monitor/model.ts:149-213](../../../../src/monitor/model.ts#L149)). Logs are requested from `/logs/json` with source, lines, offset, order, optional work ID and text filter; decoding checks response scope and content/truncation bounds ([src/monitor/model.ts:215-311](../../../../src/monitor/model.ts#L215)).
- Inventory reads `/repositories?limit=200` or `/storage/survey?limit=200`; actions POST to `/repositories/enroll`, `/projects/evict`, or a fresh storage survey ([src/monitor/Inventory.tsx:49-56](../../../../src/monitor/Inventory.tsx#L49), `99-126`, `184-195`). Job controls call `/jobs/{id}/desired-state`, `/jobs/{id}/retry`, and DELETE `/jobs/{id}` ([src/monitor/JobControls.tsx:51-79](../../../../src/monitor/JobControls.tsx#L51)). Service controls POST to `/lifecycle/start`, `/lifecycle/stop`, `/pause`, or `/resume` ([src/monitor/ServiceControls.tsx:43-49](../../../../src/monitor/ServiceControls.tsx#L43)).
- The bridge strips `/api/monitor`, checks an explicit allowlist, parses bounded request bodies, and forwards permitted non-lifecycle requests to `http://127.0.0.1:{port}` using credentials read from the service discovery record/environment; a 401 can trigger one token refresh and retry ([src/monitor/server/local-service.ts:79-118](../../../../src/monitor/server/local-service.ts#L79), `182-212`, `403-482`). Lifecycle requests run the local owner command and inventory fallback uses its inventory command ([src/monitor/server/local-service.ts:342-387](../../../../src/monitor/server/local-service.ts#L342), `420-459`, `491-505`). The static server and Vite plugin attach this middleware ([src/monitor/server/standalone.ts:112-125](../../../../src/monitor/server/standalone.ts#L112), [src/monitor/server/vite-plugin.ts:16-29](../../../../src/monitor/server/vite-plugin.ts#L16)).
- Persistent data semantics are outside this source slice. In the inspected monitor code, browser storage is limited to the theme preference and capability session value; inventory/work/log payloads are observations rendered by the UI, not locally written records.

## Boundaries and dependencies

- The frontend is coupled to the local bridge’s `/api/monitor` path and the route names/shapes validated in [src/monitor/model.ts](../../../../src/monitor/model.ts). The bridge’s own allowlist is explicit; local-service APIs beyond it are not exposed by this middleware ([src/monitor/server/local-service.ts:182-212](../../../../src/monitor/server/local-service.ts#L182)). The bridge delegates ordinary data/action semantics to the local service, while lifecycle and offline inventory behavior are separately delegated to the CLI owner ([src/monitor/server/local-service.ts:342-387](../../../../src/monitor/server/local-service.ts#L342), `403-505`).
- Standalone and Vite hosting share `monitorMiddleware`, `monitorUpgrade`, and `monitorAccess`; their asset and development-server responsibilities differ ([src/monitor/server/standalone.ts:99-169](../../../../src/monitor/server/standalone.ts#L99), [src/monitor/server/vite-plugin.ts:16-29](../../../../src/monitor/server/vite-plugin.ts#L16)).
- Local component relationships are within this slice: `App` composes view modules; `Work` composes filters, details, job controls, and logs; `Inventory` and `RequestDetails` reuse `DataTree`; health, inventory, and request details reuse shared model formatters. External library behavior and upstream service/CLI contracts were not inspected, so claims here describe only the monitor code’s declared requests, validation, and UI handling.
