## Interfaces and data flow

- CLI search accepts vault, code, document, or combined source selection. The search guide says the default combines source code with ADRs, while explicit vault and combined modes widen the selected records; aliases include `docs`, `codebase`, and `all`. Filters apply only to compatible domains, and incompatible filters are usage errors ([docs/query-craft.md:65-110](../../../../docs/query-craft.md#L65); [docs/search-and-index.md:22-31,65-77](../../../../docs/search-and-index.md#L22)).
- Documented search inputs include query text, CLI flags, and inline markers. Code controls include path/glob, language, structure, symbol, preference, noise-domain, and locale filters; vault controls include type, feature, date, tag, status, and intent; extracted-document controls include source path, extractor id/version, and locator kind ([docs/query-craft.md:78-143](../../../../docs/query-craft.md#L78); [docs/search-and-index.md:184-250,254-346](../../../../docs/search-and-index.md#L184)).
- The documented result path is CLI or HTTP/MCP request to one or more selected indexes, followed by ranked records with file locations and matching passages. Search output may include scores and readiness facts. Availability and freshness are separate response axes; an empty result is authoritative only when absence authority is established for every requested source. Combined responses preserve each source outcome and can mark a useful partial result ([docs/search-and-index.md:33-37,79-115,117-152](../../../../docs/search-and-index.md#L33)).
- Search and index commands use a running service when detected; index work is handed to it in the background, otherwise indexing runs in the current process. The documented service routes use fixed source names on `POST /search`, `POST /reindex`, and `POST /clean`; `GET /readiness` reports per-domain health and counts. MCP exposes the same operations, with typed freshness inputs passed through and canonical outcomes retained ([docs/search-and-index.md:154-182,354-390](../../../../docs/search-and-index.md#L154)).
- The provisioning sequence for host `server start` is documented as environment eligibility and port/ownership checks, model fetch and validation, managed Qdrant verification/provisioning, then service launch and model loading. The service itself loads from cache and does not download. `--local-only` uses the on-disk store and skips the managed Qdrant binary; an operator-supplied executable is selected by paired environment variables and is checked against the operator's digest ([docs/provisioning.md:60-76,97-126,227-251,326-339](../../../../docs/provisioning.md#L60); [docs/service-mode.md:16-46](../../../../docs/service-mode.md#L16)).
- Documented state locations are: model repositories in the Hugging Face `hub` cache under `HF_HOME`; managed Qdrant executable/manifest under the status directory's `bin/qdrant/<version>/`; the machine lock and canonical discovery pointer beside machine-global Qdrant storage; and a compatibility/operator discovery file at `{status_dir}/service.json`. The status directory defaults to `~/.vaultspec-rag`; the machine pointer defaults under `~/.vaultspec-rag/qdrant-server/` ([docs/provisioning.md:197-207,253-339](../../../../docs/provisioning.md#L197); [docs/service-discovery.md:159-188](../../../../docs/service-discovery.md#L159)).
- Discovery consumers are the CLI, MCP server, and supervising brokers. The documented resolution order probes the machine lock, reads the pointer (using status-file fallback only without a live lock), validates schema/version and freshness, then checks pointer PID against the lock holder. Authenticated daemon routes use the discovery service token; the monitor uses a separate link capability ([docs/service-discovery.md:1-29,31-46,120-155](../../../../docs/service-discovery.md#L1); [docs/service-mode.md:233-330,451-465](../../../../docs/service-mode.md#L233)).
- Operator workflows include status/doctor, job and log inspection, job/service controls, project listing/unloading, updates controls, Qdrant provisioning, and non-destructive discovery reconciliation. These are documented command surfaces, not verified callable interfaces ([docs/service-mode.md:70-166,186-231,351-449](../../../../docs/service-mode.md#L70); [docs/service-discovery.md:190-221](../../../../docs/service-discovery.md#L190)).

## Boundaries and dependencies

- The documents describe three content domains (vault, code, extracted documents) and two service storage modes (managed server and local-only). They describe model and Qdrant provisioning as separate prerequisites, with local-only removing the managed-server requirement ([docs/search-and-index.md:3-7,65-77,354-365](../../../../docs/search-and-index.md#L3); [docs/service-mode.md:3-10,26-46](../../../../docs/service-mode.md#L3); [docs/provisioning.md:27-58,390-393](../../../../docs/provisioning.md#L27)).
- The daemon is documented as a machine singleton protected by an OS advisory lock. A live lock establishes ownership; discovery records carry address evidence. A degraded resolution must not be rendered as stopped, replaced by fallback status-file address, or used to start a second daemon. Reconcile waits for the owner to republish and does not terminate or restart it ([docs/service-discovery.md:19-29,120-145,159-188,211-221](../../../../docs/service-discovery.md#L19)).
- The guides link to [docs/configuration.md](../../../../docs/configuration.md) for settings and source selection, [docs/cli.md](../../../../docs/cli.md) for full flags and schemas, [docs/installation.md](../../../../docs/installation.md) for host/client setup, [docs/backends.md](../../../../docs/backends.md) for backend behavior, and [docs/mcp.md](../../../../docs/mcp.md) for MCP details. These linked files were not in scope, so their details are not established here ([docs/provisioning.md:10-13,503-509](../../../../docs/provisioning.md#L10); [docs/query-craft.md:168-194](../../../../docs/query-craft.md#L168); [docs/search-and-index.md:7-11,350-365,419-427](../../../../docs/search-and-index.md#L7); [docs/service-discovery.md:223-230](../../../../docs/service-discovery.md#L223); [docs/service-mode.md:10-14,166,465-475,526-536](../../../../docs/service-mode.md#L10)).
- The assigned docs do not identify implementation module paths for the commands, resolver, service routes, storage adapters, or provisioning routines. No code-level dependency or caller beyond the documented surfaces can be confirmed. Source implementation and test coverage remain unverified.
- Documentation ambiguity: [docs/service-mode.md](../../../../docs/service-mode.md) calls `GET /health` ungated and says it also returns the service token, while [docs/service-discovery.md](../../../../docs/service-discovery.md) says unauthenticated `/health` omits `service_token`. These statements may describe conditional response fields, but the assigned text does not resolve the condition ([docs/service-mode.md:451-463](../../../../docs/service-mode.md#L451); [docs/service-discovery.md:155-157](../../../../docs/service-discovery.md#L155)).
