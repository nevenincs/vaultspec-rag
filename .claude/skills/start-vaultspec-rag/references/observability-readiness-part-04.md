## Capability summary

This package defines typed operator-facing state, probe logic, environment classifications, and remediation text/commands. Its package initializer says verdicts are owned by enums, service/client roles differ, CLI/MCP render the state, and the package exports no names itself; these are documentation claims, while the inspected modules implement the enums and helpers ([src/vaultspec_rag/operator_state/__init__.py:1-12](../../../../src/vaultspec_rag/operator_state/__init__.py#L1)).

- [src/vaultspec_rag/operator_state/__init__.py](../../../../src/vaultspec_rag/operator_state/__init__.py): package-level design description; no exports or executable behavior in the assigned lines.
- [src/vaultspec_rag/operator_state/\_compute.py](../../../../src/vaultspec_rag/operator_state/_compute.py): classifies installation role and compute capability from package metadata, optionally imports torch at verify depth, classifies an imported torch module, and emits a JSON-compatible self-report.
- [src/vaultspec_rag/operator_state/\_environment_probe.py](../../../../src/vaultspec_rag/operator_state/_environment_probe.py): starts a named interpreter in a child process to obtain that report, applies metadata/verify timeouts, parses its output, and turns missing, timed-out, failed, or malformed responses into typed facts.
- [src/vaultspec_rag/operator_state/\_features.py](../../../../src/vaultspec_rag/operator_state/_features.py): defines service-wide Typesafe states and per-root preprocessing-hook states, with operator labels, enablement, and remediation strings.
- [src/vaultspec_rag/operator_state/\_hardware.py](../../../../src/vaultspec_rag/operator_state/_hardware.py): caches a per-process hardware reading; classifies macOS Apple silicon or queries NVIDIA hardware using a bounded `nvidia-smi` invocation.
- [src/vaultspec_rag/operator_state/\_holders.py](../../../../src/vaultspec_rag/operator_state/_holders.py): classifies already-gathered environment-holder records, renders local human-readable lines, and serializes a bounded holder list without command lines.
- [src/vaultspec_rag/operator_state/\_installation.py](../../../../src/vaultspec_rag/operator_state/_installation.py): defines installation-role, hardware-presence, and compute-capability enums, plus labels, remediation, start-blocking, torch-reinstall, and defect predicates.
- [src/vaultspec_rag/operator_state/\_models.py](../../../../src/vaultspec_rag/operator_state/_models.py): defines frozen Pydantic wire models for hardware, compute, installation, degradation, feature, health, and service-state reports; unknown fields are forbidden.
- [src/vaultspec_rag/operator_state/\_provisioning.py](../../../../src/vaultspec_rag/operator_state/_provisioning.py): classifies CUDA wheel/platform and runtime-environment options, reads uv receipts and environment metadata, judges whether tool upgrades retain a CUDA source, and constructs repair/upgrade instructions and commands. It does not execute those commands in the inspected code.
- [src/vaultspec_rag/operator_state/\_service.py](../../../../src/vaultspec_rag/operator_state/_service.py): defines lifecycle and health/degradation vocabularies, broker exit codes, labels, and lifecycle remediation.
- [src/vaultspec_rag/operator_state/\_service_environment.py](../../../../src/vaultspec_rag/operator_state/_service_environment.py): combines installation role with a supplied or child-probed compute result to decide whether an interpreter can run the service.
- [src/vaultspec_rag/operator_state/\_topology.py](../../../../src/vaultspec_rag/operator_state/_topology.py): derives an interpreter's environment root and classifies it as uv tool, uvx ephemeral, project venv, or other based on paths, receipt presence, and environment variables.

## Interfaces and data flow

The module-level APIs are defined in each file's `__all__`; the package itself exports nothing. The main compute path is `installed_role()` / `metadata_verdict()` → `local_compute(depth)` → `environment_report(depth)` ([src/vaultspec_rag/operator_state/\_compute.py:27-35,52-79,142-177](../../../../src/vaultspec_rag/operator_state/_compute.py#L27)). Metadata depth uses installed distribution versions; verify depth can import torch and call `resolve_accelerator`. A torch import failure is represented as `TORCH_IMPORT_FAILED`; successful classification returns backend/device/memory information in `ComputeReport` ([src/vaultspec_rag/operator_state/\_compute.py:100-139,148-165](../../../../src/vaultspec_rag/operator_state/_compute.py#L100)).

For a remote target interpreter, `probe_interpreter` invokes an inline child script and parses the final stdout line into `InterpreterFacts`; the timeout defaults are 15 seconds for metadata and 60 seconds for verify ([src/vaultspec_rag/operator_state/\_environment_probe.py:28-37,40-89,92-130](../../../../src/vaultspec_rag/operator_state/_environment_probe.py#L28)). Failures yield typed facts instead of being propagated. `judge_service_environment` defaults to the current executable, returns not-applicable when the current process's installed role is client, accepts an earlier compute verdict, or probes the named interpreter ([src/vaultspec_rag/operator_state/\_service_environment.py:64-95](../../../../src/vaultspec_rag/operator_state/_service_environment.py#L64)). This distinction is based on the code: the role check calls `_compute.installed_role()` in the current process, while the compute probe receives `judged`.

Hardware state is independent of torch state: `read_hardware` locates `nvidia-smi`, caches `query_hardware` output, and returns a `HardwareReading` ([src/vaultspec_rag/operator_state/\_hardware.py:34-49,52-101](../../../../src/vaultspec_rag/operator_state/_hardware.py#L34)). Holder input is an `EnvironmentHolder` sequence supplied by the process-probe subsystem; output is either bounded wire data or local lines with role/remediation and shortened command line ([src/vaultspec_rag/operator_state/\_holders.py:90-120,123-189](../../../../src/vaultspec_rag/operator_state/_holders.py#L90)).

The Pydantic models combine these enums and readings into reports. `HealthReport` includes health, degradation, features, process/interpreter metadata, and subsystem-owned mappings; `ServiceStateReport` starts with installation/root-feature and subsystem mappings ([src/vaultspec_rag/operator_state/\_models.py:36-38,40-154](../../../../src/vaultspec_rag/operator_state/_models.py#L36)). The visible model fields include raw `service_token` as optional health data, so the excerpt establishes that the field exists but does not establish how any route handles it.

Provisioning flow is primarily pure classification and command construction: topology selects the environment kind; `cuda_remediation` then chooses Metal, unsupported-platform, project/other, ephemeral, or tool instructions ([src/vaultspec_rag/operator_state/\_topology.py:91-114](../../../../src/vaultspec_rag/operator_state/_topology.py#L91); [src/vaultspec_rag/operator_state/\_provisioning.py:194-213,648-782](../../../../src/vaultspec_rag/operator_state/_provisioning.py#L194)). For tool environments, receipt parsing and classification determine whether upgrade instructions first record the CUDA source; command helpers return argument tuples or rendered strings ([src/vaultspec_rag/operator_state/\_provisioning.py:181-191,303-320,550-645](../../../../src/vaultspec_rag/operator_state/_provisioning.py#L181)). No command execution is shown in these ranges.
