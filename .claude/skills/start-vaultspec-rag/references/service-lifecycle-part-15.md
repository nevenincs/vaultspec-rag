## Capability summary

- [src/vaultspec_rag/tests/test_service_quiesce_controller.py](../../../../src/vaultspec_rag/tests/test_service_quiesce_controller.py) exercises the controller contract: pause closes admission, outstanding compute tickets drain, GPU release acknowledgement reaches quiesced, warming and resume reopen a later epoch; it also covers idempotence, timeout behavior, pause abort, valid failure codes, stale/wrong-state failures, and the published envelope vocabulary (27-350). These are expectations encoded by tests, not implementation findings.
- [src/vaultspec_rag/tests/test_service_registry_quiesce_transitions.py](../../../../src/vaultspec_rag/tests/test_service_registry_quiesce_transitions.py) covers registry-level ownership of pause/resume resource transitions: same-direction callers share an outcome, opposite directions conflict, follower waits are bounded, drain timeout can be recovered, aborting a stranded pause avoids waiting for the held GPU lock, an idle pause should not import torch, and resume persistence failure should keep admission closed until repair (49-398).
- [src/vaultspec_rag/tests/test_service_quiesce_routes.py](../../../../src/vaultspec_rag/tests/test_service_quiesce_routes.py) covers authenticated loopback pause/resume responses, controller-envelope shape, refusal/conflict messages, a joined pause wait timeout, and recovery of a paused durable job after persistence repair (91-413). Separate cases assert that operator-facing failure text names closed admission and remedies and that the drain budget fits its caller (414-495).
- [src/vaultspec_rag/tests/test_service_quiesce_cli.py](../../../../src/vaultspec_rag/tests/test_service_quiesce_cli.py) checks `server pause` and `server resume` JSON outcomes against a production-service fixture: successful and repeated transitions, a resume conflict while pause is pending, unreachable service, and one JSON output line (36-180).
- [src/vaultspec_rag/tests/test_service_quiesce_adapters.py](../../../../src/vaultspec_rag/tests/test_service_quiesce_adapters.py) checks the snapshot/envelope key contract, an MCP service-state probe through discovery and authenticated HTTP, and a Textual jobs view retaining controller facts or showing quiesce unavailable after a route error (31-315).
- [src/vaultspec_rag/tests/test_service_registry.py](../../../../src/vaultspec_rag/tests/test_service_registry.py) covers broader registry responsibilities: model/project setup and cleanup, health and storage-conformance reporting, per-project isolation with shared model/reranker/GPU lock, concurrent project access and searches, leases and refcounts, root-lock identity, idle/LRU eviction, capacity refusal, and bounded shutdown/draining of warm and transient stores (72-1376). Much of this module is marked integration; one test is explicitly CUDA-marked (105-175).
- No implementation capability is established by this slice. Module docstrings and comments describe the tests' intended scenarios and rationales; they are not user-facing documentation and have not been independently verified. Inference: the set of modules suggests a quiesce lifecycle spanning controller, registry, HTTP, CLI, MCP, and TUI surfaces, plus job-resume persistence, but source for those components was not inspected.

## Interfaces and data flow

- Test-level lifecycle calls include `ServiceQuiesceController.acquire_ticket`, `begin_pause`, `wait_for_drain`, `acknowledge_vram_released`, `begin_warming`, `complete_warming`, `abort_pause`, and `fail_transition`; `ServiceRegistry` exposes the tested calls `acquire_compute_ticket`, `quiesce_resources(timeout_seconds=...)`, and `resume_resources(timeout_seconds=...)` (controller tests 27-280; registry transition tests 49-398). Tests expect immutable transition outcomes/snapshots and tickets with release/epoch evidence; implementation details remain uninspected.
- The HTTP route fixture builds `ServerRouteRuntime` with a `ServiceRegistry`, then sends bearer-authenticated `POST /pause` and `POST /resume` requests. Expected successful payloads contain `ok`, `status`, and `quiesce`; failure payloads add `error`, `message`, and `retryable`. Tests also expect unauthorized pause to return 401 (routes 162-232). A separate test deliberately uses a real loopback server and the service-client admin transport for pause, service state, and jobs (adapters 60-185, 249-315).
- The CLI tests invoke `app` with `server pause|resume --json` and optionally `--port`; expected output includes a top-level result and `data.quiesce`, with exit code 0 for achieved/idempotent outcomes and 1 for failure cases (CLI 52-180). These are test assertions only.
- The adapter test calls MCP `get_index_status(project_root=...)` after discovery and compares its returned document with the direct service-state response; it expects the canonical `quiesce` block to be preserved and heavy inference/storage packages not to appear in imports (adapters 60-212). The TUI test fetches `get_jobs` over admin HTTP and expects rendered quiesce, VRAM-release, and borrower-safety text (214-315).
- Registry tests exercise project-oriented calls including `peek_project`, `lease`, `lease_store`, `compute_lease`, `search_lease`, `try_evict`, `close_project`, `close_all`, `health`, and `get_reranker` (registry 178-350, 465-930, 932-1376). Tests create temporary vault roots, use per-test storage and job-state paths, and inspect registry/store state. No production persistence format or actual lifecycle side effect was independently confirmed.

## Boundaries and dependencies

- Locally visible relationships are through imports and fixtures: quiesce tests use `service_quiesce`, `service.ServiceRegistry`, server route runtime/app construction, CLI `app`, service-client transport, MCP `_tools.get_index_status`, and the Textual `ServerWatchApp` (adapters 13-22, 214-225; CLI 14-19; routes 14-41; registry 23-24; transitions 13-37). These imported implementations were not read.
- Test setup also depends on `. _production_service.production_service`, `.conftest.managed_env`, `._config_fixtures.reset_config`, `._quiesce_helpers`, `._job_roots`, and `test_storage_identity` helpers (adapters 21-22, 83-101; routes 34-41, 91-119; registry 363-375, 422-425; transitions 33-38). Their behavior is uninspected.
- Route/job tests attach `JobManager` to the registry's quiesce controller and use job models and run-authority types; tests create a persisted job state path and induce a failed write before repair (routes 91-119, 259-328; transitions 337-398). Storage-related tests refer to `VaultStore`, storage sidecars, Qdrant collections, and conformance state (registry 353-463, 987-1219). The imported persistence, storage, transport, and job-runner behavior is outside this slice.
- Inference: production paths cross multiple adapters but are intended to preserve controller-owned evidence. This is supported by test names and assertions, not by inspection of the adapter or route implementations.
