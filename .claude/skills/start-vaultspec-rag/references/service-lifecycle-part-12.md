## Capability summary

- [src/vaultspec_rag/tests/test_http_admin_errors.py](../../../../src/vaultspec_rag/tests/test_http_admin_errors.py): expects the shared admin and health transport to distinguish malformed or wrong-shaped responses from empty results and refused connections; return structured failures; bound timeout and auth-retry work; refuse redirects; close error responses; enforce response limits; and separate a fast connect gate from the response deadline. It uses real loopback HTTP handlers as responders (258-857).
- [src/vaultspec_rag/tests/test_http_search_errors.py](../../../../src/vaultspec_rag/tests/test_http_search_errors.py): expects HTTP search and MCP consumers to preserve valid envelopes and reject malformed ones; search routes to use their runtime registry; never-indexed searches and admission/classification failures to produce typed outcomes; status codes to follow failure classes; and combined search to retain constituent state while suppressing unusable empty results (69-983).
- [src/vaultspec_rag/tests/test_http_search_routing.py](../../../../src/vaultspec_rag/tests/test_http_search_routing.py): specifies the /logs/json URL shape, search freshness input normalization, immediate versus bounded admission, publication-target matching, typed timeout/unverifiable responses, and cleanup/cancellation behavior around ASGI disconnects (60-595).
- [src/vaultspec_rag/tests/test_import_probe.py](../../../../src/vaultspec_rag/tests/test_import_probe.py): is a positive and negative control for the shared import-probe helper: it expects detection of importing torch and torch.nn, and accepts a clean vaultspec_rag.store_schema import (1-43). The helper implementation is uninspected.
- [src/vaultspec_rag/tests/test_incremental_failure_classification.py](../../../../src/vaultspec_rag/tests/test_incremental_failure_classification.py): constructs a CODE indexer over a temporary local store with a patched lightweight encoder. It expects an injected failure after acknowledged work to mark the generation failed while retaining the confirmed delta and open receipt, require a full rebuild on recovery, preserve a successful generation on no-op, and preserve published success if a later operation raises (38-234).

## Interfaces and data flow

- Admin transport tests call private serviceclient.\_transport entry points against loopback handlers. Inputs include operation/payload/port/timeout and status-file or environment configuration; asserted outputs include mappings, None, and timeout/oversize exceptions. The auth-deadline case exercises a stale token, a refusal, discovery refresh, and retry; redirect tests record whether the bearer token reaches a second local server (258-575).
- Search response tests call try_http_search, \_search_response_envelope, and MCP \_validated_search_result, then exercise create_http_app with Starlette TestClient and authenticated POST requests. Inputs include search envelopes, root/type/query, readiness facts, registry state, and combined-domain outcomes. Assertions inspect HTTP status, JSON fields, headers, readiness evidence, remediation, and whether results is present (69-352, 353-718, 719-983).
- Routing tests normalize a request payload containing project root, query, type, freshness policy, and wait bound, then call admission/route/disconnect helpers with a ServiceRegistry. The tests inspect typed response bodies, captured generation/revision targets, cancellation, and waiter cleanup (84-595).
- Import tests pass generated child-import source from import_probe_source to assert_fresh_import_excludes; this source specifies forbidden import names and a clean control module (21-43).
- Incremental tests use CodebaseIndexer, VaultStore, and its run ledger. The test reads generation state, committed units, point IDs, failure count, and publication receipt from the temporary store/SQLite ledger to assert expected post-failure, success, and no-op state (38-234).

## Boundaries and dependencies

- The HTTP tests provide test-side evidence for contracts at service-client and server seams; they do not establish the implementation behind those imports. Their network boundary is local loopback, and their route boundary is an in-process ASGI app. They also create temporary registry, readiness, status-directory, and local-store state (258-857; 172-352; 395-595).
- Implementation: none inspected; this report makes no implementation claim. Documentation: none inspected and no documentation claim is included. Test expectations: all claims in the capability summary and Evidence table come from assertions/comments in the five assigned tests. Inference: the imports show which package seams these test callers exercise, but do not establish the full production call graph.
- No external service, GPU model, or application process was run. The incremental test explicitly substitutes an encoder returning fixed vectors (38-100); broader model/indexing behavior is outside this evidence.
