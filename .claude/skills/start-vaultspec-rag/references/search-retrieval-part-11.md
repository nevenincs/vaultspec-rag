## Capability summary

This directory contains integration coverage for vault and code search, durable result rendering/serialization, service readiness and jobs, local-store locking, and the real filesystem watcher lifecycle. Most files carry an integration marker; [src/vaultspec_rag/tests/integration/test_search_result_shape.py](../../../../src/vaultspec_rag/tests/integration/test_search_result_shape.py) is marked unit even though it resides under this directory.

- [src/vaultspec_rag/tests/integration/test_robustness.py](../../../../src/vaultspec_rag/tests/integration/test_robustness.py) covers edge inputs to document preparation and graph reranking. It writes a frontmatter-free story under `.vault/stories` and expects `prepare_document` to skip it, expects scanned audit documents with a nonstandard `related` key to remain indexable as `audit`, and expects broad search to retain positive-scored results including orphans (31-117).
- [src/vaultspec_rag/tests/integration/test_search_integration.py](../../../../src/vaultspec_rag/tests/integration/test_search_integration.py) exercises `VaultSearcher` over fixture-provided indexed vault data. It checks nonempty and descending-ranked results, type filters, `top_k`, Markdown paths, snippets and scores; relevance feedback; sparse-vector enabled/disabled query encoding; empty, filter-only, invalid, special-character, long, and adversarial filter queries; and codebase search with sparse search disabled (24-386). Its rerank cases cover disabled slicing, enabled cross-encoder ordering, the single-result shortcut, and a deliberately conflicting snippet versus `rerank_text` to express the expectation that full rerank text determines ranking (388-598). The enabled rerank test intentionally omits a shared reranker to exercise lazy loading, according to its docstring (436-454).
- [src/vaultspec_rag/tests/integration/test_search_noise_candidate_budget.py](../../../../src/vaultspec_rag/tests/integration/test_search_noise_candidate_budget.py) uses a small real local `VaultStore` and a manually constructed searcher shell to call `_fetch_codebase_candidates`. It specifies distinct candidate windows for pushed hard filters and Python path-glob filtering, then checks fallback widening when old rows lack `domain` payloads and counts dropped test-domain candidates (27-85, 88-165).
- [src/vaultspec_rag/tests/integration/test_search_result_shape.py](../../../../src/vaultspec_rag/tests/integration/test_search_result_shape.py) directly tests human CLI metadata rendering and JSON/model serialization. It expects `status` and `related` metadata to survive, codebase results to omit the vault metadata line, service serialization to preserve order and score, and `rerank_text` to stay out of the serialized transport shape (22-165).
- [src/vaultspec_rag/tests/integration/test_served_resume_drift.py](../../../../src/vaultspec_rag/tests/integration/test_served_resume_drift.py) drives a live service over HTTP. It admits a code rebuild, expects its first job to fail and readiness to degrade, retries it, mutates an admitted source, then expects a successful retry with superseded paths and restored readiness while preserving the original failed job record (71-160).
- [src/vaultspec_rag/tests/integration/test_server_doctor_route.py](../../../../src/vaultspec_rag/tests/integration/test_server_doctor_route.py) builds the real Starlette app around `ServerRouteRuntime`; it expects `GET /readiness` to reject a missing bearer token, accept the configured token, and return the same bounded snapshot as `get_readiness()` (31-69).
- [src/vaultspec_rag/tests/integration/test_server_index_concurrency.py](../../../../src/vaultspec_rag/tests/integration/test_server_index_concurrency.py) checks same-path local-store exclusion across two `VaultStore` instances and serialization of concurrent search on one store's collection lock (35-98). A marked performance case runs code indexing and code searches concurrently against a generated corpus, expects nonempty searches while indexing progresses, and checks retained CUDA reserved-memory headroom against the configured allocator fraction; it records benchmark evidence (114-244).
- [src/vaultspec_rag/tests/integration/test_server_stress_and_watcher.py](../../../../src/vaultspec_rag/tests/integration/test_server_stress_and_watcher.py) builds an isolated canonical registry/manager fixture, configures watcher/job settings, and asserts watcher/job cleanup at fixture teardown (55-125). Its helpers observe watcher-origin job snapshots and resources, manage real watcher start/stop, write documents, poll durable state and indexed payloads, and launch a separate process to hold the state lock (128-344). The tests cover vault-file intake (534-627); code create/modify/rename/delete and edits during an active watcher generation (629-759); restart refusal without canonical job history while preserving served results and publication (761-857); cooldown-suppressed deletion eventually flushing while idle ticks do not bypass cooldown (859-927); pause/coalescing and stop joining a resumed attempt, plus cancellation followed by replacement convergence (929-1027); durable failure state and restart recovery (1029-1092); state-lock contention, cancellation of an admitted claim, refresh of intent written by a retiring policy, and startup under state-lock contention (1094-1339).
- [src/vaultspec_rag/tests/integration/test_service_doctor_liveness.py](../../../../src/vaultspec_rag/tests/integration/test_service_doctor_liveness.py) invokes the Typer `server doctor` command against an isolated status directory. It specifies the dead-daemon/closed-port response as not ready with a `needs_restart` live-service state while preserving a separately labeled dependency axis, and expects dependency readiness to remain usable when no service discovery file exists (45-131).
- [src/vaultspec_rag/tests/integration/test_service_eviction.py](../../../../src/vaultspec_rag/tests/integration/test_service_eviction.py) starts real managed services and exercises HTTP routes. Helpers create small vault projects, submit and poll reindex jobs, wait for idle project references, and preserve whole response envelopes so admission failures are distinguishable from successful searches (41-190). Cases expect idle-TTL eviction, least-recently-used eviction at the project cap while a surviving warm slot can search, bounded log backups, post-rollover records in the active log, and service shutdown draining while real requests are in flight (196-523). The module docstring says these tests require a live GPU and running Qdrant (1-6); this is a source claim, not an independently verified environment fact.

## Interfaces and data flow

- Most search tests receive `rag_components` or dedicated embedding/store fixtures and construct `VaultSearcher`; they supply query text and options such as `top_k`, filters, feedback IDs, or sparse/reranker flags, then inspect result fields ([src/vaultspec_rag/tests/integration/test_search_integration.py](../../../../src/vaultspec_rag/tests/integration/test_search_integration.py) 27-386; [src/vaultspec_rag/tests/integration/test_robustness.py](../../../../src/vaultspec_rag/tests/integration/test_robustness.py) 94-117). Direct candidate-budget tests build `CodeChunk` records, upsert into a local `VaultStore`, create `_CodebaseCandidateRequest` values, call `_fetch_codebase_candidates`, and inspect rows/drop counts ([src/vaultspec_rag/tests/integration/test_search_noise_candidate_budget.py](../../../../src/vaultspec_rag/tests/integration/test_search_noise_candidate_budget.py) 27-85, 88-165).
- Result-shape tests pass dictionaries or `SearchResult` objects through CLI rendering, dataclass conversion, and `SearchResultItem.model_validate(...).model_dump(mode="json")`; expected outputs are human text and JSON-compatible fields ([src/vaultspec_rag/tests/integration/test_search_result_shape.py](../../../../src/vaultspec_rag/tests/integration/test_search_result_shape.py) 25-165).
- Service tests use temporary project roots and status directories. The HTTP cases exchange JSON envelopes with the live service using bearer tokens; the doctor route uses Starlette `TestClient` ([src/vaultspec_rag/tests/integration/test_served_resume_drift.py](../../../../src/vaultspec_rag/tests/integration/test_served_resume_drift.py) 105-160; [src/vaultspec_rag/tests/integration/test_server_doctor_route.py](../../../../src/vaultspec_rag/tests/integration/test_server_doctor_route.py) 31-69; [src/vaultspec_rag/tests/integration/test_service_eviction.py](../../../../src/vaultspec_rag/tests/integration/test_service_eviction.py) 55-103, 110-190). The liveness CLI test seeds a discovery JSON record on disk and invokes `server doctor` ([src/vaultspec_rag/tests/integration/test_service_doctor_liveness.py](../../../../src/vaultspec_rag/tests/integration/test_service_doctor_liveness.py) 45-131).
- Watcher tests write files under temporary project roots, observe manager snapshots and retry-state JSON, query store payloads, and verify readiness publications and resource ownership. A child process holds a real state lock in the contention cases ([src/vaultspec_rag/tests/integration/test_server_stress_and_watcher.py](../../../../src/vaultspec_rag/tests/integration/test_server_stress_and_watcher.py) 128-344, 369-531, 761-855, 1094-1339). The served drift test uses a bootstrap `sitecustomize.py` and control markers to coordinate source mutation after retry admission ([src/vaultspec_rag/tests/integration/test_served_resume_drift.py](../../../../src/vaultspec_rag/tests/integration/test_served_resume_drift.py) 75-105, 124-160).
- The index concurrency case calls benchmark helpers around `CodebaseIndexer.full_index` and concurrent `VaultSearcher.search_codebase`; it records corpus, timing, resource, search, and CUDA headroom fields via `retain_benchmark_evidence` ([src/vaultspec_rag/tests/integration/test_server_index_concurrency.py](../../../../src/vaultspec_rag/tests/integration/test_server_index_concurrency.py) 114-244).

- The evidence is test-side and mostly black-box at HTTP/CLI/filesystem boundaries, though several tests intentionally inspect private members such as searcher flags, store locks, watcher task maps, and indexer locks ([src/vaultspec_rag/tests/integration/test_search_integration.py](../../../../src/vaultspec_rag/tests/integration/test_search_integration.py) 199-232, 391-454; [src/vaultspec_rag/tests/integration/test_server_index_concurrency.py](../../../../src/vaultspec_rag/tests/integration/test_server_index_concurrency.py) 64-98; [src/vaultspec_rag/tests/integration/test_server_stress_and_watcher.py](../../../../src/vaultspec_rag/tests/integration/test_server_stress_and_watcher.py) 90-125, 347-367).

Imported fixture setup, service startup helpers, benchmark utilities, child-process controls, and watcher support helpers were also not read. No behavior beyond what the test source directly asserts is inferred.
- The test suite spans real local Qdrant stores, service subprocesses, GPU-marked reranking/indexing cases, ASGI routes, CLI invocations, and filesystem watcher operations. Whether these paths share production wiring or satisfy their assertions is outside this slice.
