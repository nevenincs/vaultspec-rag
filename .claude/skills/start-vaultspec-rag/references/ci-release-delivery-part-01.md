## Capability summary

- [.github/actionlint.yaml](../../../../.github/actionlint.yaml) registers the self-hosted runner labels `gpu`, `cuda`, and `build` for actionlint’s workflow-label validation (1-7).
- [.github/pull_request_template.md](../../../../.github/pull_request_template.md) prompts authors to describe the change, record each gate actually run and its result, and use one closing issue keyword per line; it also explains the limitation of comma-separated closing references (1-23).
- [.github/workflows/acquisition.yml](../../../../.github/workflows/acquisition.yml) runs public RAG acquisition on dispatch, in public or candidate mode. Candidate mode builds a common frontend from the dispatched commit. The acquisition matrix covers Linux x86_64, Linux aarch64, Windows x86_64, and macOS arm64. Public mode invokes the acquisition driver; candidate mode compiles native candidates and runs online and OS-offline smoke commands. Native acquisition evidence and smoke outputs are uploaded (1-195).
- [.github/workflows/binaries.yml](../../../../.github/workflows/binaries.yml) is a dispatch-only release-binary pipeline. It validates tag and immutable commit (or rehearsal identity), retrieves and checks the release wheel or builds one for rehearsal, builds a common frontend, builds native targets, smoke-checks and bundles them, attests release archives, and attaches only after target/archive and release-asset completeness checks. A proven draft is handed to `publish.yml` for package-index publication (1-22, 23-109, 110-264, 266-438, 439-627, 646-829).
- [.github/workflows/channels.yml](../../../../.github/workflows/channels.yml) is a manually dispatched release-channel lane with dry-run support. It rejects draft releases, reads the published checksum manifest, generates and validates Scoop and Homebrew pointers, and—outside dry run—commits only this product’s files to the shared distribution repository with bounded push/rebase retries (1-22, 24-45, 47-214).
- [.github/workflows/ci.yml](../../../../.github/workflows/ci.yml) manually dispatches the reusable accelerator workflow, selecting macOS, GPU, or both. Its comments state PR coverage belongs to [.github/workflows/merge-gate.yml](../../../../.github/workflows/merge-gate.yml) (1-19, 20-64).
- [.github/workflows/code-health.yml](../../../../.github/workflows/code-health.yml) runs a manually dispatched advisory code-health aggregate on Linux after initialization. The comments characterize the scanner results as advisory and say `just audit-all` continues across findings; the recipe behavior was not inspected (1-35, 36-73).
- [.github/workflows/devserver.yml](../../../../.github/workflows/devserver.yml) is described as generated from [dev/devserver.py](../../../../dev/devserver.py); it runs `just dev ci` on main pushes, selected pull-request events, or manual dispatch, with an internal-PR author/draft/label condition (1-23, 24-42).
- [.github/workflows/hardware.yml](../../../../.github/workflows/hardware.yml) defines reusable MPS and CUDA tiers. MPS can optionally run an advisory full suite, then warms models and runs the MPS acceptance command with fallback disabled. CUDA provisions isolated service paths, Qdrant, Node dependencies, and the monitor; starts a resident service, requires Typesafe enrollment, runs the guarded GPU test command, and stops the service even after failure (1-19, 20-54, 56-147, 148-321).
- [.github/workflows/merge-gate.yml](../../../../.github/workflows/merge-gate.yml) owns PR checks and declares a single required merge-gate check in comments. Trust conditions admit its `scope` job, which runs [dev/gate_scope.py](../../../../dev/gate_scope.py) and answers `full` (every suite), `reused` (the tree already passed on its merged pull request: audit and code scanning only) or `proof` (a version bump over a proven parent: no suite). Measuring jobs need that job and skip with it. The gate job then evaluates outcomes, checks exact-commit Dev Server proof, rejects fork PRs, and handles the `ci:full` label. Scope and gate run on GitHub-hosted runners.
- [.github/workflows/notify-marketing.yml](../../../../.github/workflows/notify-marketing.yml) manually validates the repository-specific release-tag shape and published/non-prerelease state, then dispatches an upstream-release event to the marketing repository using a dedicated token (1-53).

## Interfaces and data flow

- GitHub event interfaces include workflow dispatch, pull request, push, and the reusable hardware workflow call. Dispatch inputs carry release tags, target commits, run scopes/tiers, dry-run or rehearsal flags; reusable hardware calls accept a target SHA, tier, optional macOS suite, and required Typesafe secret (acquisition, binaries, channels, ci, hardware, merge-gate and notify-marketing triggers).
- The binary path passes validated commit identity through job outputs, checksums and wheel artifacts, a frontend artifact plus digest, per-target bundles, then release assets. Release archive provenance and monitor proofs are checked before the publication handoff. The channel lane consumes the published release’s `SHA256SUMS` and writes two product-specific files to the external `homebrew-tap` repository (binaries 54-61, 117-124, 207-264, 266-397, 399-438, 439-509, 646-829; channels 67-95, 131-157, 159-205).
- Acquisition consumes an optional tag/expected producer SHA; job steps route public runs through provenance/acquisition commands and candidate runs through frontend/native build and smoke commands (acquisition 11-26, 150-184). Outputs are uploaded as workflow artifacts (78-84, 185-195).
- CI workflow commands and jobs interface with self-hosted Linux, Windows, and macOS runners; pinned GitHub Actions; `uv`, `just`, Node/npm, GitHub CLI/API, release artifacts, and repository secrets. Hardware service state is directed to runner-temp paths; the GPU job additionally consumes a Typesafe API key and service status (hardware 161-207, 230-321; notify-marketing 24-53).
- The merge gate reads job results and GitHub API state for workflow runs, jobs, labels, PRs, and release proposals; the Dev Server proof is polled by workflow and exact SHA. The template’s gate section is author-reported evidence, not a workflow result (merge-gate job `gate`; PR template 5-9).

## Boundaries and dependencies

- The workflows define orchestration and embedded shell/PowerShell checks, but do not establish the behavior of referenced application modules or recipes. Examples include `tools.monitor.acquire`, `tools.monitor.release`, `tools.monitor.provenance`, `tools.binaries.build_pyapp`, `just release-*`, `just check-all`, `just test-python`, `just test-gpu`, `just test-mps`, and `just audit-all`; all are uninspected.
- [.github/workflows/ci.yml](../../../../.github/workflows/ci.yml) visibly calls [.github/workflows/hardware.yml](../../../../.github/workflows/hardware.yml). The hardware comments also identify `release-please.yml` as a caller, but that caller was not in the assigned slice. [.github/workflows/binaries.yml](../../../../.github/workflows/binaries.yml) dispatches `publish.yml`; channel publication is described as coming from that lane, but `publish.yml` was not inspected (ci 50-64; hardware 3-19; binaries 806-829; channels 13-15).
- [.github/workflows/merge-gate.yml](../../../../.github/workflows/merge-gate.yml) comments describe branch-protection and ruleset requirements, including the sole required check and an admin bypass. Those repository settings are claims in comments here, not independently inspected configuration (merge-gate header).
- The workflows rely on self-hosted runner labels and host-provided browser/outbound-isolation prerequisites, pinned third-party actions, GitHub artifacts/attestations/releases, the GitHub API, and secrets. Host and third-party implementations were not assessed (acquisition 94-99, 140-149; binaries 399-438; channels 73-95; hardware 161-177; merge-gate `runs-on`).
