## Capability summary

- **Implementation — [.github/workflows/publish.yml](../../../../.github/workflows/publish.yml):** Dispatches a release pipeline for a selected tag, with a default release stage and a separate package-index stage. resolve-target validates the tag, resolves its commit, requires the workflow to run from main, checks that commit against main, verifies its merged release proposal and manifest version, and ensures a draft exists for the release stage. The release stage builds a Python distribution at the resolved commit, smoke-runs the wheel and sdist under Python 3.13 and 3.14, creates/merges checksums, uploads package assets, then dispatches Binaries. The package-index stage admits the release's wheel and sdist after checksum and monitor-provenance checks, transfers those bytes to an isolated PyPI upload job, and publishes the GitHub release afterward. It then dispatches marketing, channel-pointer, and acquisition workflows.
- **Implementation — [.github/workflows/release-please.yml](../../../../.github/workflows/release-please.yml):** On pushes to main or manual dispatch, selects a pending release candidate. Pushes without a merged pending release refresh the Release Please proposal, whose own pull-request events run Dev Server and the merge gate. A candidate must change only version files over a parent whose push gate passed (`prove-parent`, [dev/gate_scope.py](../../../../dev/gate_scope.py)), pass the dependency audit (`prove-gate`) and pass the reusable hardware workflow; after those succeed, cut merges an open proposal if needed, checks that the merged tree matches the proven tree, creates and verifies the release tag, and dispatches Publish. An always-run result job checks the selected proposal or release path's job results.
- **Documentation claims in workflow comments:** The files describe a draft-first release chain, with PyPI upload before release publication and channel/acquisition dispatches after publication. They explain that draft releases are hidden from latest, that publication is intended to leave a complete visible release, and that retries/repairs are supported. These are comments describing intended workflow behavior; they do not independently establish runtime outcomes.
- **Configured test expectations:** Publish runs the checked-out pipeline's [tests/smoke_check.py](../../../../tests/smoke_check.py) against both built distribution formats for Python 3.13 and 3.14. Release Please runs the dependency audit and hardware tiers for the candidate SHA. These are configured checks only; this read did not inspect their implementations or establish that any passed.
- No other files or test modules were in the assigned source ranges.

## Interfaces and data flow

- **Publish inputs:** workflow_dispatch requires a release tag; stage is release by default or package-index. The resolver emits the exact sha and tag. The release build emits that SHA; smoke test passes it through. Artifacts are named `dist-<sha>` and `package-index-<sha>`. The admission job emits wheel and sdist SHA-256 values for the uploader. ([.github/workflows/publish.yml:18-33, 57-59, 136-145, 189-195, 362-379, 462-468, 472-504](../../../../.github/workflows/publish.yml#L18))
- **Release stage flow:** GitHub tag/API and manifest/PR data → resolved SHA → checkout/build (just init, just build-python) → dist/ artifact → two-version wheel/sdist smoke checks → release assets and SHA256SUMS → Binaries workflow dispatch with tag and target SHA. ([.github/workflows/publish.yml:61-102, 136-187, 189-258, 260-344](../../../../.github/workflows/publish.yml#L61))
- **Package-index stage flow:** Release assets → exact wheel/sdist checksum-entry validation and sha256sum -c → downloaded monitor bundles and tools.monitor.provenance invocation → package artifact plus digests → artifact download and digest recheck → uv publish --check-url https://pypi.org/simple/ → release edit to publish → marketing, channels, and acquisition workflow dispatches. ([.github/workflows/publish.yml:396-468, 499-528, 546-629](../../../../.github/workflows/publish.yml#L396))
- **Release Please flow:** GitHub PR and compare API data → candidate PR number, SHA, and merged state → parent proof, audit and reusable hardware workflow → merge/tree identity check and Release Please tag creation → remote tag identity check → Publish workflow dispatch. If no merged candidate exists, the push path runs Release Please, whose commit carries the uv.lock bump; the PR's own events run its checks. ([.github/workflows/release-please.yml](../../../../.github/workflows/release-please.yml))
- State and integrations visible here include GitHub refs, PRs, release metadata/assets, Actions dispatches/artifacts, and external PyPI publishing. The workflows use GitHub tokens with job-scoped permissions; the upload job requests id-token: write. No persistent local application storage is shown.

## Boundaries and dependencies

- Local commands include just init, just build-python, uv lock, uv publish, and uv run ... tools.monitor.provenance; their definitions and behavior were not inspected. The smoke script [tests/smoke_check.py](../../../../tests/smoke_check.py) and provenance module implementation were not inspected.
- Publish dispatches or references binaries.yml, notify-marketing.yml, channels.yml, and acquisition.yml. Release Please reuses hardware.yml, reads merge-gate.yml's push runs, and dispatches [.github/workflows/publish.yml](../../../../.github/workflows/publish.yml). Their behavior is uninspected. Comments also refer to the requires-python range and release-branch lock behavior; those source declarations were not read.
- GitHub-hosted services/API behavior, the pinned third-party Actions, self-hosted Linux X64 build runners, gh, git, shell utilities, and the PyPI trusted-publishing environment are external or runner dependencies. Their operation was not verified here.
- The [.github/workflows/publish.yml](../../../../.github/workflows/publish.yml) comments state that its artifact concurrency group is shared with binaries.yml; the other workflow was not read, so shared locking is a documentation claim in this slice.
