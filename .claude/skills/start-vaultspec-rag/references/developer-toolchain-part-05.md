## Capability summary

**Implementation**

- [dev/toolchain.py](../../../../dev/toolchain.py) is a data registry for eight developer verbs: `deps`, `lint`, `fix`, `audit`, `test`, `build`, `health`, and `ci`. Frozen `Target` and `Verb` records hold names, summaries, ordered steps, and behavior flags; `Verb.find`, `public_targets`, `find_verb`, `VERBS`, and `DEFAULTS` expose lookup, listing, and default-target data (111–174, 884–920).
- The registry also centralizes scan paths, image tags, duplication thresholds, and pytest marker selection (49–108). Its private helpers construct nested harness invocations, advisory scanner commands, and package-test commands (177–213).
- `deps` declares sync, upgrade, lock, and lock-upgrade operations (216–249). `lint` declares individual Python, typing, frontend, documentation, vault, and other static-analysis dimensions, plus `all` and `light` aggregates (296–473). `fix` declares Python, TOML, Markdown, and vault repair targets and an all-fixes aggregate (480–530).
- `audit` contains one dependency-advisory gate and advisory reporting dimensions for security, dead code, dependencies, duplication, and test-tree complexity; its `all` aggregate references the reporting dimensions (537–639). `test` declares Python, fast, GPU, performance, MPS, provisioning, and Windows selections, plus an aggregate over the Python, GPU, MPS, and performance lanes (646–793).
- `build` declares wheel/sdist build and its aggregate (800–824). `health` declares normal and fast reports, both marked advisory (831–848). `ci all` composes lint-all, dependency audit, test-all, and build-all harness commands (855–881).
- [dev/typesafe_evaluation.py](../../../../dev/typesafe_evaluation.py) defines immutable candidate records and a fixed candidate inventory. For a candidate, `result(rank)` reads its named source file, parses it, locates a matching function AST node, and builds a `SearchResult` with a rank-derived score, a 200-character snippet, the full function as rerank text, and function and line metadata (19–48, 51–82).
- [dev/typesafe_search_spike.py](../../../../dev/typesafe_search_spike.py) builds synthetic code rows from those candidates, supplies a deterministic query-encoding fixture and identity graph-order fixture, then runs five named queries through timed codebase, document, or combined search methods on a manually constructed `VaultSearcher` (26–55, 57–164). Storage responses and selected search leaves are patched in the harness; classification is not explicitly patched in this file.
- [dev/warm_models.py](../../../../dev/warm_models.py) provides a command-line wrapper around `provision_models()`: it prints each returned repository record, maps the returned action to `OK` or `FAILED`, and prints a failure detail to stderr for other actions (24–39).

**Documentation claims**

- The toolchain module describes the verbs by consequence: dependencies mutate, lint/test gate, fixes mutate, audits report leads except for dependency audit, build produces artifacts, and health measures (1–23). These are module claims; the runner’s actual exit and execution semantics were not inspected.
- Toolchain comments explain design choices and assert prior CI or runtime problems, including accelerator marker coverage, GPU test memory pressure, lane timing, and artifact-build coverage (83–105, 281–305, 650–670, 693–720, 800–809, 871–877). These explanations were not independently verified.
- The evaluation fixture says its scores are fixed fixtures rather than a measured GPU baseline, and that judgments come from the hosted endpoint (1–5). The spike says it uses real search orchestration and requires a dedicated key, while encoding, storage, and graph leaves are fixtures (1–4). The warm-up docstring says the fetch is idempotent, attempts all configured repositories, and requires all to be cached (1–14). These statements are documentation claims; no program was run.

**Test expectations**

- The spike encodes five pass conditions: retrieval of the environment-variable test; exclusion of test paths after an explicit `only:prod`; no results for the AES-GCM invoice query; retrieval of the noise guide; and a combined result containing code plus a vault/document source. Each case also requires at least two reported Typesafe requests and no classification fallback (124–143). These are expectations implemented by the script, not evidence that any case passes.
- The spike prints per-case JSON containing pass status, result IDs/sources/scores, code-fetch budgets, and timings; its process returns zero only if all five cases pass (144–164). It was not executed, so no outcome is known.

## Interfaces and data flow

- The toolchain registry’s primary data flow is `Verb` → named `Target` → ordered `Step` objects. References compose targets, while `_verb` creates a command that re-enters the harness through `python -m dev <verb> <target>` (111–185, 260–294, 461–470, 523–528, 620–637, 781–791, 855–881). The imported runner types and the code that dispatches this registry are outside the assigned ranges.
- The spike’s code path is candidate inventory → source-function extraction → `SearchResult` → synthetic code rows → mocked store fetch. Its one synthetic document is returned for document and document-search calls. The searcher is initialized with `__new__`, then receives the project root and mock store; query encoding, graph access/order, and reranking are patched before timed search calls (26–43, 57–123).
- The spike reads `EnvVar.TYPESAFE_API_KEY` from the process environment and raises if it is empty (57–60). It calls `search_{surface}_timed(query, top_k=5)` for the listed surfaces and emits JSON on stdout (87–164). The exact remote-client behavior and timing production are in uninspected imported code.
- The warm-up wrapper’s input is the result of `provision_models()`; its observable output is one line per repo plus either a success code or a stderr failure line and failure code (24–35). The cache-writing behavior belongs to the uninspected product provisioner.

## Boundaries and dependencies

- [dev/toolchain.py](../../../../dev/toolchain.py) imports `Gate` and gate constants from `dev.gates`, and command/step abstractions and builders from `dev.runner` (37–47). It declares command data and target composition here, but execution, gate probing, skip accounting, and status propagation cannot be established from this slice.
- The evaluation fixture imports the `SearchResult` model (14); the concrete search-result behavior was not inspected. Candidate paths and function names are strings, not source inspected in this assignment (51–82).
- The spike imports `VaultSearcher`, query parsing, an environment-variable enum, and candidate fixtures (15–19); it imports request/result types only for typing (21–23). Its mocked store intercepts hybrid code, document, and document-search lookups; this slice does not establish how search orchestration classifies queries or makes hosted requests (57–123).
- The warm-up wrapper imports exit codes and, inside `main`, the provisioning action and model provisioner (21, 26–35). Their definitions and effects remain outside the inspected boundary.
- Repository-source candidates in the fixture include production helpers and one test function. Their retrieval suitability and whether the live cases behave as intended cannot be confirmed without reading the named candidate files.
