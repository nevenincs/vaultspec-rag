## Capability summary

**Implementation observed**

- [src/vaultspec_rag/commands/\_tool_torch.py](../../../../src/vaultspec_rag/commands/_tool_torch.py) owns the persistent uv-tool CUDA torch repair flow. It assesses environment type, torch compute capability, and receipt durability; returns structured terminal outcomes; offers remediation commands when the repair is not run; and, when eligible and authorized, runs bounded uv steps and verifies both the resulting torch capability and receipt. The outcome includes a JSON-safe representation and a limited holder summary. (Lines 97-163, 262-320, 347-489, 491-548.)
- [src/vaultspec_rag/commands/\_torch_flow.py](../../../../src/vaultspec_rag/commands/_torch_flow.py) shares cu130 torch configuration handling between install and uninstall. Install checks enablement, install role, and detected pyproject state; handles dry-run, confirmation, patching, direct torch dependency placement, and optional uv sync. Uninstall reverses the managed config and managed direct dependency where appropriate, with dry-run and customized-state handling. (Lines 30-40, 121-245, 262-307, 310-391.)
- [src/vaultspec_rag/commands/\_uninstall.py](../../../../src/vaultspec_rag/commands/_uninstall.py) implements workspace uninstall orchestration. It gates destructive execution on force or dry-run, resolves without bootstrapping, checks workspace/link safety, preflights and transacts MCP disenrollment, removes bundled candidates and obsolete sentinels, reconciles provider/MCP state, reverses torch config, and optionally removes `.vault/data`. It records outcomes and errors in `UninstallReport`. (Lines 51-67, 69-143, 146-187, 189-347, 354-509.)
- [src/vaultspec_rag/commands/\_util.py](../../../../src/vaultspec_rag/commands/_util.py) provides cycle-safe exception-chain matching and a confirmation adapter that distinguishes approval, decline, interrupt, EOF, and callback errors. (Lines 16-55.)
- [src/vaultspec_rag/commands/\_uv_sync.py](../../../../src/vaultspec_rag/commands/_uv_sync.py) runs `uv sync --reinstall-package torch` from the target project and classifies the result into report action/warning fields, including missing uv, timeout, launch failure, and nonzero exit. (Lines 21-26, 29-126.)
- [src/vaultspec_rag/commands/\_workspace.py](../../../../src/vaultspec_rag/commands/_workspace.py) resolves/bootstrap-checks workspace paths, creates only the needed workspace directories, checks parent paths for plain directories, and initializes Core context at its explicit call site. (Lines 31-61, 64-94, 96-113.)

## Interfaces and data flow

- `repair_tool_torch(request: ToolRepairRequest) -> ToolTorchRepairOutcome` chooses the supplied interpreter or `sys.executable`, assesses it, and returns either the assessment outcome or a repair outcome. `ToolRepairRequest` carries dry-run, interpreter, consent, and stream options. `ToolTorchRepairOutcome` carries action, detail, commands, holders, remediation steps, compute capability, receipt verdict, and reason; `to_dict()` serializes these and bounded holder information. ([src/vaultspec_rag/commands/\_tool_torch.py](../../../../src/vaultspec_rag/commands/_tool_torch.py), lines 110-163, 238-250, 309-320.)
- Assessment recognizes non-uv-tool environments and torch-not-requested environments as not applicable; ready torch plus durable receipt as already ready; and capability states that cannot be repaired by reinstall as unverified. Otherwise it requests remediation. The repair branch checks repairability and dry-run first, hands off if installed release metadata is unreadable or consent is absent, then runs and verifies the remediation. ([src/vaultspec_rag/commands/\_tool_torch.py](../../../../src/vaultspec_rag/commands/_tool_torch.py), lines 262-306, 491-548.)
- Repair commands are built from provisioning helpers. Before running them, the code resolves uv from absolute PATH search, requires the requested target to be the running process's environment, and checks that `uv tool dir` plus the package entry points to that same target. Each uv step is a bounded argument-vector subprocess; verification probes changed compute state and checks receipt durability. Imported helper semantics are not included here. ([src/vaultspec_rag/commands/\_tool_torch.py](../../../../src/vaultspec_rag/commands/_tool_torch.py), lines 347-455, 458-489.)
- `uninstall_run(path, **options) -> UninstallReport` validates skip tokens and packages options into an internal request. The runner requires force or dry-run, resolves the target with bootstrap disabled, constructs a report, performs topology preflight unless MCP is skipped, checks plain workspace paths, and returns early if `.vaultspec` is absent. Otherwise it reverses MCP placement/enrollment, removes owned files and stale sentinels, runs Core cleanup, reverses torch configuration, optionally removes `.vault/data`, then returns the report. ([src/vaultspec_rag/commands/\_uninstall.py](../../../../src/vaultspec_rag/commands/_uninstall.py), lines 51-67, 354-360, 363-509.)
- The uninstall file-removal path derives bundled candidates from `list_builtins()` and uses held plain-directory operations for candidate unlinking and tree removal. Data removal checks the `.vault/data` entry type and refuses a link; dry-run records the data-removal intent and attempts to report resolved path and size. ([src/vaultspec_rag/commands/\_uninstall.py](../../../../src/vaultspec_rag/commands/_uninstall.py), lines 69-100, 146-187.)
- Torch install flow mutates the consumer [pyproject.toml](../../../../pyproject.toml) through imported inspect/mutate/direct-dependency helpers. A canonical config may ensure a direct torch dependency and optionally invoke `_run_uv_sync_torch`; a newly applied patch follows the same path. Uninstall calls the removal helper and removes the managed dependency only when the config patch reports removal. ([src/vaultspec_rag/commands/\_torch_flow.py](../../../../src/vaultspec_rag/commands/_torch_flow.py), lines 92-103, 163-245, 262-307, 310-391.)
- `_run_uv_sync_torch` resolves uv on PATH, runs with cwd set to the target, captures UTF-8 output with replacement decoding, and updates the report. On failure, classification prefers the last five stderr lines, then stdout, then an exit-code-only warning. ([src/vaultspec_rag/commands/\_uv_sync.py](../../../../src/vaultspec_rag/commands/_uv_sync.py), lines 29-86, 89-126.)
- Workspace resolution uses the supplied path or current directory and resolves it. Bootstrap mode creates the target and ensures `.vault` and `.vaultspec`; non-bootstrap mode returns the resolved path without mutation. Core context setup separately calls Core's workspace resolver and path initializer. ([src/vaultspec_rag/commands/\_workspace.py](../../../../src/vaultspec_rag/commands/_workspace.py), lines 31-61, 86-94.)
- Confirmation callers consume string outcomes: the torch-config flow records action/warnings for no terminal, EOF, interrupt, or callback error; tool repair maps outcomes to operator-facing explanations and authorizes only approval or `--yes`. ([src/vaultspec_rag/commands/\_util.py](../../../../src/vaultspec_rag/commands/_util.py), lines 35-55; [src/vaultspec_rag/commands/\_torch_flow.py](../../../../src/vaultspec_rag/commands/_torch_flow.py), lines 42-89; [src/vaultspec_rag/commands/\_tool_torch.py](../../../../src/vaultspec_rag/commands/_tool_torch.py), lines 323-344.)
